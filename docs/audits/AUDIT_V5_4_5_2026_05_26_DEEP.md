# AUDIT_V5_4_5_2026_05_26_DEEP

## Executive summary

Merged audit of lumenairy v5.4.5 across two pass campaigns:

- **v1 audit**: polarization-finder pass, 5 P3 findings carried forward (all pre-verified).
- **v2 audit**: 15 finder dimensions (11 re-runs plus 4 cross-cutting), each finding 3-lens adversarially verified.

**Counts (merged total):**

| Severity | v1 | v2 confirmed | Merged total |
|----------|----|--------------|--------------|
| P1       | 0  | 1            | 1            |
| P2       | 0  | 4            | 4            |
| P3       | 5  | 23           | 28           |
| **All**  | **5** | **28**    | **33**       |

v2 produced 86 raw findings; 58 were rejected on 3-lens review (68% rejection rate), leaving 28 confirmed.

**Themes that emerged:**

1. **JAX kernel drift behind NumPy fixes** - the v5.4.1 direction-aware root-pick correction was applied to NumPy intersect paths but not to the two JAX kernels (`_intersect_jax`, `_intersect_jax_param`). This is the only P1 and the highest-impact P3 in the report.
2. **Per-component scalarization in JonesField** - the polarization wrapper silently collapses s/p splits, drops `self.dy`, and is silent about high-NA / large-tilt / metallic-mirror / handedness regimes where per-component dispatch is physically wrong.
3. **Source-cited validity vs advertised "range"** - TiO2 and Ta2O5 coating entries advertise ranges 3x-8x wider than their cited Sellmeier fits support (same class of bug v5.4.5 fixed for SiO2 but not propagated).
4. **Cross-sibling contract drift** - two Sellmeier evaluators (`glass._sellmeier_index` vs `coatings._coating_sellmeier`) handle pole coincidence, non-physical n^2, and negative/NaN wavelength differently. v5.4.5 hardened only one.
5. **Multiprocess worker state loss** - parent's `set_default_*` / `set_fft_threads` / `set_pyfftw_planner` overrides silently revert in spawn workers. Long-standing v4.16.3 documented gap.
6. **Plan-cache lock held during expensive MEASURE build** - serializes the FFT subsystem during plan promotion.
7. **Anamorphic-grid bugs** - `polychromatic_psf` uses `dx` for the y-axis, exact class of v4.13.x footgun.
8. **Vacuous tests / dead parameters** - `mtf_radial` and `rayleigh_resolution` accept parameters never used; `test_seidel_returns_named_data` only asserts `is not None`.
9. **Stokes/Mueller convention drift** - jones_pupil_dock missing 1/2 normalization and wrong S1 sign pattern; waveplate sign convention undocumented decoupling from library exp(+i k OPL).

**Overall health verdict:**

v5.4.5 is shippable today. The single P1 (JAX kernel direction-blind root pick) is a correctness regression but is localized to the JAX trace path - users on the NumPy backend are unaffected. The four P2s are correctness/clarity-grade and ship-blocking for any caller on the affected code paths (anamorphic grids, polarized fresnel, Sellmeier extrapolation). The 28 P3s are predominantly docstring/API drift and per-component-scalarization carve-outs - non-urgent but worth a v5.5 cleanup pass. The themes show the library's correctness invariants are well-pinned on the canonical NumPy path; the leakage is into peripheral paths (JAX, JonesField wrappers, multiprocess workers, UI/Stokes) where regression coverage is thinner.

## P1 findings (must-fix -- physics/correctness)

### P1-1. JAX intersect (static-branch kernel) still uses direction-blind root pick

- **Location**: `lumenairy/raytrace/jax_trace.py:256`
- **Dimension**: ray-trace-geometry
- **Votes**: 3/3
- **What's wrong**: The v5.4.1 fix that changed direction-blind root pick to direction-aware (|t1|<=|t2| chooses the near root) was applied to `intersection.py` for the NumPy paths (both fast-spherical and Newton initial guess), but the corresponding JAX kernel `_intersect_jax` still uses the old `t1 if R > 0 else t2` selector. A backward-propagating ray (N<0 after a reflection) lands on the wrong side of the sphere.
- **Why it matters**: `trace_jax` is the production JIT path used for differentiable raytrace (Cassegrain/folded designs, optimizer surrogates). All ghost paths that traverse a mirror or any reverse leg silently put a ray on the wrong root. This is the exact bug the v5.4.1 audit P1 documents - re-surfaced in the JAX backend.
- **Evidence**:
  ```
  else:
      t_pick = t1 if R_safe > 0 else t2
      t0 = jnp.where(disc_pos, t_pick, 0.0)
      # disc<=0 means the ray missed the sphere entirely.
  ```
- **Proposed fix**: Replace `t_pick = t1 if R_safe > 0 else t2` with the direction-aware equivalent: `t_pick = jnp.where(jnp.abs(t1) <= jnp.abs(t2), t1, t2)`. Mirror the analogous fix from `intersection.py` lines 141 and 195. Add the v5.4.1 reproducer (post-reflection backward leg) to `test_v5_4_1_raytrace_mirror_backward_ray` under the JAX backend.

## P2 findings (should-fix)

### P2-1. TiO2 / Ta2O5 "range" field claims validity 3x-8x wider than the source-cited Sellmeier fit

- **Location**: `lumenairy/elements/coatings.py:404` (TiO2) and `:425` (Ta2O5)
- **Dimension**: dispersion-and-coatings
- **Votes**: 3/3
- **What's wrong**: v5.4.5 tightened SiO2 to 200-6700 nm to match Malitson 1965 (its source), but TiO2 still advertises `'range': (400e-9, 5000e-9)` while its inline comment correctly notes "DeVore 1951 ... valid 0.43-1.53 um" (430-1530 nm). TiO2's advertised range is ~3.3x wider than the source supports; Ta2O5 advertises `(350e-9, 8000e-9)` while citing "Bright 2013 ... valid 0.5-1.0 um" - 8x wider than the fit.
- **Why it matters**: Out-of-range UserWarning never fires for callers sweeping 1530-5000 nm on TiO2 even though the 1-term polynomial extrapolates well past its calibration. Same class of silent-extrapolation bug that v5.4.5 fixed for SiO2.
- **Evidence**:
  - Line 404: `'range':          (400e-9, 5000e-9),`
  - Line 406: `# DeVore 1951 ordinary-ray Sellmeier (refractiveindex.info main/TiO2/Devore-o); valid 0.43-1.53 um.`
  - Line 425: `'range':          (350e-9, 8000e-9),`
  - Line 427: `# Bright 2013 Ta2O5 1-term Sellmeier ... valid 0.5-1.0 um.`
- **Proposed fix**: Tighten TiO2 `'range'` to `(430e-9, 1530e-9)` and Ta2O5 to `(500e-9, 1000e-9)` to match cited source validity. If a wider design-band is desired, swap to a multi-pole fit (Sarkar 2019 TiO2 / Gao 2012 Ta2O5) that actually covers it; do not paper over by advertising a wider `'range'` than the cited polynomial supports.

### P2-2. polychromatic_psf centroid / D4-sigma uses dx for the y-axis (anamorphic-grid bug)

- **Location**: `lumenairy/analysis/polychromatic.py:431`
- **Dimension**: sources-coherence
- **Votes**: 3/3
- **What's wrong**: The diagnostic centroid + D4-sigma computation builds `y = (arange(N) - N/2)*dx`, but `dy` is plumbed through for the `pixel_area` scaling 20 lines earlier (line 410: `pixel_area = dx*dy`). On anamorphic grids where `dy != dx` the y centroid coordinate and the d4sigma y width are computed with the wrong physical pitch.
- **Why it matters**: Anamorphic-aware callers (the documented v4.13.x L3 fix class) get wrong metres-in-y on the diagnostic. The file's own comment at lines 401-406 acknowledges anamorphic correctness as a concern; this block then violates it.
- **Evidence**:
  ```
  x = (np.arange(N) - N / 2) * dx
  y = (np.arange(N) - N / 2) * dx
  X, Y = np.meshgrid(x, y)
  xc = float((psf_out * X).sum() / total)
  yc = float((psf_out * Y).sum() / total)
  ```
- **Proposed fix**: Replace line 431 with `y = (np.arange(N) - N / 2) * (dy if dy is not None else dx)`. Match the dy-aware `pixel_area` block above so the diagnostic respects anamorphic pitches end-to-end.

### P2-3. JonesField.apply_real_lens passes fresnel/slant_correction/absorption through without polarization-correctness guard

- **Location**: `lumenairy/elements/polarization.py:326`
- **Dimension**: per-component-scalarization
- **Votes**: 3/3
- **What's wrong**: Scalar `apply_real_lens` documents at `_lens_real.py:908` that "For polarised inputs route through the Jones pipeline" and uses an s/p-averaged INTENSITY transmission `T_eff = 0.5*(|t_s|^2 + |t_p|^2)` - the unpolarized power coefficient. `JonesField.apply_real_lens` then dispatches that same scalar to Ex AND Ey separately, so a JonesField with a 100% x-polarized input through a Brewster-angle surface receives unpolarized `sqrt(T_eff)` on both components and loses the p-vs-s split entirely. There is NO guard rejecting `fresnel=True` (or `slant_correction=True`, which activates the same theta_i/theta_t calculation in TIR masking).
- **Why it matters**: Silent, physically wrong answer for any high-AOI Fresnel pipeline through a JonesField. Extends v1 P3-4 with cross-confirming evidence.
- **Evidence**: `polarization.py:340-348` calls `apply_real_lens` twice with `fresnel=fresnel`, then `_lens_real.py:911-914`:
  ```
  t_s = 2.0 * n1c * cos_ti_safe / denom_s
  t_p = 2.0 * n1c * cos_ti_safe / denom_p
  T_eff = 0.5 * (xp.abs(t_s) ** 2 + xp.abs(t_p) ** 2)
  E = E * xp.sqrt(T_eff)
  ```
  The s/p split is collapsed BEFORE the JonesField sees the result.
- **Proposed fix**: On `JonesField.apply_real_lens`, raise `NotImplementedError` if `fresnel=True` (document that the polarized path requires a future vectorial helper). Alternatively, dispatch by computing per-pixel cos_ti and applying t_s to the s-projected component and t_p to the p-projected component (a real Jones treatment). At minimum, emit a `UserWarning` that the s/p split has been collapsed to the unpolarized power.

### P2-4. JonesField methods drop self.dy when delegating to scalar apply_real_lens / apply_mirror / apply_aperture

- **Location**: `lumenairy/elements/polarization.py:340`
- **Dimension**: per-component-scalarization
- **Votes**: 2/2
- **What's wrong**: Three of the per-component dispatch methods on `JonesField` forget to forward `self.dy` to their scalar callees, even though the scalar signatures accept a `dy` kwarg (default None -> dx). `JonesField.__init__` explicitly allows `dy != dx` (`polarization.py:118-123`), so this is not a defensive-only concern. `apply_thin_lens` (line 315) and `apply_spherical_lens` (line 320) correctly forward `dy=self.dy`, so the inconsistency is real, not a wholesale dy-unsupported decision.
- **Why it matters**: Any anamorphic JonesField (rectangular pixels) silently has its y-axis aperture / sag / radial coordinate stretched to dx in `apply_real_lens`, `apply_mirror`, and `apply_aperture`.
- **Evidence**:
  - `polarization.py:340-343` apply_real_lens: `self.Ex = apply_real_lens(self.Ex, prescription=prescription, wavelength=wavelength, dx=self.dx, ...)` - no dy.
  - `polarization.py:351-352` apply_mirror: `self.Ex = apply_mirror(self.Ex, wavelength, self.dx, **kwargs)`.
  - `polarization.py:362-363` apply_aperture: `self.Ex = apply_aperture(self.Ex, self.dx, shape=shape, ...)`.
  - Contrast `polarization.py:315` apply_thin_lens which DOES pass `dy=self.dy`.
- **Proposed fix**: Forward `dy=self.dy` in all three methods. For `apply_aperture` pass as a kwarg (the parameter is positional after dx). For `apply_mirror` likewise (signature accepts `dy=None` at the end). For `apply_real_lens` add `dy=self.dy` to both Ex and Ey calls.

## P3 findings (nice-to-have)

### P3-1. JAX always-Newton parametric intersect ALSO uses direction-blind root pick

- **Location**: `lumenairy/raytrace/jax_trace.py:1388`
- **Dimension**: ray-trace-geometry
- **Votes**: 3/3
- **What's wrong**: Second JAX intersect kernel `_intersect_jax_param` (always-Newton variant used when prescription params are JAX tracers, i.e. when curvature/conic are being optimised via `jax.grad`) carries the SAME direction-blind root pick. The kernel `trace_jax_with_prescription_grad` and the differentiable optimisation pipeline route through it.
- **Why it matters**: A backward-traveling chief ray in any optimiser run with mirrors will be initialised at the wrong sphere root; Newton then converges to a bogus intersection, silently corrupting gradients. Logged as P3 (not P1) because it shares the P1's locus, fix, and remediation patch.
- **Evidence**:
  ```
  t1 = (-b_q - sqrt_disc) / 2.0
  t2 = (-b_q + sqrt_disc) / 2.0
  t_sphere = jnp.where(R_finite > 0, t1, t2)
  t_sphere = jnp.where(disc_pos, t_sphere, 0.0)
  ```
- **Proposed fix**: Replace `t_sphere = jnp.where(R_finite > 0, t1, t2)` with `t_sphere = jnp.where(jnp.abs(t1) <= jnp.abs(t2), t1, t2)`. Note this also removes the now-unnecessary `R_finite > 0` dependence on a static-curvature sign - a JAX-traceability improvement (sign of a traced R no longer drives a where-branch).

### P3-2. Biconic / rotationally-symmetric sag derivative silently zeroes outside conic validity (norm>=0.9999) - masks bad geometry

- **Location**: `lumenairy/raytrace/surface.py:400`
- **Dimension**: ray-trace-geometry
- **Votes**: 2/3
- **What's wrong**: Both `_surface_sag_derivative` (rotational) and `_axis_deriv` (biconic) zero out the conic dz/dh contribution when `(1+k)h^2/R^2 >= 0.9999`. This zero is wrong - the surface-normal at that radius becomes (0, 0, 1) (a flat) even though the sag formula itself becomes complex (no real surface). For a hyperbolic mirror (k<-1) with rays approaching the asymptote, the normal silently flips to axial and refraction/reflection proceeds with a nonsense normal. `lenses.py:322` uses the same 0.9999 clamp and returns 0 for sag, so the ray lands at z=0 with a flat normal regardless of the real surface.
- **Why it matters**: Combined with the JAX direction-blind bug, would silently corrupt rather than RAY_MISSED.
- **Evidence**:
  ```
  valid = norm < 0.9999
  denom = np.where(valid, np.sqrt(np.maximum(1 - norm, 1e-30)), 1.0)
  # d(sag)/dh for conic: h / (R * sqrt(1 - (1+k)*h^2/R^2))
  dz_dh = np.where(valid, h / (R * denom), 0.0)
  ```
- **Proposed fix**: When `norm >= 0.9999` set the rays' `alive=False` with `RAY_MISSED_SURFACE` (or a new `RAY_BEYOND_CONIC` code) rather than silently returning 0. Requires plumbing a mask back from `_surface_sag_derivatives_xy` to the intersection loop. Less invasive interim: at the trace-loop level after `_intersect_surface`, verify `|sag(xi, yi) - zi| < tolerance` and kill rays where it isn't.

### P3-3. Tangent-ray (disc == 0) treated as "missed" on NumPy fast path

- **Location**: `lumenairy/raytrace/intersection.py:146`
- **Dimension**: ray-trace-geometry
- **Votes**: 2/3
- **What's wrong**: Both fast-spherical and Newton initial-guess branches use `disc > 0` (strict) to gate the intersection. The tangent case `disc == 0` is a real single-point intersection (ray tangent to the sphere) but is treated as "missed" (rays marked dead with `RAY_MISSED_SURFACE`). For an aperture-grazing ray in a stop trace or a chief-ray search where the chief ray sits exactly on the stop edge, this drops the ray that should be the canonical chief.
- **Why it matters**: Not a regression (pre-v5.4.1 the comment claims this matched legacy vignetting), but a known footgun for stop-edge tracing.
- **Evidence**:
  ```
  # disc <= 0: ray entirely misses the sphere.  Disc == 0 is
  # the tangent case -- legacy behaviour treats it as "missed"
  # to keep the same vignetting cutoff.
  disc_pos = disc > 0
  t = np.where(disc_pos, t, 0.0)
  ```
- **Proposed fix**: Change `disc > 0` to `disc >= 0` (or `disc > -tol_disc * (1 + |b|)`) on both NumPy paths. Add a test: a collimated ray at exactly `r = semi_diameter` against a flat-stop-then-sphere should produce a finite intersection (currently produces `RAY_MISSED_SURFACE`).

### P3-4. glass.py _sellmeier_index / _polynomial_index have no NaN or negative-wavelength guards

- **Location**: `lumenairy/glass.py:583`
- **Dimension**: dispersion-and-coatings
- **Votes**: 2/3
- **What's wrong**: v5.4.5 added negative-wavelength and NaN guards to `coatings.get_coating_material_index` but the sibling `get_glass_index` dispatcher and its evaluators have ZERO such guards. `_sellmeier_index` squares lam (so a negative wavelength silently returns `n(|lam|)` - the same class of bug v5.4.5 fixed). Worse, `_polynomial_index` at line 541 computes `lam_um ** exponent_i` directly: for bundled Hikari/Sumita/CDGM polynomials with odd negative powers, a negative wavelength returns a different value than `|wavelength|` - silently wrong. NaN wavelengths propagate without warning.
- **Why it matters**: Cross-module parity gap with the v5.4.5 coatings fix.
- **Evidence**:
  - Line 583: `lam2 = (wavelength_m * 1e6) ** 2  # wavelength^2 in um^2`
  - Line 541: `lam_um = float(wavelength_m) * 1e6` (no abs, no NaN check)
  - Line 544: `n_sq = n_sq + float(c_i) * (lam_um ** float(exponent_i))`
- **Proposed fix**: Add the same triad of guards to `glass.py` that `coatings.py` got in v5.4.5: (1) `np.any(wl_arr < 0)` -> UserWarning about sign-symmetry / probable unit error, then proceed with `np.abs(wl)`; (2) `np.any(np.isnan(wl_arr))` -> UserWarning about upstream NaN propagation; (3) for `_polynomial_index`, treat negative wavelength as a hard `ValueError` (NOT just a warning) because, unlike Sellmeier, the polynomial form is NOT sign-symmetric - silently returning `n(-lam) != n(|lam|)` is a worse bug than the Sellmeier one v5.4.5 caught.

### P3-5. No energy-conservation R+T=1 pin test for lossless coating stacks

- **Location**: `lumenairy/elements/coatings.py:290`
- **Dimension**: dispersion-and-coatings
- **Votes**: 2/3
- **What's wrong**: `coating_reflectance` returns R and T but the test suite never asserts `R+T ~ 1` for a stack with all-real-n layers. Grep across `tests/` for `R + T`, `R\+T`, `energy.*conservation` -> no matches. T computation in the "avg" branch uses `np.maximum(0.0, 0.5*(T_s+T_p))` which silently clamps negative T but provides no upper-bound check; combined with the Macleod p-pol sign convention being implicit, any future refactor that flips a sign in the eta_p admittance would not be caught.
- **Why it matters**: Especially load-bearing because the TMM was vectorised in v4.14 (tournament reduction over the layer axis) - a regression should be caught by an energy-conservation assertion.
- **Evidence**:
  - Line 290: `T[:] = np.maximum(0.0, 0.5 * (T_s + T_p))` (no symmetric clip to <=1, no R+T assertion in tests)
  - Grep `tests/` for `R + T` returns no matches.
- **Proposed fix**: Add a unit test that (a) takes a lossless multilayer (all-real n, no metal), (b) sweeps wavelength inside each layer's validity band at normal AND off-normal incidence for both s and p, (c) asserts `np.allclose(R + T, 1.0, atol=1e-9)` and asserts `max(R) <= 1.0 + 1e-12` and `max(T) <= 1.0 + 1e-12`. Use bundled `quarter_wave_ar` and `broadband_ar_v_coat` designs as fixtures so the test follows future API changes naturally.

### P3-7. coatings.py _coating_sellmeier dummy-pole guard differs from glass.py _sellmeier_index handling

- **Location**: `lumenairy/elements/coatings.py:501`
- **Dimension**: dispersion-and-coatings
- **Votes**: 2/3
- **What's wrong**: Two Sellmeier evaluators ship in the library: `glass._sellmeier_index` (raises ValueError if `lam^2 == C_i` within 1e-12 OR if `n^2 - 1 <= -1`) and `coatings._coating_sellmeier` (skips poles where B == 0 to avoid div-by-zero at the 1-term TiO2/Ta2O5 dummies). The two evaluators have ~the same job and overlapping callers but contradict each other on: (a) pole-coincidence handling - glass.py raises, coatings.py silently returns NaN; (b) non-physical n^2 - glass.py raises, coatings.py does `np.sqrt` unconditionally and propagates NaN; (c) glass_name labelling - glass.py threads it through error messages, coatings.py has none.
- **Why it matters**: Maintenance hazard - a Sellmeier audit fix landing in one will silently fail to land in the other.
- **Evidence**:
  - `coatings.py:501-504`: `for B, C in ((B1, C1), (B2, C2), (B3, C3)): if B == 0: continue; n_sq_minus_1 = n_sq_minus_1 + B * lam2 / (lam2 - C)`
  - `glass.py:586-592`: `for ci in (C1, C2, C3): if abs(lam2 - ci) < 1e-12: raise ValueError(...)`
- **Proposed fix**: Consolidate to a single `_sellmeier_eval(wavelength_m, coeffs, *, label='')` helper in `glass.py` and have `coatings._coating_sellmeier` delegate. Add the dummy-pole-skip (B == 0) optimisation to the unified helper. Add NaN-radicand check and pole-coincidence check. Move the cross-cutting v5.4.5 negative/NaN wavelength warnings into the unified helper so P3-4 lands once.

### P3-10. Per-realization unit-mean normalization biases the Schell MCF kernel

- **Location**: `lumenairy/sources/core.py:1857`
- **Dimension**: sources-coherence
- **Votes**: 3/3
- **What's wrong**: `_schell_phase_realizations` divides each individual realisation by `sqrt(mean(|Phi|^2))` computed from that realisation. The Schell two-point correlation `<phi(r1) phi*(r2)>` converges to the kernel `exp(-|r1-r2|^2/(2 sigma_g^2))` only when phi is scaled by a fixed deterministic constant, not by the realisation-specific random scalar. Dividing each realisation by its own random mean intensity is a non-linear operation in the ensemble that biases the empirical MCF.
- **Why it matters**: Bias is O(1/sqrt(N_pix)) per realisation but is systematic, not zero-mean, so it does NOT average out with more realisations. Docstring claim no longer holds exactly.
- **Evidence**:
  ```
  # Normalise to unit mean intensity per realisation.
  mean_I = float(np.mean(np.abs(Phi) ** 2))
  if mean_I > 0.0:
  ```

### P3-13. MEASURE plan build runs under global plan-cache lock, blocking every concurrent FFT for 100-1000 ms

- **Location**: `lumenairy/propagators/fft_infra.py:891`

- **Votes**: 3/3

### P3-14. _PYFFTW_BAD_SHAPES set mutated without a lock

- **Location**: `lumenairy/propagators/fft_infra.py:1441`
- **Dimension**: memory-perf-threading
- **Votes**: 3/3

### P3-19. JonesField.apply_mirror silent about ideal-phase-only model and circular-polarization handedness inversion

- **Location**: `lumenairy/elements/polarization.py:350`
- **Dimension**: per-component-scalarization
- **Votes**: 3/3
