## 1. V5 -- the cost gate was fit-backend-blind and size-blind

### 1.1 Root cause

`_note_pool_deferral(n_workers, seconds)` stored a BARE WALL TIME against a
worker count.  `_pool_reuse_is_likely(n_workers)` then applied it to every
later inversion at that worker count that cleared `_POOL_MIN_PIXELS_WARM`.

Neither of the two things that actually decide the cost was in the key:

* **the fit backend.**  At a FIXED 65 536 Newton points the serial step is
  0.048 s (polynomial + numba -- its Chebyshev evaluator is an
  `@njit(parallel=True)` kernel already using every core), 0.553 s (spline --
  `RectBivariateSpline.ev`, single threaded, holds the GIL) and 0.95 s
  (polynomial, numba unavailable).  A 20x spread at identical size, against a
  ~0.22 s per-dispatch pool overhead.  Those numbers are `FIX_D1_POOL` S3's
  own table -- i.e. the design already knew the backend was the cost driver,
  and then keyed the evidence on something else.
* **the point count.**  The warm band spans 8 000 - 200 000 points, a 25x
  range, and the step's cost scales with points.

### 1.2 Fail-before (reproduced with the verifier's own probes, unmodified)

`scratchpad/p_d1_pool.py`, shipped cost gate, nothing neutralised, one
scenario per fresh process, `n_workers=4`:

```
  BEFORE (settled tree, f2c0eeb)
    crosscontam   2 SPLINE groups @ 65536 pts -> dispatches 0  state=(4, 0.5038, 2)
                  then 4 POLYNOMIAL groups
                       @ the SAME 65536 pts   -> dispatches 4  wall 4.943 s

    sizeextrap    2 SPLINE groups @ 116281 pts -> dispatches 0  state=(4, 1.0363, 2)
                  then 4 groups @ 16384 pts    -> dispatches 4
```

Both defects reproduce exactly as reported.  The polynomial step that
dispatched four times measures 0.048 s steady state -- **7.3x under the 0.35 s
bar** and ~4.6x cheaper than the dispatch it was replaced with.

### 1.3 Shipped fix

The pending measurement is keyed by a COST CLASS and re-armed from scratch
whenever any leg of it changes:

| leg | what it is | why |
|---|---|---|
| worker count | `_POOL_DEFERRED_NWORKERS` (unchanged) | a pool built for a different count is torn down and rebuilt, so it amortises nothing |
| fit backend | `_POOL_DEFERRED_CLASS`, from `_newton_cost_class(newton_fit)`: `'polynomial+numba'` / `'spline'` / `'polynomial'` | the 20x spread above is measured at FIXED size, so it is a property of the backend, not of the work |
| point-count band | `_POOL_DEFERRED_POINTS` + `_POOL_PROMOTE_SIZE_RATIO = 2.0` | the step's cost scales with points and the warm band is 25x wide |

and, inside the band, the recorded sample is SCALED to the querying call's
size before it meets the bar:

```
    est = _POOL_DEFERRED_SECONDS * n_points / _POOL_DEFERRED_POINTS
    promote iff  est >= _POOL_PROMOTE_MIN_SECONDS
```

Three design points worth stating rather than leaving to be re-derived:

1. **Band AND scaling, not one or the other.**  Scaling alone would
   extrapolate a 25x range on an unmeasured linearity assumption (there is a
   fixed per-call fit/setup cost, so the step is not exactly proportional to
   points).  The band alone would leave the estimate flat across a factor of
   two, i.e. up to 2x optimistic at the edge, against a bar that carries only
   1.4x margin over the measured break-even.  Together, the extrapolation is
   never applied over more than a factor of 2, which is where
   proportionality is a defensible local model.
2. **The estimator is now the cheapest sample PER POINT** in the bucket, kept
   together with its own point count so the pair is one coherent measurement.
   With every sample the same size (the normal case) that is exactly the
   previous "minimum wall time" rule, so
   `test_the_cost_gate_rejects_a_cheap_newton_step` still asserts what it
   used to.
3. **Re-arm, do not widen.**  The cost of being wrong is asymmetric: a bucket
   that has to re-measure loses the win on two calls, while a bucket that
   promotes on another bucket's evidence taxes every remaining call in the
   process.  `_newton_cost_class` gives an unknown `newton_fit` a bucket of
   its own for the same reason.

`_note_pool_deferral` and `_pool_reuse_is_likely` take the cost class and the
point count as REQUIRED arguments, so no call site can be backend- or
size-blind by omission.  `close_worker_pool()` clears the two new fields as
well, so it still returns the process to a genuinely cold state.

### 1.5 What the fix costs

A heterogeneous chain that ALTERNATES sizes across the band edge (65 536,
16 384, 65 536, ...) now never accumulates two samples in one bucket, so it
never promotes where it previously would have.  That is under-promotion: it
loses the win on those calls and costs nothing else.  Deliberate, per design
point 3 above.

## 2. V4 -- `on_fit_domain_basis` had no validation

### 2.1 Fail-before (verifier's probe `scratchpad/p_d5_bypass.py` S3, unmodified)

```
  BEFORE
    on_fit_domain_basis='warn'   : exc=None        announcements=1  returned=True
    on_fit_domain_basis='error'  : exc=ValueError  announcements=0  returned=False
    on_fit_domain_basis='silent' : exc=None        announcements=0  returned=True
    on_fit_domain_basis='warm'   : NO RAISE   announcements=1
    on_fit_domain_basis='Error'  : NO RAISE   announcements=1
    on_fit_domain_basis=None     : NO RAISE   announcements=1
    on_fit_domain_basis=1        : NO RAISE   announcements=1
    on_fit_domain_basis=''       : NO RAISE   announcements=1
    on_fit_domain_basis='ignore' : NO RAISE   announcements=1
```

The knob was read in exactly two places -- `!= 'silent'` and `== 'error'` --
so its complete semantics were "'silent' suppresses, 'error' raises,
EVERYTHING ELSE warns".

Two consequences, the second with teeth:

1. `'Error'` -- a caller who wants the combination FATAL gets a
   `RuntimeWarning` and a returned field.  Past the aperture:beam cliff on the
   spline basis that field can be ALL ZERO (`FIX_D2_D3_D5` S3.2), i.e. exactly
   the silent-wrong-answer path the knob exists to close.
2. `'ignore'` -- the vocabulary every `on_*` knob in
   `lumenairy/propagators/carrier.py` uses for suppression
   (`_check_guard_action`: `'error'` / `'warn'` / `'ignore'`) -- was accepted
   AND INERT.  It neither silenced nor complained.

### 2.2 The valid set, decided and documented

| value | behaviour |
|---|---|
| `'warn'` (default) | name which knob is inert, warn, continue |
| `'error'` | RAISE `ValueError` where the announcement would have fired |
| `'silent'` | acknowledge -- what a caller deliberately using spline as a fit-domain-free reference passes |
| `'ignore'`, `'off'` | accepted ALIASES for `'silent'` |
| anything else | `ValueError` at ENTRY |

The aliases are not indulgence.  This one knob sits between two house styles:
`carrier.py`'s guards spell suppression `'ignore'`, and this signature's own
siblings (`on_undersample`, `on_aperture_beam`) spell it `'silent'`.
`on_noncollimated` in this same file already resolves that exact collision the
same way (`_NONCOL_ALIASES` maps `'silent'`/`'ignore'` onto its canonical
`'off'`), so honouring `'ignore'`/`'off'` here is the house rule, not a new
one.  Rejecting them outright would also have been honest; accepting them and
doing nothing was not.

The gate sits at ENTRY, in the same "Enum membership guards" block as
`on_noncollimated` and `inversion_method` -- i.e. AFTER the
`_check_2d_scalar_field` dispatcher guard (so
`test_v4_15_3_dispatcher_pin_2d_scalar_field` is unaffected) and BEFORE any
propagation.  Placing it next to the announcement's own read site would have
left every call that does not reach that branch -- including every
default-basis call -- silently accepting junk.  Same `ValueError`, same
message shape as `on_noncollimated`:

```
apply_real_lens_traced: on_fit_domain_basis='Error' is not a valid policy.
Choose from 'warn' (default), 'error', 'silent' ('ignore' / 'off' are accepted
aliases for 'silent').  Pre-v5.32.2 any unrecognised value silently selected
'warn', so a caller asking for 'error' got a warning and a returned field
instead of a refusal.
```
