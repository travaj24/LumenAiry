# Lumenairy v4.13.0 — Audit Report

**Date:** 2026-05-17
**PyPI state:** v4.12.2 published 2026-05-17T04:27:54Z. v4.13.0 tagged in git, not yet on PyPI.
**Scope:** Two releases since the last audit (`AUDIT_V4_12_1_2026_05_16.md`):
- **v4.12.2** — pre-PyPI audit closure (A1-A5, D3/D4, 878×→300× reconciliation, Item 11 strengthening, L1/L7 follow-ups)
- **v4.13.0** — Phase 1 (S1/S2/S3 + L2/L3/L4/L6/L8 audit known-limitations), Phase 2 (`except Exception:` sweep), Phase 3 (Tier-2 perf bundle, rcwa→thin_grating rename)

**Methodology:** 8 parallel single-domain audit agents across (1) v4.12.2 cache hygiene, (2) S1-S3, (3) L2-L8, (4) except-sweep + rename, (5) Tier-2 perf bundle, (6) cross-cutting physics correctness, (7) previously under-examined areas, (8) PyPI release artifacts. ~7,445 lines of diff across 74 files reviewed.

---

## TL;DR

**v4.12.2 closes its scoped objectives correctly** — A1/A2/A3/A5 cache hygiene, D3/D4 documentation-drift-made-true, and the 878×→300× headline reconciliation all verified at the published git tag. PyPI artifact is clean (correct sha256, not yanked, all 9 cache symbols importable from `la.`, `pytest-benchmark` actually in the `dev` extra).

**v4.13.0 (tagged, pending publish) substantively delivers all 13 audit-known-limitation closures (S1-S3, L1-L8) plus the except-sweep and Tier-2 perf bundle.** Test count grew from 482 → 573; 34/34 validation files pass.

**However, this audit identified 7 P1 (latent bug) findings — most importantly 3 sibling-gap recurrences in v4.13.0's own audit closures.** The pattern that round 1, 2, 3, 4, and 5 each found is here again: a fix sweeps N call sites but misses N+1.

- **L4a missed its own parent** — `apply_real_lens` (the non-`_traced`, non-`_maslov` variant) did not get the same mirror guard that the 4 siblings received. Silent miscomputation for a hand-built prescription with `surfaces[i]['is_mirror']=True` and no `'elements'` key.
- **L2 missed `error_reduction_jax` / `hybrid_input_output_jax`** — these skip `_resolve_jax_complex_dtype`, so `dtype=np.float64` with `jax_enable_x64=False` silently demotes to complex64. The exact bug L2 was supposed to close, still live on those two kernels.
- **L3 missed `Source.propagate()` + 5 classmethod factories** — `dy` is dropped from the wrapped Source. The underlying E-field uses the anamorphic grid; the Source dataclass advertises `dy=dx`.

Plus: a non-functional UI dock (`ThinGratingDock._run` kwargs don't match the function signature; click silently no-ops), an `_context.py` import outside its try-block (one bad import bypasses 6 cache-clear guards), `RandomState.choice` on JAX silently ignoring `replace=False`, and a merit-propagator inconsistency where off-nominal optimization legs use a different physical model than the nominal leg.

**Verdict:** v4.12.2 is safe on PyPI. **v4.13.0 should not be tagged for PyPI until at least P1-A (apply_real_lens mirror guard), P1-B (ER/HIO dtype resolver), P1-C (Source.propagate dy threading), and the UI dock signature mismatch are fixed.** All four are short fixes (~10-30 LOC each), all four have clear test gaps that should be closed alongside.

Documentation drift is the other large finding class — 12 CHANGELOG-vs-code mismatches catalogued (line numbers, function names, threshold directions, claim tightness). Each is cosmetic individually; collectively they erode doc trust.

**Physics verification (Stream 6):** The Seidel σ-scaling derivation is mathematically sound for paraxial third-order theory:
- Chief-ray initial conditions are exactly linear in field angle σ
- Through the paraxial transfer matrix (linear) and refraction (linear in y, nu), chief-ray quantities at every surface remain ∝ σ
- Lagrange invariant `H = y_c·nu_m − y_m·nu_c` ∝ σ (since `y_c, nu_c ∝ σ` and `y_m, nu_m` are field-independent)
- Therefore: `S1 ∝ const`, `S4 ∝ const`, `S2 ∝ σ`, `S3 ∝ σ²`, `S5 ∝ σ³`, `y_chief ∝ σ` ✅

### P1 findings (latent bugs — fix before PyPI tag)

#### P1-A — `apply_real_lens` missed the L4a `surfaces`-list mirror guard

**File:** `lumenairy/elements/_lens_real.py:194` (`apply_real_lens` body)

The L4a fix hardened four `apply_real_lens_*` siblings (`_traced`, `_traced_jax`, `_maslov`, `_maslov_jax`) to reject `is_mirror=True` in the surfaces list. But the parent `apply_real_lens` itself was NOT hardened — it only calls `_check_no_silent_fold_drop` which inspects `prescription['elements']`, not `prescription['surfaces']`. A user with a hand-built prescription containing `surfaces[i]['is_mirror']=True` or `'glass_after'='MIRROR'` (and no `'elements'` key) gets:
- `ValueError` from the 4 hardened siblings (correct)
- **Silent miscomputation** from `apply_real_lens` (treats mirror as refractor with wrong sign)

This propagates into `chromatic_focal_shift` (`analysis/core.py:1055`) and `multi_field_strehl_map` (`:1228`), which both call `apply_real_lens` directly.

The L4a test class (`test_audit_fixes_v4_13_0_jax_dtype_dy_siblings.py:384-421`) tests only the 3 hardened siblings — its comment says "Pin the mirror guard fires for all three siblings of `apply_real_lens_traced`", missing that `apply_real_lens` itself is a sibling that was supposed to be in the sweep.

**Fix:** Port the same pre-flight `is_mirror` / `glass_after='MIRROR'` guard from `_lens_traced.py:1286-1290` (the template) into `_lens_real.py:apply_real_lens`. Extend the L4a test class with a fourth test calling `apply_real_lens` (not its siblings).

#### P1-B — L2 fix missed `error_reduction_jax` and `hybrid_input_output_jax`

**File:** `lumenairy/analysis/phase_retrieval.py:794`, `:848`

`gerchberg_saxton_jax` (`:736-746`) correctly routes through `_resolve_jax_complex_dtype`, which auto-enables `jax_enable_x64` (with a `RuntimeWarning`) when complex128 is requested. The two sibling kernels `error_reduction_jax` (`:794-806`) and `hybrid_input_output_jax` (`:848-859`) skip this step — they just do `jnp.asarray(measured_amplitude, dtype=dtype)`.

If a user passes `dtype=np.float64` while `jax_enable_x64=False`:
- JAX silently demotes intermediate `1j * init_phase` to complex64
- The cache key encodes `'float64'` but the kernel internals are float32/complex64
- This is the EXACT silent-demotion bug L2 was supposed to close, still live on ER/HIO

`gerchberg_saxton` is correctly fixed; the L2 sweep stopped one function short of completeness.

**Fix:** Route the `dtype` argument through `_resolve_jax_complex_dtype` in both `error_reduction_jax` and `hybrid_input_output_jax`, matching the GS pattern. Add a test exercising ER/HIO with `dtype=np.float64` under `jax_enable_x64=False` and assert the output dtype is complex128 (or that the warning fires).

#### P1-C — `Source.propagate()` and 5 classmethod factories drop `dy`

**File:** `lumenairy/sources/core.py:1030-1033` (`Source.propagate`) and `:1045-1124` (5 factories)

`Source.propagate(...)` constructs the result Source without `dy=self.dy`. An anamorphic source's y-pitch is silently lost on every call. Same gap in:
- `Source.gaussian` (lines 1045-1064)
- `Source.plane_wave` (lines 1066-1078)
- `Source.point_source` (lines 1080-1097)
- `Source.top_hat` (lines 1099-1112)
- `Source.fiber_mode` (lines 1114-1124)

Each factory forwards `dy` to its `create_*` helper via `**factory_kwargs` (so the underlying E-field IS built on the anamorphic grid via `create_gaussian_beam:150`), but the wrapped `cls(E=E, dx=dx, wavelength=wavelength, ...)` call at the end omits `dy`. The result advertises `dy == dx` even though `E.shape` reflects anamorphic pixel counts.

**Fix:** Add `dy=self.dy` (for `propagate`) or `dy=kwargs.get('dy', dx)` (for factories) to each `cls(...)` call. Add a test exercising `Source.propagate(...).dy` — currently `grep '\.propagate\(.*\)\.dy'` across tests returns nothing.

#### P1-D — `ThinGratingDock._run` calls `grating_efficiency_vs_wavelength` with wrong kwargs

**File:** `lumenairy/ui/thin_grating_dock.py:145-155`

The dock's run handler calls:
```python
la.grating_efficiency_vs_wavelength(
    groove_index=..., substrate_index=..., profile=..., angle=...
)
```

But the function (`thin_grating.py:170`) expects:
```python
grating_efficiency_vs_wavelength(
    period, depth, *, n_ridge, n_groove, n_substrate, n_superstrate, order, ...
)
```

Required `n_ridge` and `n_superstrate` are not provided. Every dock click raises `TypeError: grating_efficiency_vs_wavelength() got an unexpected keyword argument 'groove_index'`, swallowed silently into the summary text box. **The dock is non-functional.** Most likely written against an earlier API and never re-tested after the v4.4.0 public-symbol rename + v4.13.0 file rename. **Zero test coverage on this dock.**

**Fix:** Either rewrite `_run` to use current kwargs, or stub the dock with a clear "stub" message. Add a smoke test that imports `ThinGratingDock`, instantiates it, and calls `_run()` against a synthetic model.

#### P1-E — `_context.py` cache-clear import outside try-block

**File:** `lumenairy/_context.py:240`

```python
from .propagators.propagation import clear_asm_caches   # line 240 -- OUTSIDE try
try:
    clear_asm_caches()
except (RuntimeError, AttributeError):
    pass
```

The block-level comment at `:237-239` says "Each call is guarded." But the import on line 240 is OUTSIDE the try block. The other 6 cache-clears use the pattern `try: from X import Y; Y()` (import inside try). If the line-240 import raises (rename, circular import, partial install), `ImportError` bypasses the function and all 6 subsequent guarded cache-clear blocks.

**Fix:** Move the import inside the try, add `ImportError` to the except tuple, matching the other 6 clears.

#### P1-F — `RandomState.choice` on JAX silently ignores `replace=False`

**File:** `lumenairy/backend/random.py:143-144`

`RandomState.choice` on JAX backend with `p=None` silently ignores `replace=False` and returns with-replacement samples. The `p=None` code path doesn't dispatch to `jax.random.choice(..., replace=False)`.

**Fix:** Either raise `NotImplementedError` when `p is None and not replace`, or use `jax.random.choice(sub, n, shape=shape, replace=False)`.

#### P1-G — Merit propagator inconsistency

**File:** `lumenairy/optimize/core.py:1975, 2080-2081, 2353`

`MultiWavelengthMerit.evaluate`, `MultiFieldMerit.evaluate`, and `ToleranceAwareMerit.evaluate` always call `apply_real_lens` directly for off-wavelength / off-field / perturbed legs, regardless of the `wave_propagator` selected at the `design_optimize` call site. The on-axis nominal `ctx.E_exit` uses the chosen propagator (GBD / HF / HFPI / asymptotic); chromatic / field / tolerance penalties use the analytic paraxial path.

For a high-NA design optimized with `wave_propagator='gbd'`, the merit's off-nominal penalties don't actually exercise GBD. The optimizer is then minimizing a hybrid objective that mixes two physical models.

**Fix:** Either thread `wave_propagator` through `sub_merit.evaluate` so off-nominal legs use the same propagator as on-axis, or add a prominent caveat to each Merit's docstring (and a warning at `design_optimize` time when `wave_propagator != 'real_lens'`).

### P2 findings (code smells)

1. **`apply_mirror` docstring says "ellipse"; code computes circle.** `elements/elements.py:147-152` comment claims geometric ellipse aperture; line 145 computes `h_sq = (X - xc)**2 + (Y - yc)**2` in physical coordinates — a true circle. Implementation correct; docstring misleading.
2. **`_resolve_jax_complex_dtype` "one-shot RuntimeWarning"** is implicit (gated by the `jax_enable_x64` flag flip), not enforced via `warnings.simplefilter('once')` or a state flag.
3. **Inconsistent cache-key dtype semantics:** GS keys on `str(np.dtype(cdtype))` (complex); ER/HIO key on `str(np.dtype(dtype))` (real). Both work, but the L2 commit comment claims uniformity.
4. **`_fd_grad_pure` doesn't validate user-supplied `f0`.** Stale `f0 != f(x)` silently produces wrong forward-FD gradients. Not triggered by current library callers (default is `'central'`).
5. **TIS broadcast hides BSDF-shape bugs.** `bsdf.py:110`'s `np.broadcast_to(B, T.shape)` silently corrects shape mismatches from subclass BSDF evaluators.
6. **`_RestoreDtype.__del__` relies on CPython refcount** for unhappy-path dtype restoration. `try/finally` would be more robust under `KeyboardInterrupt` / exception.
7. **`_merit_jac_auto` (`:2902`) doesn't pass cached `f0` or `scheme='forward'`** — pays 2× FD evaluations unnecessarily on every iteration. scipy already evaluated `merit_fn(x)` before calling jac on the same `x`.
8. **Readability:** `optimize/core.py:3001`: `method='lm' if not (bounds is not None) else 'trf'` — double negative.
9. **No cancellation protocol in `progress.py`** — callback can only halt computation by raising `KeyboardInterrupt`. Documented elsewhere as a known limitation.

### P3 findings (minor)

- `memory.py:78`: `set_max_ram(-5)` silently accepted (treated as -5 GB → negative bytes); `pick_batch_size` clamps via `min_batch=1` so no crash, but a `ValueError` on `< 0` would be cleaner.
- `memory.py:442`: `get_max_ram` missing from `__all__` despite being a documented public accessor.
- `optimize/core.py`: `MultiPrescriptionParameterization` doesn't detect duplicate `(prescription_index, *path)` entries in `free_vars`. Duplicate entries silently get separate `x[i]` slots competing for the same field.
- `backend/random.py:152-163`: `_is_jax_prng_key` detects uint32 / shape-trailing-2 typed keys but not the new opaque PRNG keys from `jax.random.key()` (JAX 0.4.20+). May reject valid keys on newer JAX.
- `elements/elements.py:154`: `xp.where(..., E, 0.0+0.0j)` literal is complex128. On JAX with x32 default this may upcast or fail jit. Suggest `xp.zeros((), dtype=E.dtype)` or `E.dtype.type(0)`.
- `optimize/core.py:2517`: FD step `step = eps * max(abs(x[i]), float(scale_floor[i]))` doesn't snap to representable. With `eps=1e-7`, `x[i]=1.5e-3`, `step=1.5e-10` — the denominator uses the requested step, not the realised one. ~1e-15 relative loss for typical radii. Marginal.
