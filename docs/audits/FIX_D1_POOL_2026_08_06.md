# FIX D1 -- the Newton pool's warm tier, made reachable AND made to pay

**2026-08-06.**  Closes review D1 (HIGH) from
`docs/audits/REVIEW_TRACED_EXACT_2026_08_05.md`, plus the D9 documentation
items.  All edits are in `lumenairy/elements/_lens_traced.py` and
`tests/unit/test_niche_newton_pool_both_fits.py`.

> **Headline.**  The reachability defect is REAL and is fixed.  But fixing
> reachability ALONE -- the change the review's "fix direction" describes --
> makes the motivating workload **5-7% SLOWER**, because at design 121's shape
> the serial Newton step costs 0.048 s while a pool dispatch costs ~0.22 s.
> So the shipped policy promotes on a MEASUREMENT, not on a point count.  On
> the default path (polynomial + numba) design 121 still runs its Newton
> inversions in-process -- and that is the fast answer, not a bug: the
> polynomial evaluator is an `@njit(parallel=True)` kernel already using all
> 24 cores.  The pool now engages automatically in the two regimes where it
> genuinely wins (spline 1.03x, numba-unavailable 1.07x end-to-end).

---

## 1. Root cause (reproduced, not taken on trust)

`_pool_is_warm` was derived from `_PERSISTENT_POOL is not None`, but
`_PERSISTENT_POOL` is created at exactly one site
(`_get_persistent_worker_pool`) which is called DOWNSTREAM of the gate that
reads it.  A process whose calls all sit in the 8k-200k band therefore never
warmed, and the two-tier threshold's warm arm was dead code.

Runtime proof, fresh process, N=512 / ray_subsample=2 (65 536 Newton points
per group -- design 121's own per-group count at rs=4), 4 workers, spy on the
single pool-dispatch site:

```
pre-fix, 3 groups                 pool created? False   dispatches 0   4.297 s
pre-fix, one 262 144-pt call
  first, then the same 3 groups   pool created? True    dispatches 3
```

The mechanism was correct; its trigger was unreachable.  This reproduces the
review's table exactly.

## 2. What the naive fix does (fail-before-switch, measured)

"Seed the pool once a pool-sized inversion has been deferred" -- i.e. a
second-call promotion with no cost test -- restores reachability and REGRESSES
the north star.  121 shape (N=1024, ray_subsample=4, 65 536 Newton points per
group, polynomial fit, 8 workers), 3 interleaved reps per arm, quiet box,
min wall (spread in brackets):

```
groups   pre-fix (all serial)          reachability-only fix        delta
   6     19.363 s [19.363-19.467]      20.673 s [20.673-21.013]     +6.8 %
  12     45.806 s [45.806-47.528]      48.215 s [48.215-50.768]     +5.3 %
```

The gap GROWS with group count, so it is a per-dispatch cost (~0.22 s at 8
workers), not a one-off spawn that more groups amortise.  Interleaving the
arms within each rep, and reporting the min, is what makes a 1.3 s effect
readable against a box whose per-group time wanders by up to 30% between
quiet and busy windows.

## 3. Why: point count is not cost

The threshold is a POINT count, but what the pool competes against is the WALL
TIME of the serial Newton step -- and at a FIXED 65 536 points that varies by
20x with the fit backend.  The polynomial fit evaluates through
`_get_cheb2d_val_grad_numba`, an `@njit(cache=True, parallel=True)` kernel, so
it is ALREADY multicore in-process (numba reports 24 threads here);
`RectBivariateSpline.ev` is single-threaded and does not release the GIL.

Per-group deferred serial Newton time, 65 536 points, same chain, 8 workers
(promotion blocked so every group is measured):

```
polynomial + numba (DEFAULT)   0.637  0.055  0.048  0.051  0.055  0.049
spline                         0.534  0.545  0.547  0.580  0.612  0.619
polynomial, numba unavailable  1.028  1.011  0.978  1.099  1.250  1.173
```

and as a share of one group's wall (steady state, N=1024/rs=4):

```
polynomial + numba   0.048 s/group    1.5 %  of the group
spline               0.553 s/group   13.1 %
polynomial, no numba 0.95  s/group   17.3 %
```

**Note the first column.**  0.637 s against a 0.048 s steady state: the first
Newton inversion in a process pays one-time numba warm-up, 13x the recurring
cost the pool would actually be competing against.  A rule that decided on
that sample promoted on an artifact -- measured, it pooled all 5 remaining
groups of a 6-group chain and cost 6.8%.

## 4. Shipped policy

Two arms, both required:

1. **Second-call promotion (reachability).**  A deferred inversion -- one that
   cleared `_POOL_MIN_PIXELS_WARM` but not `_POOL_MIN_PIXELS`, so it ran
   serial -- records a pending promotion at that worker count.  This is the
   "has been asked" flag the review asks for, as distinct from "is alive": a
   fact about the WORKLOAD, which is why it can be true before any pool
   exists.  A one-shot call never sees a second call and never pays a spawn.
2. **Cost gate (does the pool pay?).**  Each deferred inversion is TIMED.  The
   promotion arms only once `_POOL_PROMOTE_MIN_SAMPLES` (2) inversions have
   been timed at that worker count and their MINIMUM is at least
   `_POOL_PROMOTE_MIN_SECONDS` (0.35 s).

   * *Minimum*, not first or max, so the warm-up sample is outvoted by the
     first steady-state one; and conservative on a heterogeneous sweep
     (under-promoting costs only the win, over-promoting costs every
     remaining call).
   * *0.35 s*: a dispatch saves at most `t (1 - 1/n_workers)` and costs
     ~0.22 s, so break-even at 8 workers is 0.25 s.  0.35 s carries a 1.4x
     margin over break-even while sitting 6.4x above the default path's
     0.055 s.  With very few workers the break-even rises and this single
     constant is optimistic; the pool is only a modest win at n=2 anyway.

`close_worker_pool()` now also clears the pending promotion, so it is the one
entry point that returns a process to a genuinely cold state -- which is what
its name promises, what the tests need between scenarios, and the right
back-off after the pool-infrastructure fallback tears down a pool that broke.

Why promote rather than pool the first call: for a chain the two are exactly
equivalent in total cost (one call pays the spawn either way), and only the
promotion rule leaves the genuine one-shot untouched -- cold 16k measured
1.62x SLOWER pooled.

## 5. End-to-end effect

121-shape synthetic chain: 6 groups, N=1024, ray_subsample=4 (65 536 Newton
points per group), 8 workers, fresh process per rep, interleaved arms, quiet
box.  Min wall, spread in brackets.

**Default path (polynomial + numba) -- the gate correctly refuses:**

```
serial (n_workers=1)          23.842 s [23.842-23.963]   dispatches 0
pre-fix (n_workers=8)         23.177 s [23.177-23.911]   dispatches 0
SHIPPED (n_workers=8)         23.081 s [23.081-23.711]   dispatches 0
```

(6 reps were taken; the three quoted are the quiet block, reps 4-6.  Two
earlier reps show the same arms at 21.6 s and 30.4 s -- the box wanders.  With
`dispatches 0` on both arms the shipped path differs from pre-fix only by two
`perf_counter()` calls per group, so the residual spread is noise by
construction, not a measured difference.)

**Regimes where the gate fires:**

```
spline               pre-fix 29.142 s [29.142-29.592]
                     SHIPPED 28.207 s [28.207-28.366]   1.033x  4 dispatches

polynomial,          pre-fix 35.786 s [35.786-36.717]
numba unavailable    SHIPPED 33.394 s [33.394-34.159]   1.072x  4 dispatches
```

4 dispatches out of 6 groups: two groups measure the serial step, the
remaining four pool.

**Bit-identity.**  The spline arm returns `sum|F| = 1.667296197767e+04` on
both sides, and the default arm `1.667296903114e+04` across serial, pre-fix
and shipped.  The numba-unavailable arm's sums differ in the 12th digit
(`...124e+04` vs `...126e+04`) for a MEASUREMENT-HARNESS reason only: the
harness disables numba by setting `_NUMBA_AVAILABLE = False` in the PARENT,
while the spawned workers import lumenairy fresh and still use the numba
kernel.  That is a property of the probe, not of the library; the shipped
identity guarantee is asserted by
`test_warm_tier_pool_result_is_bit_identical_to_serial` (both fits) and
`test_pool_result_is_bit_identical_to_serial` (both fits), which pass.

**Box.**  24 logical CPUs, 128 GB RAM (103 GB free), Windows 11, Python
3.14.6, numba 0.65.1 reporting 24 threads.  Idleness was checked immediately
before each measurement block: no process above 10% CPU, aggregate 1.8-16%.

## 6. Consequence for design 121 (this contradicts the review's premise)

D1 says the unreachable warm tier is why 121's groups "ran serial", and the
task framing says that is "a large part of why the 121 runs take too long".
The reachability half is confirmed.  The impact half is **refuted by
measurement** on the shipped default:

* the Newton inversion is **1.5% of a group's wall** at rs=4 (0.048 s of
  ~3.2 s), so removing it entirely would buy ~1.5%;
* it is not "serial" in the sense that matters -- the Chebyshev evaluator's
  numba kernel already runs on all 24 cores;
* dispatching it to 8 worker processes measured a **5-7% net LOSS**.

So 121's runtime is not in the Newton inversion, and this fix is not the
speed-up that campaign wanted.  Whatever is making 121 slow should be
re-profiled with the polynomial default in force -- the handoff's own Sec 5
item 1 already flags that the only profile on record is stale.  A same-shape
profile taken for this fix puts ~23% of a group in `map_coordinates`
resampling and the rest spread across the carrier / ASM legs, with the exact
final leg (memory-dominant, quadratic in `window_factor`) outside the chain
entirely.

## 7. Follow-up (not done)

The ~0.22 s per-dispatch overhead is the constant that decides everything
above, and it is paid re-pickling the fit payload once per CHUNK -- `n_cpu`
copies of `_spline_data` per call.  Shipping it once per pool (a
`ProcessPoolExecutor` initializer, or a shared-memory handle) would lower the
break-even and could bring the default path into range at larger point counts.
Untested hypothesis; it needs its own fail-before measurement.
