## Part 2 — New findings

### 🔴 P0 — Silently-wrong physics / data loss

#### P0-NEW-1 — `storage.py:444 / :782` non-atomic `n_planes` increment

**Files:** `lumenairy/io/storage.py:444` (`append_plane_h5`), `:782` (`_zarr_append_plane`)

**Mechanism:** `grp.attrs['n_planes'] = n + 1` is written AFTER `create_dataset(name)`. Failure modes:
- **HDF5**: Crash between create and increment → orphan dataset; next append computes `name='plane_{n:02d}'` with old `n`, hits name collision → **raises**
- **Zarr**: Same scenario but `overwrite=True` at line 769 means next append **silently clobbers** the orphan
- **Concurrent**: Two appenders both read `n_planes=N`, both write to `plane_{N:02d}` → **silent data loss in Zarr**

**This is the canonical streaming-write path** used by HFPI / Monte-Carlo / `MhsPipeline.run(store=...)`. The append API is documented for sequential use but with no explicit "single-process only" warning, users running multi-process MC will hit silent loss.

**Fix:** Atomic increment via attrs transaction OR retry-on-collision with monotonic counter OR write attr BEFORE dataset creation (so partial states are detectable).

#### P0-NEW-2 — `makedammann2d` silently mangles legitimate large-period SI gratings

**File:** `lumenairy/elements/doe.py:633-636`

**Independently confirmed by F1 (P0) and F2 (P1) — disagreement on severity.**

```python
_periodx_legacy = periodx > 1e-3  # P0-NEW-2
_periody_legacy = periody > 1e-3
_waveln_legacy  = waveln  > 1e-3
```

The heuristic treats any `value > 1mm` as legacy µm. But:
- **5 mm SI grating period** (structured illumination, coarse industrial Dammann, THz/MMW) gets multiplied by 1e-6 → 5 nm garbage
- **1.1 mm SI wavelength** (far-IR / THz, legitimate) → rescaled to 1.1 nm (X-ray range)

The user gets a `DeprecationWarning` but the math runs silently with wrong output. **No upper-bound sanity check.** The 8-cell combinatorial test coverage in `test_audit_fixes_v4_14_2_agent_d.py::TestP1New6MakedammannSiUnits` does NOT exercise the 1-2 mm SI boundary — only `61e-6` and `61.0`.

**I lean P0** because of silent garbage output (no ValueError), no migration guidance for legitimate >1mm users, and real-world THz/MMW DOE designers hitting this routinely.

**Fix:** Add upper-bound sanity check (`if periodx > 1.0: raise ValueError`) OR carry an explicit `_legacy_units='um'|'SI'` kwarg rather than guessing. Document the supported range.

**P1-NEW-4** — **`create_led_source` `*args` VAR_POSITIONAL accepts new-order 5-positional and silently mis-routes** (F2)
