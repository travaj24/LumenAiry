## Part 1 — V1: publish.yml verify gate (P1 closure)

**Status: VERIFIED. Structurally sound. No bypass paths discovered.**

The new `verify` job at `.github/workflows/publish.yml:38-68`:

- `fail-fast: true` (matrix entry failure aborts whole verify job)
- Matrix `python-version: ['3.11', '3.12', '3.13']` (matches Python support window in `pyproject.toml`)
- Runs `pytest tests/unit -m "not integration" --maxfail=5` on the tag's source
- Install command `pip install -e ".[fft,perf,numba,hdf5,zarr,dev]"` + `pip install tomli` matches `unit-tests.yml` exactly (which is the lesson learned from the v5.0.1 `abf2294` "pytest not installed because [dev] not in extras" fix-up commit)
- `build` job: `needs: verify` (line 79)
- `publish` job: `needs: [verify, build]` (line 99)

**Bypass analysis (F1):**
- No `continue-on-error: true` anywhere in `publish.yml`. (`continue-on-error` does exist on the `lint` job in `unit-tests.yml:140`, but `lint` is not in the publish pipeline.)
- No `if: always()`, `if: ${{ always() }}`, or `if: success() || failure()` overrides on `build` or `publish`.
- `workflow_dispatch` is a re-run trigger only — it does not let downstream jobs skip their `needs:` dependencies. The only way to bypass `verify` is to edit `publish.yml` itself, which surfaces in the diff.

**Caveat (F1, honest):** The verify gate fires on `release: types[published]`, not on a raw tag push. A maintainer who pushes a `v*.*.*` tag and skips the GitHub Release UI step will not trigger `publish.yml` at all — but that also means nothing publishes to PyPI, so the gate IS sound for the release-to-publish flow.

**The question "Can a v5.2.0 tag tomorrow ship to PyPI with broken CI?":** No.

## Part 2 — V2: P2 closures (5 items, all verified)

### 2.1 — `tests/unit/test_v4_15_agent_e.py` doubled `@_skip_no_qt` decorators (lines 215, 254)

**Status: VERIFIED.** TestUI3 and TestUI4 each had two stacked `@_skip_no_qt` decorators; v5.1.1 reduces each to one. Empirical pytest run shows the affected tests still skip cleanly when Qt is unavailable and execute normally when Qt is present. No behavior change.

### 2.2 — `tests/unit/test_v4_16_1_agent_d.py::test_examples_output_dir` AST tightening (lines 355-393)

**Status: VERIFIED PRESENT — but PARTIALLY GAMEABLE (F1 finding, deferred to v5.2).**

The check now requires three structural signals via `ast.walk(tree)`:
1. A `'output'` string literal somewhere in the AST
2. A call to `makedirs(...)`
3. A `__file__` reference

**Closes one gameability path:** A previous bypass used `pathlib.Path(__file__).parent / 'output'` with `Path.mkdir()` — the new check requires `makedirs` specifically (not generic `mkdir`), so that bypass is now caught.

**F1's gameability demonstration (v5.2 candidate):** The three predicates are independent `ast.walk(tree)` traversals — they don't have to co-occur structurally. F1 constructed and empirically verified a passing gaming source:

```python
import os
x = 'output'                                    # signal 1
def something():
    os.makedirs('/tmp/wherever', exist_ok=True) # signal 2 (different dir!)
def loc():
    return __file__                             # signal 3
```

All three predicates fire; the pin passes even though the three pieces are functionally unrelated. **Recommendation (v5.2):** the `'output'` literal should be required to be inside the argument tree of the `makedirs(...)` call (co-located AST nodes), not anywhere in the file.

### 2.3 — `tests/unit/test_validation_helpers.py` Migration-Guide content-locks (lines 375-457)

**Status: VERIFIED PRESENT — ROBUST TO RENAME, LOOSE ON DELETION (F1 finding, deferred to v5.2).**

The `_migration_guide_text()` helper anchors on `repo_root / 'Migration-Guide.md'` and asserts `guide.is_file()`. Three content-lock blocks added inside the three existing shim-removal tests pin the actual recipe text for:
- `lumenairy.ao` removal
- `lumenairy.io.hdf5` removal
- v5.0 `propagate_through_system` move (full `from lumenairy.propagators.system import propagate_through_system` substring — tightest of the three)

**Rename robustness:** A `Migration-Guide.md` rename breaks the pin immediately. ✓
**Restructure robustness:** Pure substring `in` checks — section reorganization, heading-level changes, prose rewrites all keep the pin green so long as the literal substrings remain. ✓ (correct trade-off for documentation pinning)

**Loose-on-deletion (F1):** Each pin asserts `` '`lumenairy.ao`' in guide `` AND `'**Removed.**' in guide` as two **independent** global file substrings. The file currently has **5** `**Removed.**` instances. A maintainer who deleted the entire `lumenairy.ao` section could leave the pin green if `` `lumenairy.ao` `` (with backticks) appears anywhere else — a CHANGELOG quote, a comparison table, a "removed in v5.0" recap. **Recommendation (v5.2):** anchor `**Removed.**` to be within N lines of the shim-name match, not as a global substring.

### 2.4 — `unit-tests.yml` re-add Python 3.10 + ::error:: rationale (lines 30, 99-115)

**Status: VERIFIED.** Python 3.10 returns to the matrix; the inline `::error::` block at lines 99-115 documents the rationale for the audit reviewer (anti-fabrication: cite-the-source).
