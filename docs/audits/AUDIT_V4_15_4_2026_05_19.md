**Headline new findings (sorted by severity):**

1. **🔴 P1-NEW-2WAY-1: Walker name-filter is the new sibling-gap class** (F1 + F2 2-way confirm). 30+ public `lumenairy.__all__` functions take 2-D `E`/`field`/`pupil` but are not matched by the walker's name prefixes. 2. **🔴 P1-NEW-F2-2: `DeformableMirror.apply` class method bypasses the guard.** Module-level `apply_dm` IS guarded (v4.15.4 new), but the class method is a 3-line `E_in * np.exp(1j * phi)` that silently broadcasts a 3-D ensemble. Walker's exclusion of class methods is documented as "they delegate to guarded module-level functions" — true for the Cluster-B operator algebra, false here.

3. **🔴 P1-NEW-V2-1: `opd_fan_data` ↔ `plot_opd_fan` units mismatch is undefended** (V2). `opd_fan_data` returns *waves*; `plot_opd_fan` expects *metres*. None of the 10 unit tests cover this end-to-end pipeline. The docstring note exists at lines 1257-1262 of `plotting.py` but is easy to miss.

4. **🔴 P1-NEW-V2-2: RMS-metric inconsistency on the 4-panel summary** (V2 + F1 2-way confirm). `_radial_rms_profile` (`plotting.py:1416`) uses raw `sqrt(mean(opd²))` (variance about zero); the 1-D fan RMS (`:1173`) and the 2-D heatmap annotation (delegated to `plot_wavefront`, `:1107-1108`) use mean-subtracted `sqrt(mean((opd - mean)²))` (variance form, standard wavefront-error RMS). For a pure-defocus OPD, the radial-RMS curve looks like `r²` (piston-dominated) while the heatmap annotation is the much smaller actual wavefront RMS. Numbers on the same figure don't reconcile.

**P1-NEW-F2-2 — `DeformableMirror.apply` bypasses the guard**

- File: `lumenairy/analysis/ao.py` (`DeformableMirror.apply` method)
- Module-level `apply_dm` IS guarded as of v4.15.4
- The class method is a 3-line `E_in * np.exp(1j * phi)` with no `_check_2d_scalar_field` call
- Failure mode: `dm.apply(np.random.randn(4,16,16).astype(complex))` returns `(4, 16, 16)` silently — the textbook silent-wrong-axis broadcast
- Walker docstring at `:308-311` explicitly excludes class methods on the basis that "per-class wrapper methods delegate to the guarded scalar functions". **True** for Cluster-B operator algebra (`ThinLens.apply`, `FreeSpace.apply`, `FourierTransform.apply`, `Aperture.apply` all delegate). **False** for `DeformableMirror.apply`.
- **Fix:** 1-line `_check_2d_scalar_field(E_in, 'DeformableMirror.apply')` at top of method body, plus a 5-line regression test in `test_v4_15_5_*.py`.

**P1-NEW-V2-1 — `opd_fan_data` ↔ `plot_opd_fan` units mismatch is undefended** (V2)

- File: `lumenairy/raytrace/core.py:3772, 3780` (returns waves: `opd / wavelength`) vs `lumenairy/analysis/plotting.py:1240-1244, 1249-1250` (docstring says metres)
- Canonical workflow trap: `plot_opd_fan(*opd_fan_data(...), units='waves', wavelength=wl)` divides by `wavelength` a *second* time → silently wrong by factor ~6e5
- Docstring note at `:1257-1262` documents the mismatch but is easy to miss
- None of the 10 unit tests cover this end-to-end pipeline; D.1.4 builds synthetic metres-data specifically to avoid the trap; D.2.3 hand-builds metres
- The runnable example does `opd_y_w * wavelength` to convert (line 70-71), but this conversion is not enforced anywhere
- **Fix:** either (a) accept waves natively via `fan_units='waves'` kwarg, or (b) add `units_in='m'` parameter, plus a regression test using `opd_fan_data` end-to-end

**P1-NEW-V2-2 — RMS-metric inconsistency on the 4-panel summary** (V2 + F1 2-way confirm)

- File: `lumenairy/analysis/plotting.py:1416` (radial RMS, raw form) vs `:1173` (1-D fan RMS, centered) vs `:1107-1108` in `plot_wavefront` (2-D heatmap RMS, centered)
- `_radial_rms_profile` computes `np.sqrt(np.mean(values ** 2))` per bin — variance about zero
- `_opd_pv_rms_1d` and `plot_wavefront` compute `np.sqrt(np.mean((finite - finite.mean()) ** 2))` — variance about mean
- For a pure-defocus OPD where each annulus is a near-constant value, the radial profile is dominated by piston (per-bin offset) and looks like `r²`; the heatmap annotation is the much smaller actual wavefront-error RMS
- On the SAME 4-panel figure, the radial-RMS curve at `r=1` and the heatmap-RMS annotation are different numbers and cannot be reconciled by the user
- Example reproduces it: example prints `PV=2.9318 / RMS=1.3347 waves`; but the figure's heatmap annotation reports centered RMS ≈ 0.89 waves (~50% disagreement)
- **Fix:** change `_radial_rms_profile` line 1416 to centered form: `values_centered = values - in_aperture_mean; sqrt(mean(values_centered² ))`. Or document the choice prominently and add a `bin_radius='linear' | 'equal_area'` kwarg.
