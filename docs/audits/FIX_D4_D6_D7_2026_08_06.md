## D4 (MED) -- `gap_kernel` string handling

### Root cause

The kernel was resolved by an `if`/`elif` chain in `_carrier_step_fast` whose
LAST arm was an unguarded catch-all:

```
if gap_kernel == 'auto':   gap_kernel = 'exact'
if gap_kernel == 'exact' and xp is not np:   ...exact xp...
elif gap_kernel == 'exact':                  ...exact numpy...
elif xp is np:                               ...FRESNEL...      <- catch-all
else:                                        ...FRESNEL xp...
```

so any value that was not literally `'auto'` or `'exact'` selected the PARAXIAL
kernel.  Two of the four public entry points (`propagate_traced_carrier_chain`,
`..._multi`) validated the knob; the other two (`propagate_carrier_referenced`,
`carrier_referenced_focus_readout`) did not validate it at all.

### Fail-before (measured 2026-08-06, working tree)

`propagate_carrier_referenced`, N=256, dx=2 um, w=60 um, R=0.5 m, z=1 mm --
distance of the returned envelope from the two reference kernels:

```
gap_kernel='auto'     -> EXACT    dist_to_exact=0.000e+00 dist_to_fresnel=2.731e-06
gap_kernel='exact'    -> EXACT    dist_to_exact=0.000e+00 dist_to_fresnel=2.731e-06
gap_kernel='fresnel'  -> FRESNEL  dist_to_exact=2.731e-06 dist_to_fresnel=0.000e+00
gap_kernel='exsct'    -> FRESNEL  dist_to_exact=2.731e-06 dist_to_fresnel=0.000e+00
gap_kernel='EXACT'    -> FRESNEL  dist_to_exact=2.731e-06 dist_to_fresnel=0.000e+00
gap_kernel='Fresnel'  -> FRESNEL  dist_to_exact=2.731e-06 dist_to_fresnel=0.000e+00
gap_kernel=None       -> FRESNEL  dist_to_exact=2.731e-06 dist_to_fresnel=0.000e+00
gap_kernel=1          -> FRESNEL  dist_to_exact=2.731e-06 dist_to_fresnel=0.000e+00
gap_kernel=''         -> FRESNEL  dist_to_exact=2.731e-06 dist_to_fresnel=0.000e+00
```

`carrier_referenced_focus_readout`, in a geometry where the two kernels are
genuinely separated (N=512, dx=1 um, w=100 um, R=-5 mm, z=4.5 mm; the readout
leg separates the kernels by relL2 4.483e-07):

```
PRE-FIX
  gap_kernel='auto'   -> EXACT    rel_to_exact=0.000e+00 rel_to_fresnel=4.483e-07
  gap_kernel='exsct'  -> FRESNEL  rel_to_exact=4.483e-07 rel_to_fresnel=0.000e+00
  gap_kernel='EXACT'  -> FRESNEL  rel_to_exact=4.483e-07 rel_to_fresnel=0.000e+00
  gap_kernel=None     -> FRESNEL  rel_to_exact=4.483e-07 rel_to_fresnel=0.000e+00
```

### Fix

* `_GAP_KERNELS = ('auto', 'exact', 'fresnel')` -- the vocabulary, spelled once.
* `_check_gap_kernel(value, fn)` raises `ValueError` for anything else,
  naming the whole accepted set, the resolution of `'auto'`, and the reason
  there is no fallback.  **Case-sensitive** (`'EXACT'` is a typo, not a
  synonym -- every other mode knob in this module is strict, and normalising
  would make this the one exception).  **`None` is refused**, explicitly: the
  documented default is the STRING `'auto'` on every signature, so `None` is
  what a forgotten variable looks like, and mapping it to a default would
  reinstate the silent path.
* Called at all four public entry points AND inside `_carrier_step_fast`
  itself -- the single site every carrier leg funnels through -- so a future
  entry point that forgets its own gate still cannot reach the paraxial arm.
* The two chain-side checks that DID exist were replaced by the shared gate.
  Their message was itself stale: it named `'fresnel'` as "(default...)" and
  omitted `'auto'` from the accepted set entirely, two releases after the
  default flipped.

### Sibling knobs (the "same disease" sweep)

Every string-valued mode knob reachable on the traced path was audited:

| Knob | Where | Verdict |
|---|---|---|
| `gap_kernel` | 4 public entry points + `_carrier_step_fast` | **was broken -- fixed** |
| `final_leg` | chain: strict (`carrier.py`, raises on anything but auto/exact/paraxial); **multi: deferred to the inner chain** | **fixed** -- validated up front in the multi (see below) |
| `carrier_reference` | chain: strict; **multi: deferred** | **fixed** -- validated up front in the multi |
| `on_tilt_exact_grid` and every other `on_*` | `_check_guard_action` | already strict |
| `self_check` | chain | already strict (`'dx'`/`'off'`/`None`, and `None` IS documented there) |
| `recombine`, `on_mem_budget`, `on_replica`, `on_readout_clip`, `readout_tile` | multi | already strict |
| `estimator`, `on_aliased` | `carrier_referenced_fit_radius` / `_fit_carrier_inv` | already strict |
| `on_ram_cap`, `on_readout_window` | `carrier_referenced_exact_focus_readout` | already strict |
| `newton_fit`, `inversion_method`, `amplitude_model`, `remap_sampling`, `preserve_input_phase` | `lumenairy/elements/_lens_traced.py` | OUT OF SCOPE (another agent owns that file).  The review already checked `newton_fit` and found it strict (`_lens_traced.py:7646`, `'auto'` resolved first). |

Why the multi's `final_leg` / `carrier_reference` mattered even though the

silently took the exact-leg branch there; and with `congruence_workers > 1`
the chain's raise has to be marshalled back out of a worker process.

### Pass-after

```

  -> ValueError at ALL FOUR public entry points and at _carrier_step_fast

```

`tests/unit/test_niche_exact_gap_kernel.py` now DISCOVERS the entry points that
take `gap_kernel` (by signature inspection over `carrier.__all__`) rather than
listing them, pins the discovered set, and walks 8 bad values x 4 entry points.
A new public function that grows the knob fails the premise guard until it is
wired in -- which is the actual D4 lesson: the defect was an entry point nobody
had thought to check.

## D4b (NEW, reported not fixed) -- the chain's `gap_kernel` never reaches its PARAXIAL focus readout

While auditing the forwarding paths: `propagate_traced_carrier_chain` builds
the paraxial readout's kwargs as

```
_par_kw = {kk: fr[kk] for kk in
           ('dx_out', 'N_out', 'standoff', 'centre_out', 'bandlimit')
           if kk in fr}
```

and `gap_kernel` is neither in that tuple nor in `_OUTPUT_GRID_PASSTHROUGH` /
`_FOCUS_READOUT_KEYS`.  So the chain-level `gap_kernel` is applied to every gap
leg but NOT to the carrier leg inside `carrier_referenced_focus_readout`, which
silently uses its own default (`'auto'` -> exact).

Consequence: a caller who passes `gap_kernel='fresnel'` to the chain for a
byte-identical legacy comparison does not get a fully paraxial run.  Today this
errs TOWARD the campaign's north star (that leg stays exact), which is why it is
reported rather than changed -- forwarding it would flip a shipped leg from
exact to paraxial for `gap_kernel='fresnel'` callers and would move test
baselines, both of which are outside this brief.

## D4c (NEW, fixed) -- the private default was still `'fresnel'`

`_carrier_step_fast(..., gap_kernel='fresnel')` and
`_propagate_carrier_focus_crossing(..., gap_kernel='fresnel')` kept the
pre-flip default when the public default became `'auto'` on 2026-08-05.  The
same silent-fallback disease as D4, one level down: any internal call that
omitted the argument would quietly run paraxial while every public path ran
exact.

It was already a live failure.
`tests/unit/test_carrier_referenced.py::test_near_focus_landing_fast_path_unchanged`
compares a DEFAULTED public call against a DEFAULTED private one:

```
out = propagate_carrier_referenced(env, 30e-3, 40e-3, WL, dx)     # 'auto' -> exact
ref = _carrier_step_fast(env, 30e-3, 40e-3, WL, dx, dx)           # 'fresnel'
assert np.array_equal(out.env, ref.env)
```

and had been FAILING on the working tree since the flip.  Proven pre-existing:
it fails identically with the D4 and D7 fixes reverted at runtime
(`PREFIX_MODE=both`).  This is one of the failures the handoff's partial
regression run (204 passed, then stopped) never reached.

**Fix:** align both private defaults to `'auto'`.  No shipped physics moves --
all three library call sites (`carrier.py:712`, `964`, `986`) pass `gap_kernel`
explicitly, so the default was reachable only from tests.  The test then passes
and once again means what it says.

## D6 (MED) -- the chain-A cache key

### Root cause

6dfc79d added `final_leg` to the `_chainA_*.npz` filename, which was correct
and genuinely orphaned the older files.  But the SAME commit flipped two
library defaults that change the cached field -- `gap_kernel` `'fresnel'` ->
`'auto'` (exact) and `newton_fit` `'polynomial'` -> `'auto'` (spline on CPU) --
and neither is a `chain_a` argument, so neither could ever appear in a
hand-spelled filename.  `nw` (`n_workers`) was also unkeyed, and `dx0` was
rounded to integer nanometres (`{dx0*1e9:.0f}nm`), so two pitches differing by
less than 0.5 nm collided.

### The audit -- every parameter now keyed

Enumerated from the `propagate_traced_carrier_chain` call `chain_a` actually
makes, not from the four the review named:

| # | Keyed | Why it changes the field |
|---|---|---|
| 1 | `schema` (`_CHAIN_A_SCHEMA`) | manual orphan switch |
| 2 | `lumenairy_version` | release-level changes |
| 3 | `lumenairy_source_sha256` -- SHA-256 over every `lumenairy/**/*.py` | catches a default flip WITHIN one version (the exact D6 failure: 6dfc79d shipped under the same 5.32.1), a semantic flip that leaves the default STRING alone (`'auto'` re-resolving), and a module-constant flip (`_FOCUS_STANDOFF_ZR` 6.0 -> 0.8).  No signature inspection can see any of those. |
| 4 | `n` | grid size; sizes `env0` |
| 5 | `dx0` -- full `repr(float)` | grid pitch; the old `%.0f nm` collided |
| 6 | `ray_subsample` (`rs`) | traced-ray density |
| 7 | `n_workers` (`nw`) | expected field-inert (the Newton pool is deterministic) but not PROVEN inert, and a cache is the wrong place to bet on that |
| 8 | `final_leg` | the 6dfc79d fix, kept |
| 9 | `chain_defaults` -- all 25 defaulted parameters of `propagate_traced_carrier_chain`, by value | `chain_a` passes none of them, so `gap_kernel`, `carrier_reference`, `na_exact_threshold`, every guard action and every tolerance are keyed |
| 10 | `traced_defaults` -- all 40 defaulted parameters of `apply_real_lens_traced`, by value | the chain drives it with `traced_kwargs=None`: `newton_fit`, `amplitude_model`, `preserve_input_phase`, `remap_sampling`, `newton_poly_order`, `inversion_method`, ... |
| 11 | `LAM`, `W0`, `Z1` | build `env0` and `r_in=R1` |
| 12 | `OBJ_GAP`, `DOE_ELEM`, `FRAME_PITCH`, `ORDERS` | the group split and `final_distance=gap_to_doe` |
| 13 | `zmx_sha256` -- content hash of the design file | the prescription IS an input; an updated `.zmx` must not be served the old field |
| 14 | `runner_sha256` -- content hash of `run_poc_119_120_v518.py` | its `_NEW_GLASSES` Sellmeier coefficients are parsed and registered at import, so they set the dispersion the trace uses |
| 15 | `d121_common_sha256` -- content hash of `_d121_common.py` itself | `geometry()` owns the group split and `chain_a` owns the source-beam construction; either can change the field with every keyed constant unchanged |

Any of 13-15 that cannot be read takes a distinct sentinel, so a cache written
WITH a file can never be read back without it.

The dict is JSON-dumped with sorted keys and SHA-256'd; the first 12 hex
characters name the file
(`_chainA_v2_n{n}_rs{rs}_{hash12}.npz`).  The full dict is ALSO stored inside
the `.npz` as `key_json` and CHECKED on load, so a file renamed or copied onto
a matching hash is refused rather than silently used.

**Stated cost, plainly:** any edit anywhere in the library invalidates chain A
(~1-2 min to rebuild at the production grid).  That is the intended trade.
A version string demonstrably does not catch a default flip, and on this branch
the alternative is a plausible-looking wrong answer.

## D7 (LOW, inherited) -- odd-`N` frequency grid

### Root cause

`_freq_sq_1d_bld` and `_freq_1d_bld` build the CENTRED frequency axis and every
caller un-shifts it with `ifftshift`, so the bins must be the integers
`j - N//2`.  They used `- N / 2`, which is the same number for even `N` but
HALF-INTEGER for odd `N`, and `ifftshift` of a half-integer axis is not
`fftfreq`:

```
N = 5, d = 1:  ifftshift(old) = [-0.1, 0.1, 0.3, -0.5, -0.3]
               fftfreq(5)     = [ 0.0, 0.2, 0.4, -0.4, -0.2]
N = 1:         ifftshift(old) = [-0.5]        fftfreq(1) = [0.0]
```

Every transfer function built on that axis multiplied the wrong spectral bin.

### Fail-before / pass-after

```
                                            BEFORE      AFTER
_exact_tf_2d_xp  vs _exact_envelope_tf_step
  N= 64 tilt=(0.00,0.00)                   3.995e-16   3.995e-16   (unchanged)
  N= 65 tilt=(0.00,0.00)                   1.239e+00   5.463e-16
  N=128 tilt=(0.05,0.02)                   4.666e-16   4.666e-16   (unchanged)
  N=127 tilt=(0.05,0.02)                   7.209e-01   8.399e-16

_fresnel_tf_2d_xp vs fresnel_tf_propagate
  N= 64                                    3.816e-16   3.816e-16   (unchanged)
  N= 65                                    1.239e+00   5.839e-16
  N=128                                    4.623e-16   4.623e-16   (unchanged)
  N=127                                    7.189e-01   8.228e-16

vs the INDEPENDENT plain-numpy exact-ASM oracle (shares no code with either
implementation), relL2 on the bright support:
  N= 64  numpy 1.540e-14   xp 1.539e-14 -> 1.539e-14
  N= 65  numpy 2.744e-14   xp 1.239e+00 -> 2.742e-14
  N=127  numpy 1.386e-12   xp 7.190e-01 -> 1.386e-12
  N=128  numpy 1.629e-13   xp 1.629e-13 -> 1.629e-13
```

### Even-`N` bit-identity (required, verified)

`N // 2 == N / 2` exactly for even `N`, so no even-`N` value can move.  Verified
bitwise rather than argued:

```
builders, new vs OLD transcription   : 15 even sizes (2..4096) x 4 pitches
                                       (1.0, 1e-6, 2e-6, 0.37e-6)   mismatches = 0
_exact_tf_2d_xp   full output        : 6 even sizes x 3 tilts       mismatches = 0
_fresnel_tf_2d_xp full output        : 6 even sizes                 mismatches = 0
_fresnel_tf_axis / _asm_axis output  : 4 even sizes x 2 axes        mismatches = 0
   (the two OTHER consumers of _freq_sq_1d_bld -- the astigmatic per-axis
    Fresnel step and the near-focus ASM bridge; both were silently carrying the
    same odd-N defect and both are fixed for free)
```

### Odd-`N` vs `np.fft.fftfreq`

The BIN MAPPING is now exact for every `N` (compared in integer space,
`f * N * d`).  The VALUES agree to 1-2 ulp, not bitwise: `fftfreq` multiplies
by `1/(N*d)` while the builders divide by `(N*d)`, which differ in the last
place whenever `N*d` is not a power of two.  Switching to the reciprocal
multiply would make them bit-equal AND would perturb the validated even-`N`
path, so it is deliberately not done; the test asserts exact bin mapping plus a
4-ulp value bound and says why.

### Not fixed (out of scope, reported)

`_freq_sq_1d` (`carrier.py`, the plain-NumPy twin) carries the identical
`- N / 2`.  It is **unreferenced** -- `grep -rn "_freq_sq_1d\b"` over the repo
returns only its own definition -- and it sits outside this brief's writable
region.  Flagged for whoever next opens that part of the file: it is a live
trap if anyone resurrects it.

## D11 (MID-TASK ADDITION) -- split-leg composition under the exact gap kernel

Handed over as 6 failures in `tests/unit/test_niche_d4_dgrating.py`:
propagating a leg in one step versus two agreed to ~1e-11 under the old
paraxial default and disagrees by up to 9.4e-03 under the exact one.

**Verdict: PHYSICS, and provably NOT fixable inside the Sziklas-Siegman frame.
The tests encoded a paraxial-only identity.  Two real defects were found next
to it and both ARE fixed (D11a, D11b).**

The handed-over diagnosis ("the carrier reference/expansion at the split plane
must be treated so the composed product equals the single-leg exact kernel")
was checked and is refuted: no such treatment exists.

### Reproduce

`propagate_carrier_referenced`, one leg of 58.5393 mm versus 51.5393 + 7.0 mm,
N=256, dx=20 um, w=1.5 mm Gaussian, max-abs relative:

```
    703.5912   1.0001    False |     2.180e-11     7.545e-11          4.185e-06   0.000
```

`crosses` = the carrier's focus falls inside the leg (both routes then go

away: the residual is ZERO (1e-11, the FFT round-trip floor) exactly where
`m1 = 1`, and grows with `|m1 - 1|`.

### Root cause -- derivation

Split `z` into `z1 + z2` about a carrier `R`.  Leg 2 runs on the MAGNIFIED
co-moving grid (pitch `m1*dx`, `m1 = (R+z1)/R`), so the SAME FFT bin is a
factor `m1` lower physical frequency there.  The composed phase at bin `q` is
therefore

    phi(z_eff1, q) + phi(z_eff2, q/m1)      vs      phi(z_eff, q)

and the reduced distances telescope EXACTLY:

```
  R=-0.200: m1= 0.742304  z_eff1 + z_eff2/m1^2 = 8.276404683421e-02  z_eff = 8.276404683421e-02  rel 0
  R=-0.045: m1=-0.145318  z_eff1 + z_eff2/m1^2 =-1.945646008287e-01  z_eff =-1.945646008287e-01  rel 3.3e-16
  R=-0.003: m1=-16.17977  z_eff1 + z_eff2/m1^2 =-3.162047415074e-03  z_eff =-3.162047415074e-03  rel 1.1e-16
```

So a kernel whose only `q` dependence is `q^2` composes exactly -- and that is
the ONLY kind that can.  Composition for every split requires

    phi(t1, q) + phi(t2, q/m) = phi(t1 + t2/m^2, q)     for all m,

and substituting `s = t*q^2` turns it into `phi~(s1) + phi~(s2) = phi~(s1+s2)`
-- Cauchy's functional equation -- so `phi~` is LINEAR in `z_eff*q^2`.

**Composition across a Sziklas-Siegman split and non-paraxiality are mutually
exclusive.**  The exact kernel
`z*sqrt(k^2-q^2) = k z - z q^2/2k - z q^4/8k^3 - ...` carries `z*q^4`, which is
not a function of `z*q^2`, so it composes only at `m = 1`.  Requiring the old
`< 1e-9` identity IS requiring the paraxial kernel.

This is not a surprise once stated: the scaled-coordinate frame is derived from
the DILATION SYMMETRY of the paraxial wave equation, which `sqrt(k^2 + grad^2)`
breaks.  "Exact kernel on an approximate frame" (the spec's own words) cannot
inherit the frame's composition law.

### Root cause -- numerical proof that it is the kernel and nothing else

The entire split-vs-single field difference is reproduced from the closed-form
composed-minus-single TOTAL phase (transfer function + SS piston), so no
piston, amplitude or pitch bookkeeping is involved:

```
  R=-0.2  m1=0.7423   exact: measured 1.6782e-06  predicted 1.6782e-06  |pred-meas|/meas 1.8e-05
  R=-0.5  m1=0.8969   exact: measured 1.6834e-07  predicted 1.6835e-07  |pred-meas|/meas 5.7e-05

  R=+0.3  m1=1.1718   exact: measured 8.0919e-08  predicted 8.0907e-08  |pred-meas|/meas 3.5e-04
```

Shipped as
`test_the_exact_split_residual_is_exactly_the_predicted_kernel_mismatch`: if

### D11a -- REAL DEFECT, FIXED: a COLLIMATED leg ignored `gap_kernel` entirely

Found while sizing the bound.  `propagate_carrier_referenced`'s `R = +/-inf`
branch called `fresnel_tf_propagate` unconditionally, so a collimated leg ran
the PARAXIAL kernel and silently dropped `tilt`, whatever `gap_kernel` said:

```
BEFORE:  R = inf   exact-vs-fresnel = 0.000e+00     (the knob does nothing)
         R = -0.2  exact-vs-fresnel = 1.275e-05     (same leg, finite carrier)
AFTER:   R = inf   exact-vs-fresnel = 4.186e-06
```

This is the worst possible place to be silently paraxial: `m = 1` means no
frame rescaling, which is the ONE regime where the exact kernel is genuinely
exact (1e-12 against the ASM oracle) and where it composes across splits
perfectly (the fixed collimated split residual is 2.3e-11, unchanged).  A chain
entered with `r_in=inf` -- the documented default -- had its first gap run
paraxially.

**Fix:** the kernel choice was factored into one function, `_envelope_tf_step`,
used by BOTH the co-moving step and the collimated branch, so they cannot drift
apart again.  `tilt` now reaches the collimated branch too.

### D11b -- REAL DEFECT, FIXED: an ASTIGMATIC carrier silently downgraded

`propagate_carrier_referenced` forwards nothing to
`_propagate_carrier_astigmatic`, so `gap_kernel='exact'` on a 2-tuple carrier
was accepted and ignored.  That one CANNOT be honoured -- the astigmatic
transform is a separable per-axis Sziklas-Siegman step and
`sqrt(k^2 - qx^2 - qy^2)` does not factor into an x part and a y part (only its
paraxial expansion does).  So the D4 remedy applies: **refuse, do not
downgrade**.  An explicit `gap_kernel='exact'` now raises a `ValueError` that
says why; `'auto'` still resolves to the paraxial per-axis kernel there, which
is now documented rather than silent.

### What changed in the tests, and why it is not a re-baseline

`tests/unit/test_niche_d4_dgrating.py`, two tests:

1. `TestSplitLegPathDependence::test_split_is_inert_when_the_split_plane_is_clear_of_the_focus`
   -- the `< 1e-9` identity is now asserted with `gap_kernel='fresnel'`, where
   it is a THEOREM, at the ORIGINAL bar and on all seven carriers.  The
   shipping default gets a COMPARATIVE bound instead: the split-vs-single
   residual must stay below the exact-vs-paraxial correction on the same leg
   (measured ratios 0.000 / 0.000 / 0.132 / 0.554 / 0.229 / 0.042 / 0.004).
   A ratio cannot erode into a bigger constant, and it fails the moment the
   ambiguity costs more than the kernel buys.
2. `TestDoeChainBookkeeping::test_matches_the_manual_hand_split` -- the hand
   split transports the leg in two pieces where the DOE entry transports it in
   one, so under a non-composing kernel this test stopped measuring the
   bookkeeping claim it exists for (the two-piece term grew 1.14e-10 ->
   1.95e-04 and swamped it).  The equivalence is now measured under the
   COMPOSING kernel, keeping the original tight bars (1e-6 / 1e-4) and the
   original documented numbers, and a second assertion prices the default-kernel
   pair against the correction the exact kernel applies to the same chain.
   The `runs` fixture gained `*_fr` (fresnel) variants of the four hand-split
   chains.

No bar was loosened, nothing was xfailed or skipped, and the DOE design's own
guarantee is untouched: the chain DEFERS a DOE's transport rather than
splitting there, so `test_an_order_zero_doe_is_immune_to_that_corner` and the
bitwise-inertness tests still pass unchanged -- which is precisely the design
decision this whole property was documented to justify.

`tests/unit/test_niche_exact_gap_kernel.py` gained the section "COMPOSITION
ACROSS A SPLIT LEG" (30 tests): the telescoping identity, the paraxial
composition theorem on all seven carriers, the predicted-mismatch bug detector,
the comparative bound, the oracle premise guard, the scaled-step adjudication
(D10), and the two bypass tests for D11a / D11b.
