## P0-NEW-1 -- ``make_off_axis_parabola`` doubly broken

Audit `docs/audits/AUDIT_V4_15_0_2026_05_18.md` Part 2 V4 + Part 3 F1
found two independent bugs in the v4.15.0 OAP factory, neither of
which was caught by the v4.15 test class (which pinned dict-field
shapes only and never traced a chief ray through the geometry):

### Bug 1 -- DECENTER formula off by 2x

`lumenairy/io/prescriptions.py:316` (v4.15.0) computed
`h_decenter = focal_length * math.tan(off_axis_angle)`.  The
chief-ray geometry on the parent paraboloid `z = r^2/(4f)` requires
`r = 2 * f * tan(alpha)`, where `alpha` is the surface-normal off-
axis angle.  Worst case at the 90-deg-fold geometry (`alpha = pi/4`):
the pre-fix value `f * tan(pi/4) = f` is exactly half the correct
chief-ray launch radius `2 * f`.  At smaller alpha the error is
still ~2-fold but masked because the absolute decenter is small;
the dict-field test happened to pin the WRONG value at
`alpha = 15 deg`.

**Fix:**

```python
# v4.15.0 (off by 2x):
h_decenter = focal_length * math.tan(off_axis_angle)

# v4.15.1 (correct chief-ray geometry):
h_decenter = 2.0 * focal_length * math.tan(off_axis_angle)
```

### Bug 2 -- 3-tuple TILT misinterpreted by `apply_real_lens`

The factory writes `'tilt': (off_axis_angle, 0.0, 0.0)` -- the full
surface-normal angle about the local x-axis.  `apply_real_lens` at
`_lens_real.py:619-621` reads

```python
tilt = surf.get('tilt') or (0.0, 0.0)
if tilt[0] != 0.0 or tilt[1] != 0.0:
    sag = sag + tilt[0] * Xs + tilt[1] * Ys
```

i.e. the function treats `tilt` as a 2-tuple of *small-angle*
linear surface-sag ramps.  Indexing a 3-tuple still yields the
correct `tilt[0]` and `tilt[1]` for the read, but the linear-ramp
interpretation is a paraxial approximation that diverges badly at
OAP fold angles:

| `alpha` | true sag tilt | linear ramp `alpha*x` | Error |
| --- | --- | --- | --- |
|  15 deg | `tan(15) * x = 0.268 * x` | `15 / 57.3 * x = 0.262 * x` | ~2 % |
|  45 deg | `tan(45) * x = 1.000 * x` | `45 / 57.3 * x = 0.785 * x` | ~27 % |
|  90 deg | `tan(90) = inf` | `90 / 57.3 = 1.57` | divergent |

**User decision** (recorded in this agent's task brief): the OAP
factory targets the **traced raytrace path**
(`apply_real_lens_traced`, `apply_real_lens_traced_jax`), which
applies a proper coordinate-frame rotation that consumes the
3-tuple correctly.  The factory continues to write the 3-tuple, but
the docstring is rewritten to make the intended-consumer requirement
loud and explicit and to add a *Warnings* section explaining the
paraxial-`apply_real_lens` failure mode.  No runtime warning is
added in this scope because the natural place to surface that
warning is in `apply_real_lens` itself (out of this agent's file
list, and the existing `apply_real_lens` already warns on
`freeform_type` -- which catches most accidents).

### Convention reconciliation in the docstring

The v4.15.0 docstring said `off_axis_angle` was the chief-ray fold
angle ("from the parent optical axis to the chief ray reflected by
the OAP"), but the surrounding code already used it as the surface-
normal angle (`tilt = (off_axis_angle, ...)` matches the surface-
normal convention, not the chief-ray-fold convention; the audit's
test for the bug fix at `alpha = pi/4` -> `decenter = 2*f` likewise
matches surface-normal `alpha`, not chief-ray fold `2*alpha`).
v4.15.1 reconciles the docstring with the geometric convention used
internally: `off_axis_angle` IS the surface-normal angle, and a
"90-deg-fold OAP" is `off_axis_angle = pi/4`.  The *Notes* section
now derives the formula from `z = r^2/(4f)`, and the *Examples*
section confirms `decenter = 2 * f` at `alpha = pi/4`.

### P3-F1-3 closure -- `vertex_radius` validation

The pre-v4.15.1 factory accepted `vertex_radius=0` and
`vertex_radius=-1` silently (producing a flat or oppositely-curved
surface).  v4.15.1 raises `ValueError` for any non-positive or
non-finite override; the implicit `None` default still resolves to
`R = 2 * focal_length`.

## P1-NEW-E -- Zemax `.zmx` loader has no QBFS / QCON parsing

Audit Part 3 F2 found that `io/prescriptions.py` had zero matches for
`QBFS`, `QCON`, `q_bfs_coeffs`, or `freeform_type.*q_` -- a `.zmx`
file with Forbes Q-type freeforms loaded with `freeform_type=None`
(silently degrading to base conic), even though the v4.15.0 release
shipped working math (`surface_sag_q_bfs`, `surface_sag_q_con`) and
a working dispatcher (`surface_sag_freeform` recognises `'q_bfs'` /
`'q_con'`).  Forbes Q was advertised as a shipped feature but the
canonical consumer path (`load_zemax_zmx` -> dispatcher) silently
dropped the coefficients.

### Resolution

Add a Q-type SURFTYPE branch to the per-surface element construction
in `load_zemax_zmx` (`lumenairy/io/prescriptions.py:809-1003`):

1. **PARM 0 stored unconditionally.**  The pre-v4.15.1 loader filtered
   out PARM 0 via `if parm_val != 0.0` and a downstream
   `parm_num >= 1` filter.  PARM 0 is meaningful on Q-type surfaces
   (Zemax "Norm Radius" field), so the loader now stores PARM 0
   regardless of value.  EVENASPH parsing is unaffected -- it
   continues to skip PARM 0 via the `parm_num >= 1` filter inside
   the EVENASPH branch.

2. **SURFTYPE-driven branching.**  The per-surface element loop reads
   `s.get('type')` and dispatches to:

   - `QBFS` -> `freeform_type='q_bfs'`, `q_bfs_coeffs` from PARM 1..N
     with `m = parm_num - 1` (Forbes order), `r_max` from PARM 0
     (lens units -> meters via `unit_scale`).
   - `QCON` -> `freeform_type='q_con'`, `q_con_coeffs` ditto.  The
     existing `CONI` parsing already preserves the conic constant
     that Q-con surfaces require.
   - `EVENASPH` / anything else -> legacy path, populating
     `aspheric_coeffs` via the existing `power = 2 + 2*parm_num`
     rule.

3. **`r_max` source.**  Zemax stores the Q-type Norm Radius as PARM 0
   on the surface.  When PARM 0 is missing or zero (some Zemax
   exporters emit a Q-type surface that uses its DIAM as the
   normalisation radius), we fall back to the surface's
   `semi_diameter` (already in meters at the point of fallback) and
   then to a conservative 1.0 m placeholder.

4. **Flat-key forwarding.**  The lens-only `prescription_surfaces`
   list (consumed by `apply_real_lens` /
   `surfaces_from_prescription` etc.) carries `freeform_type`,
   `q_bfs_coeffs` / `q_con_coeffs`, and `r_max` so the downstream
   dispatcher actually sees the coefficients.

### Judgment calls

- **PARM 0 vs DIAM for r_max.**  Zemax's documented Q-type
  convention puts the Norm Radius in PARM 0 of the surface, in lens
  units (consistent with how the rest of the Q-type PARM table
  carries coefficients in lens units of sag).  Some exporter
  variants leave PARM 0 absent and use DIAM (the semi-aperture) as
  the implicit normalisation radius.  We treat PARM 0 as the
  primary source and fall back to DIAM (`semi_diameter * unit_scale`,
  already in meters) when PARM 0 is absent or zero.  The fall-back
  matches the dispatcher's expectation: a Q-type surface evaluated
  on a grid larger than `r_max` zeros out the freeform departure
  outside the rectangular `[-norm_x, norm_x] x [-norm_y, norm_y]`
  domain, so a DIAM-sourced `r_max` produces the physically correct
  truncation at the clear aperture.

- **Coefficient list ordering.**  The dispatcher
  `surface_sag_freeform` reads `q_bfs_coeffs` as a flat sequence
  where `coefficients[m]` is the Forbes `a_m`.  Zemax PARM
  numbering is 1-indexed, so the loader uses `m = parm_num - 1`
  to produce a 0-indexed Python list.  Missing PARMs in the
  range `[1, max(parm_num)]` are filled with `0.0`.

- **`stype` upper-casing.**  Zemax PARSER variants emit SURFTYPE
  in different cases (`QBFS` vs `qbfs` vs `QBfs`); the loader
  normalises to upper for the dispatch comparison.
