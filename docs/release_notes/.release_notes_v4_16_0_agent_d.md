# v4.16.0 -- Agent D release notes

Agent D scope (per dispatch): ROADMAP items #13, #14, #15 -- the
v4.18 glass/materials expansion + the central cache-clearer registry.

## Headline

* **CDGM / Hikari / Sumita glass catalogues bundled** (ROADMAP #13).
  GLASS_REGISTRY grows from 46 to 78 entries (12 CDGM + 10 Hikari +
  10 Sumita additions).  Each new entry resolves via the
  refractiveindex.info live database when the optional
  ``refractiveindex`` package is installed.  Eight CDGM glasses
  also have bundled Sellmeier-2 coefficients in
  ``SELLMEIER_COEFFICIENTS`` for offline fallback.
* **Sellmeier validity ranges per glass** (ROADMAP #14).  Every
  bundled glass now carries an explicit
  ``GLASS_VALIDITY[name] = (lambda_min, lambda_max)`` entry (77
  entries).  Querying ``get_glass_index(name, wavelength)`` outside
  the documented range emits a one-shot ``UserWarning`` per
  ``(glass, wavelength)`` pair -- the value is still returned
  (extrapolation accepted) but the user is notified.
* **Central cache-clearer registry** (ROADMAP #15).  Retires the
  lazy-import fan-out in ``clear_asm_caches`` in favour of
  ``lumenairy.register_cache_clearer(name, clear_fn)``.  9 known
  caches register at module-import time;  ``clear_asm_caches`` now
  simply walks the registry.  Counter-measure to the recurring
  "fix N, miss N+1" sibling-gap meta-pattern.

## Validity ranges (ROADMAP #14)

* ``GLASS_VALIDITY`` is a top-level dict mapping
  ``glass_name -> (lambda_min_m, lambda_max_m)``.
* Default for glasses without explicit entries: ``(0.0, np.inf)``
  -- no warning ever fires.  Documented exemption.
* Out-of-range warning behaviour:
  - Emits ``UserWarning`` (one-shot per ``(glass, wavelength_nm)``).
  - Does NOT raise -- extrapolation is accepted for design-space
    exploration; the warning is advisory.
  - User-supplied callable glasses skip the check (they define
    their own valid band).

* Schott N-series: SCHOTT TIE-29 "Refractive index and dispersion"

## Central cache registry (ROADMAP #15)

### New module: ``lumenairy._cache_registry``

Provides three public-API entry points:

* ``register_cache_clearer(name, clear_fn)`` -- module-import-time
  registration.  Idempotent on duplicate names.
* ``list_registered_cache_clearers()`` -- introspection helper;
  returns sorted list of cache names.
* ``clear_all_registered_caches()`` -- internal walker used by
  ``clear_asm_caches``.

### Registration pattern

Each cache-owning module registers via a *late-binding* closure
that re-resolves the clear-function from the module's current
namespace at call time.  This preserves the pre-v4.16
``mock.patch.object`` semantic: tests that monkey-patch
``module.clear_<X>_cache`` still observe their counter increment
when ``clear_asm_caches`` walks the registry.  Cost: one attribute
lookup per cache per drain -- negligible vs. the actual cache-clear
work.

### Refactored ``clear_asm_caches``

Pre-v4.16: lazy-import + try/except fan-out (8 sibling clearers
enumerated by hand).
v4.16.0: single call to ``clear_all_registered_caches()``.

External contract preserved bit-for-bit:

* Same caches drained (verified by ``test_v4_14_1_dispatcher_pin_
  cache_clears.py`` pin -- still passes).
* Same narrowed-except classes swallowed
  (``ImportError``, ``RuntimeError``, ``AttributeError``).
* Same idempotent behaviour (no error on repeated calls).
* No change to ``__all__`` -- every ``clear_<X>_cache`` name still
  importable at top level.

### Counter-measure ratio

Pre-v4.16: each new cache required 5-10 lines of lazy-import +
try/except + comment in ``clear_asm_caches``, with the "fix N,
miss N+1" sibling-gap meta-pattern recurring 5 ways inside v4.14.2
alone.

Post-v4.16: each new cache requires ~6 lines at the bottom of its
owning module (one ``register_cache_clearer`` call).  No edit to
``clear_asm_caches`` required.  Counter-measure: 1 registry
prevents N future sibling-gap recurrences.
