# v4.15.2 -- PartialCoherenceMCF + 3-D ensemble defensive guards (Agent C)

Patch release closing **2 P1s** from
`docs/audits/AUDIT_V4_15_1_2026_05_18.md`:

* **P1-NEW-E**: existing propagators silently accept
  `PartialCoherenceMCF` instances introduced in v4.15.1 and crash
  downstream with a cryptic `AttributeError: 'PartialCoherenceMCF'
  object has no attribute 'copy'`.
* **P1-NEW-F**: existing propagators silently accept the 3-D ensemble
  `(n_realizations, Ny, Nx)` returned by `create_*_schell_source()` and
  run the FFT over the unintended axis, producing wrong-but-plausible
  output.

v4.15.2 (Agent C) adds defensive guards at the top of every propagator
entry point.  The guards are the FIRST executable statements in each
entry point (before any input validation or backend dispatch) so the
user gets a clear, actionable error before any downstream surprise.

## Guards added

Each entry point now begins with:

```python
from <appropriate>.sources.core import PartialCoherenceMCF as _PartialCoherenceMCF

if isinstance(E_in, _PartialCoherenceMCF):
    raise TypeError(
        "<fn_name>: PartialCoherenceMCF inputs are not yet supported "
        "by this propagator (v4.15+). MCF-aware downstream "
        "propagators are scheduled for v4.16+.  ...iterate-over-"
        "ensemble workaround..."
    )

_ndim = getattr(E_in, 'ndim', None)
if _ndim is not None and _ndim != 2:
    raise ValueError(
        "<fn_name>: expected 2-D complex field of shape (Ny, Nx); "
        "got <N>-D array of shape <shape>.  ...iterate-over-ensemble "
        "workaround..."
    )
```

The lazy `from ..sources.core import PartialCoherenceMCF` import
inside the function body avoids a circular dependency between
`sources/` and `propagators/` / `elements/` / `system.py`.

## Entry points covered

All public propagator entry points that previously accepted the new
types silently now raise:

| Module | Function | TypeError on MCF | ValueError on 3-D |
|---|---|---|---|
| `lumenairy.system` | `propagate_through_system` | yes | yes |
| `lumenairy.propagators.dispatch` | `propagate` | yes | yes |
| `lumenairy.propagators.propagation` | `angular_spectrum_propagate` | yes | yes |
| `lumenairy.propagators.propagation` | `fresnel_propagate` | yes | yes |
| `lumenairy.propagators.propagation` | `fraunhofer_propagate` | yes | yes |
| `lumenairy.propagators.propagation` | `rayleigh_sommerfeld_propagate` | yes | yes |
| `lumenairy.propagators.propagation` | `scalable_angular_spectrum_propagate` | yes | yes |
| `lumenairy.elements._lens_thin` | `apply_thin_lens` | yes | yes |
| `lumenairy.elements._lens_thin` | `apply_cylindrical_lens` | yes | yes |
| `lumenairy.elements._lens_real` | `apply_real_lens` | yes | yes |

`apply_thin_lens` / `apply_cylindrical_lens` / `apply_real_lens` are
re-exported from `lumenairy.elements.lenses` so existing imports
continue to work.  The guards live on the actual function definitions
in `_lens_thin.py` / `_lens_real.py`.

## Documented 3-D exemptions

Per the audit guidance (C.4), the existing propagator entry points
were grep'd for any legitimate non-2-D inputs (polychromatic stack,
per-source multi-field).  **No public propagator entry point in scope
currently documents accepting a 3-D shape** -- polychromatic handling
lives in `lumenairy.analysis.core.polychromatic_*` which iterates over
the wavelength axis and calls the 2-D propagators per slice.  The
strict `ndim != 2` guard is therefore applied uniformly to every entry
point.

Pre-existing inner guards (e.g. `scalable_angular_spectrum_propagate`
already had `if E_in.ndim != 2`) are kept; the new top-of-function
guard fires first with the canonical iterate-over-ensemble message.

## Error message contract

The raised messages carry two load-bearing pieces of information that
the test suite pins:

* **TypeError**: the literal substring `v4.16` so users know
  MCF-aware propagators are a scheduled-for-future feature, not a
  permanent limitation.
* **ValueError**: the literal substring
  `for k in range(ensemble.shape[0])` so users see the canonical
  iterate-over-ensemble workaround inline with the error.

## Constraints honoured

* cp1252-compatible (no non-ASCII characters in any added code or
  tests).
* No widening of narrowed `except` clauses; the existing
  `_validate_propagator_inputs` exception ladder is unchanged.
* No changes outside the scoped files (`system.py`,
  `propagators/dispatch.py`, `propagators/propagation.py`,
  `elements/_lens_thin.py`, `elements/_lens_real.py`,
  `tests/unit/test_v4_15_2_agent_c.py`, this release-notes file).
  `elements/lenses.py` was intentionally NOT touched because the
  three relevant functions are re-exported from `_lens_thin.py` /
  `_lens_real.py`; the guards on those private modules reach the
  public API automatically.
* Lazy `from ..sources.core import PartialCoherenceMCF` import
  inside each guard avoids a circular dependency between `sources/`
  and the consumer modules.  `python -c "import lumenairy"` confirms
  clean post every edit.
* Guards run as the FIRST executable statement in each entry point
  (before backend selection, before input-shape validation, before
  z-sign checks) so the user gets the clearest error fast.
* No silent coercion -- the guards raise, never normalise.

## Why both `isinstance` and `ndim` checks (not just one)

`PartialCoherenceMCF` is a `@dataclass`, not an ndarray; it has no
`ndim` attribute and no `shape` attribute compatible with the
2-D-ndarray contract.  Without the explicit `isinstance` check it
would slip past a generic `ndim != 2` guard via the
`getattr(E_in, 'ndim', None) is None` clause and hit a downstream
`AttributeError`.  Splitting the checks lets each path raise a
type-appropriate exception (`TypeError` for wrong type;
`ValueError` for right type / wrong shape) and emit a
type-appropriate workaround message.
