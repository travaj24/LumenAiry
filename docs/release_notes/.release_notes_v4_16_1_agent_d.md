## D.2 -- `refractiveindex` to optional deps (audit M-1)

Pre-fix `pyproject.toml:46-52` declared `refractiveindex>=1.0` as
a HARD dependency, but `glass.py:62-89` treats it as optional via
the standard `importlib.util.find_spec(...)` lazy-load + Sellmeier
fallback pattern.  The careful lazy-load handling was partially
defeated by the hard-dep declaration: `pip install lumenairy` always
pulled in the YAML-database package (~25 MB of catalog data) even
when the user only needed the bundled Sellmeier coefficients.

Fix:

1. Removed `refractiveindex>=1.0` from `[project.dependencies]`.
2. Added `glass = ["refractiveindex>=1.0"]` to
   `[project.optional-dependencies]`.
3. Added `refractiveindex>=1.0` to the existing `all` group so
   `pip install lumenairy[all]` still pulls it (parity with the
   v4.16.0 `pip install lumenairy[all]` contract).
4. Extended `glass.py`'s ImportError hint to mention both
   `pip install refractiveindex` and `pip install lumenairy[glass]`.

The `refractiveindex` lazy-import handling in `glass.py:_ensure_refractiveindex_loaded`
already raised a clear ImportError on first call when the package
was missing (test path: glass with tuple-style registry entry +
no Sellmeier fallback).  Confirmed unchanged by the v4.16.1 patch.

Regression coverage:
`test_pyproject_refractiveindex_not_in_hard_deps`,
`test_pyproject_refractiveindex_in_glass_extras`,
`test_pyproject_refractiveindex_in_all_extras`.

## D.3 -- `zarr>=3.0` floor in extras (audit M-3)

`storage.py:1118-1120` calls `planes_grp.create_array(name=..., data=...,
chunks=...)`.  This API is **Zarr v3-only** -- Zarr v2 named the
equivalent method `create_dataset` and signed it differently.  A user
pinning `zarr==2.14` (the previous `pyproject.toml` floor) hits
`AttributeError: 'Group' object has no attribute 'create_array'` on
the first append.

**Is this a real breaking version bump?**  Effectively no:
v4.16.0 already required Zarr v3 at runtime via the `create_array`
call and the `_open_zarr_group_safe` helper (which works around
zarr v3-specific Windows mkdir behaviour).  The previous
`zarr>=2.14` floor in pyproject.toml was metadata drift -- the
declared lower bound did not match the actual API in use.  v4.16.1
brings the two into agreement.

Users on `zarr 2.x` were already broken; they were just getting an
`AttributeError` at first-call instead of a clear pip-resolution
error.  The bump is documentation of reality, not a new
restriction.

Regression coverage: `test_pyproject_zarr_floor_v3`.

## D.4 -- `ProcessPoolExecutor` spawn context (audit M-2)

`_lens_traced.py:_get_persistent_worker_pool` constructed
`ProcessPoolExecutor(max_workers=int(n_workers))` without an
explicit `mp_context` kwarg.  On Linux this defaults to `fork`,
which:

1. Inherits the parent's pyFFTW plan cache (module-private locks
   the forked child cannot release).
2. Inherits the parent's NumPy/MKL thread pool (the fork doubles
   the thread count, oversubscribing the CPU).
3. Inherits any matplotlib backend state, leading to deadlocks
   on certain GUI backends.

v4.16.0's CHANGELOG and README both claimed the library used
spawn; this was only true of the v4.16.0 multi-process-storage
tests (which constructed their own spawn contexts), not the
library worker pool itself.

Fix: `mp_context=_mp.get_context('spawn')`.

Note: `spawn` is the default on macOS (Python 3.8+) and Windows;
the explicit kwarg is portable and produces the same behaviour
across all three platforms.

Regression coverage: `test_lens_traced_pool_uses_spawn_context`
(AST-level inspection of the `ProcessPoolExecutor(...)` call's
kwargs).

5. `result = la.trace(fan, surfaces, wavelength=587.56e-9)`.

   radius.

## D.8 -- `CONVENTIONS.md` (audit item 23)

Top-level `CONVENTIONS.md` codifying the de-facto patterns used
across the library.  Audit ORG-1 P0-3 specifically called out
the `create_*` vs `make_*` factory-verb ambiguity; this document
formalises the underlying rule (`create_*` returns a field /
Source; `make_*` returns a non-field aggregate).

Sections:

1. Factory-verb naming (`create_*` vs `make_*`) -- with full
   alphabetical enumeration of the 23 `create_*` and 13 `make_*`
   helpers in the public namespace.
2. Error message prefix (`f"{fn_name}: ..."`) discipline.
3. RNG kwarg name (`rng` canonical; `seed` / `random_state` /
   `random_seed` legacy).
4. Wavelength kwarg name (`wavelength`; no aliases).
5. Spatial sampling kwargs (`dx`, `dy=None` -> `dx`).
6. Units (meters / radians / dimensionless complex `n + 1j*kappa`).
7. Sign conventions (`exp(-i omega t)` time, `exp(+i k z)`
   forward, OPD-positive == phase-advance).
8. Top-level re-exports (Tier-1 -- Tier-5; `__all__`-symmetry
   walker enforcement).
9. Sentinel pattern (the v4.14.1 `__slots__ = ()` + `is`-only
   contract).
10. Optional dependency lazy import (the
    `_FOO_AVAILABLE = find_spec(...) is not None` pattern with
    deferred + cached actual import, ImportError citing both the
    bare package and the `lumenairy[group]` extras).

The factory-verb rule is checked by
`tests/unit/test_v4_16_1_agent_d.py::test_factory_verb_naming_contract`,
which walks `dir(lumenairy)` and verifies that no `make_*`
symbol takes a grid-size `N` parameter (a heuristic proxy for
"this returns a field").  Two exempt callables documented:
`make_lg_aberration_merit_jax` (returns a closure) and
`make_jax_ray_state` (takes `N` as the z-direction cosine of
each ray, per the RayBundle convention).

Regression coverage:
`test_conventions_md_exists`,
`test_conventions_md_documents_create_and_make_factories`,
`test_factory_verb_naming_contract`.
