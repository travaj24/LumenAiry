# Release notes -- v5.1.0 Agent A

**Scope.**  Library-wide default-config knob resolver rollout.  Closes
the long-deferred work item from AUDIT_V5_0_1_2026_05_20.md Part 7
v5.1 horizon item 1.  The three v4.16.2 setter knobs were API-only
at v4.16.2 - v5.0.x with a one-shot ``UserWarning`` advertising the
gap; v5.1.0 retires that warning and wires the resolver at every
applicable entry point.

## Summary

* ``set_default_wave_propagator(name)`` now steers
  ``apply_real_lens``, ``apply_real_lens_traced``, and the
  ``method=`` argument of ``propagate_through_system``.
* ``set_default_dy(value)`` now steers ``apply_real_lens`` and
  ``apply_real_lens_traced`` (the ``dy=None -> get_default_dy() ->
  dx`` chain).
* ``set_default_real_dtype(dtype)``'s consumer set extended to one
  additional user-facing site: the ``_geometric_lens_phase`` OPL
  accumulator inside ``apply_real_lens_traced``.  Other user-facing
  entry points correctly DERIVE their real dtype from the complex
  input's real counterpart and need no additional wiring; see the
  per-site rationale below.
* v4.16.3 one-shot no-consumer ``UserWarning`` emissions from
  ``set_default_wave_propagator`` and ``set_default_dy`` are
  retired.  The corresponding tests in
  ``tests/unit/test_v4_16_3_agent_b.py`` were rewritten from
  "must emit one-shot UserWarning" to the inverse pin "must NOT
  emit the no-consumer UserWarning".
* The v4.16.3 sibling-gap pin
  (``test_wave_propagator_and_dy_have_zero_consumers_lib_wide``,
  designed to fail loudly when the first consumer wired) was
  retired and replaced with the v5.1.0 inverse pin
  (``test_wave_propagator_and_dy_now_have_consumers``) that
  grep-verifies the resolver calls at the expected sites.
* Migration-Guide.md §4.16.2 + §5.0.0 retired the "API-only"
  framing and now documents the v5.1.0 one-shot recipe.

## Sibling-gap sweep -- sites I deliberately did NOT wire

The audit scope (Critical conventions item 4) asked: "find these via
grep for ``np.float64`` allocation patterns. Focus on USER-FACING
entry points; internal-only helpers can keep hardcoded dtype."  The
``np.float64`` grep returns 27 files.  My audit of the user-facing
ones found:

* **Sources** (``lumenairy/sources/core.py``, ``polarization.py``):
  user-facing source-field constructors allocate
  ``np.float64`` Gaussian / Hermite-Gauss / etc. envelope arrays.
  These DERIVE precision from the user's ``dx`` / sigma / etc.
  arguments and are converted to complex via
  ``DEFAULT_COMPLEX_DTYPE`` at the final assembly step.  Per the
  rationale below they correctly inherit precision via the
  existing complex-dtype knob.
* **Analysis** (``lumenairy/analysis/core.py``,
  ``lumenairy/analysis/detector.py``, ``aberration.py``,
  ``ao.py``, ``interferometry.py``,
  ``image_plane_wfe.py``, ``phase_retrieval.py``): user-facing
  analysis routines accept a complex field input and produce
  intensity / OPD / Strehl / etc. real outputs that DERIVE from
  the input dtype (``abs(E)**2`` of a ``complex64`` is naturally
  ``float32``).  Wiring these to the default would FIGHT the
  user-precision-propagation contract.
* **Lenses thin / Maslov / JAX** (``_lens_thin.py``,
  ``lenses_maslov.py``, ``_lens_jax.py``): the thin-lens family
  produces an output field whose dtype tracks the complex input
  (the user's ``E_in``).  No fresh-real allocation is the load-
  bearing one; the few ``np.float64`` allocations are in
  parameter-grid setup (``X``, ``Y`` from ``np.arange(N)*dx``),
  which is type-flexible scratch.
* **Optimize / multi-objective**
  (``lumenairy/optimize/core.py``, ``multi_objective.py``):
  internal scratch for differential-evolution / pymoo
  population arrays.  Internal-only.
* **Raytrace** (``raytrace/core.py``, ``raytrace/from_field.py``,
  ``raytrace/jax_trace.py``): ray geometry uses ``float64`` for
  numerical conditioning of the per-surface inversion; users
  rarely run ray-trace at ``float32``.  Internal-only.
* **Coatings / BSDF / Bluestein /
  vector-diffraction**: internal helpers.
* **UI / examples**: not library code paths.

**Rationale.**  The library follows the convention "match the
input's precision" wherever a complex input array is present; the
default-real-dtype knob fills the gap only at sites that allocate
a fresh real array with NO complex parent.  The single such site
in the legacy library was ``propagate_ensemble`` (v4.16.3 wiring);
v5.1.0 adds ``_geometric_lens_phase``.  Other fresh-real allocations
are either (a) internal scratch with no user-visible memory
footprint, or (b) parameter-grid setup that the JIT optimizer
collapses, neither of which the user is likely to want to flip.

The v5.1.0 ``set_default_real_dtype`` extension is intentionally
narrow.  A future v5.2 sweep could extend it further (e.g. the
``_geometric_lens_phase`` siblings in ``lenses_maslov.py``) but
each new wiring needs an end-to-end behavioural pin like the one
v5.1.0 added; broadening the consumer set without per-site test
coverage would silently break the user-precision-propagation
contract for callers who set ``np.float32`` expecting only
``ensemble.py`` to honour it.

## Backwards compatibility

* All existing callers that pass ``wave_propagator='asm'`` (or any
  explicit name) keep bit-for-bit pre-v5.1 behaviour.  The
  resolver fires ONLY when the kwarg is ``None`` (the new default).
* All existing callers that pass ``dy=<value>`` keep bit-for-bit
  pre-v5.1 behaviour.
* All existing callers that pass ``method='asm'`` (or any explicit
  name) to ``propagate_through_system`` keep bit-for-bit pre-v5.1
  behaviour.
* The setters' return-and-store contract is unchanged.
* The setters' validation contract is unchanged (invalid names /
  values still raise ``ValueError``).
* The module-level ``_DEFAULT_WAVE_PROPAGATOR_NO_CONSUMER_WARNED``
  / ``_DEFAULT_DY_NO_CONSUMER_WARNED`` globals are preserved for
  back-compat with code that introspects them; they are pinned
  to ``True`` permanently so no warning can be revived by
  flipping them.
* The ``set_default_real_dtype`` no-consumer-warning asymmetry
  pin (``TestSetDefaultRealDtypeDoesNotEmitNoConsumerWarning``)
  is preserved unchanged -- ``real_dtype`` never emitted the
  no-consumer warning (it was already considered "consumed" at
  v4.16.3 ship).
