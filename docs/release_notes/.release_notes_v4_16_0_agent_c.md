## C.1 -- Constrained optimisation (ROADMAP #9)

### Constraint dataclass

```python
@dataclass
class Constraint:
    fun: Callable               # f(x) -> scalar | ndarray
    lb: Optional[float] = None  # None -> -inf
    ub: Optional[float] = None  # None -> +inf
    label: str = ''             # appears in progress messages
    jac: Optional[Callable] = None
```

Validation in ``__post_init__``:
* ``fun`` must be callable; raises ``TypeError`` otherwise.
* At least one of ``lb`` / ``ub`` must be supplied; both ``None``
  raises ``ValueError`` (unbounded constraint is a no-op).

``Constraint.to_scipy()`` returns a
``scipy.optimize.NonlinearConstraint(fun=..., lb=..., ub=...)``
ready for inclusion in ``minimize(constraints=[...])``.

### Method compatibility

``design_optimize`` validates the constraint-method combination
up-front (right after ``need_wave`` / ``n_params`` setup):

```python
_METHODS_SUPPORTING_CONSTRAINTS = ('SLSQP', 'trust-constr')

if constraint_seq and method not in _METHODS_SUPPORTING_CONSTRAINTS:
    raise ValueError(
        f"design_optimize: method={method!r} does not support "
        f"hard constraints via scipy.optimize.NonlinearConstraint. "
        f"Use one of {list(_METHODS_SUPPORTING_CONSTRAINTS)} "
        f"...")
```

Edge case discovered during method-compatibility checking:
``method='lm'`` (Levenberg-Marquardt) silently ignores
``constraints=`` because it dispatches to ``scipy.optimize.
least_squares``, which has its own ``bounds=`` API but no
``constraints=`` parameter.  v4.16 explicitly rejects ``method='lm'
+ constraints=`` with the same clear ValueError as L-BFGS-B etc.

Similar edge case: ``differential_evolution``, ``basin_hopping``,
``dual_annealing`` all silently ignore ``constraints=`` in scipy's
core ``minimize`` API.  v4.16 rejects them up-front.

### Constraint label in progress callback

Inside ``merit_fn`` (after the eval): if ``constraint_seq`` is non-
empty, the first constraint's current value + label are appended
to the progress message:

```
eval 42: merit=1.23e-4  efl=100.001mm  [BFL >= 5 mm=5.001234]
```

When the constraint callable raises, the message degrades to
``[constraint=err]`` so the user can see the FD-Jacobian step is
exploring infeasible territory.

### Tests (4)

* ``test_constraint_enforced_hard`` -- sum(x) >= 15 constraint on a
  quadratic with unconstrained sum(x*) = 10; verifies the
  optimised solution lies on the constraint boundary within 1e-3.
* ``test_unsupported_method_raises`` -- ``method='L-BFGS-B'`` with
  constraints raises ValueError matching ``r'(SLSQP|trust-constr)'``.
* ``test_constraint_callable_signature_validated`` --
  ``Constraint(fun=42.0)`` raises TypeError; ``Constraint(fun=...,
  lb=None, ub=None)`` raises ValueError.
* ``test_constraint_label_in_progress_output`` -- captures progress
  messages from an SLSQP run with a labelled constraint; asserts
  at least one message contains the label.

## C.2 -- Checkpoint / resume on long ``design_optimize`` runs (ROADMAP #10)

### State-file format

JSON, atomic-replace on write (write to ``state_file + '.tmp'``
then ``os.replace``):

```json
{
  "version": "4.16.0",
  "call_count": 42,
  "x_best": [0.123, 0.456, ...],
  "merit_best": 1.234e-4,
  "history": [
    {"call": 1, "merit": 5.0, "efl": null},
    ...
  ]
}
```

History buffer is capped at 1000 entries to keep the on-disk
payload bounded on multi-hour runs.  Pre-cap was unbounded and
could grow to MB-scale JSON on 10000-eval runs.

### Resume contract

On startup, if ``state_file`` exists and parses as a valid
state dict:

* ``x0`` is overridden with the persisted ``x_best``.
* ``merit_best`` is restored from the persisted value (the in-
  memory tracker starts from the resumed value, so the next
  merit-fn eval only overrides it if it's strictly lower).
* ``call_count`` is restored.  Note: ``max_iter`` still applies
  to the new run (we don't subtract resumed calls from the
  budget).
* If the persisted ``x_best`` has the wrong shape (param vector
  length changed since last run), the resume silently starts
  fresh.

### state_save_every throttle

The state-file write happens on every Nth call to ``merit_fn``
(default N=1, write every eval).  A force-save at the end of the
optimisation ensures the converged result is on disk regardless of
where the rolling counter left off.

### Tests (3)

* ``test_state_file_created_and_populated`` -- run for 10 iter,
  asserts file exists + has expected keys.
* ``test_resume_from_state_file`` -- pre-populates the file with a
  known ``x_best`` at the unconstrained optimum, runs with
  ``max_iter=1``, asserts final merit << what
  ``param.initial_values()`` would give.
* ``test_state_save_every_throttles_io`` -- replaces
  ``_core_mod._json`` with a counting stub; asserts the dump-call
  count stays in [1, 30] for a 20-iter L-BFGS-B run with
  ``state_save_every=5`` (vs the >100 calls a per-eval save would
  produce).

## C.3 -- Multi-objective Pareto via pymoo (ROADMAP #11)

### Module design

New module ``lumenairy/optimize/multi_objective.py``.  The module
imports unconditionally (no top-level ``import pymoo``), so users
can write:

```python
from lumenairy.optimize.multi_objective import (
    design_optimize_multi_objective, PYMOO_AVAILABLE,
)
```

regardless of whether pymoo is installed.  The actual pymoo
imports happen inside ``design_optimize_multi_objective`` and
raise a clear ``ImportError`` with the install hint if pymoo is
missing:

```python
def _check_pymoo() -> None:
    if not PYMOO_AVAILABLE:
        raise ImportError(
            "design_optimize_multi_objective requires pymoo "
            "(optional dependency).  Install via 'pip install "
            "lumenairy[multi_objective]' or 'pip install pymoo>=0.6'."
        )
```

### Public API

```python
def design_optimize_multi_objective(
    merits, x0, bounds, *,
    n_generations=100, pop_size=50, seed=None,
    constraints=None, progress=None, verbose=False,
) -> ParetoResult:
    ...

@dataclass
class ParetoResult:
    X: np.ndarray                          # (n_solutions, n_params)
    F: np.ndarray                          # (n_solutions, n_merits)
    n_evaluations: int = 0
    n_generations: int = 0
    pymoo_result: Any = None               # raw pymoo handle
    constraint_violations: Optional[np.ndarray] = None
```

### Constraint translation

Each :class:`Constraint` contributes 0, 1, or 2 pymoo ``g(x)<=0``
constraints depending on which of ``lb`` / ``ub`` are set:

* ``lb=L`` -> ``g(x) = L - f(x) <= 0``
* ``ub=U`` -> ``g(x) = f(x) - U <= 0``

The same ``Constraint`` shape works seamlessly between
``design_optimize`` and ``design_optimize_multi_objective``.

### Progress callback wrapper

When the user supplies ``progress=ProgressCallback(...)``, the
wrapper invokes ``progress('design_optimize_multi_objective',
gen / n_generations, msg)`` per generation.  pymoo's NSGA-II
provides per-generation hooks via the ``callback=`` parameter
(an instance with a ``__call__(algorithm)`` method).

### Tests (4) -- all gated on ``_PYMOO_AVAILABLE``

* ``test_pymoo_import_required`` -- when pymoo absent, calls
  ``design_optimize_multi_objective`` and asserts ``ImportError``
  matching ``r'pymoo'``.  When pymoo present (skipped here per
  the env note below), smoke-tests that the call doesn't itself
  raise ImportError.
* ``test_nsga2_2_objective_pareto_front`` (pymoo-required) --
  ZDT1-like 2-objective: ``f1(x)=x``, ``f2(x)=1-sqrt(x)`` on
  x in [0,1]; verifies the returned ``F`` array shape +
  on-curve fidelity to within 0.05.
* ``test_constraints_threaded_through_pymoo`` (pymoo-required) --
  ``x >= 0.5`` Constraint; asserts >50% of returned Pareto
  solutions satisfy the constraint.
* ``test_progress_callback_fires`` (pymoo-required) -- 10
  generations + asserts at least 5 callback invocations all
  using the canonical stage name.

## C.4 -- Hessian / Newton-step optimisation (ROADMAP #12)

### Dispatch

``method='newton'`` is intercepted in ``design_optimize``'s
dispatch chain before the catch-all ``else: so.minimize(...)``
branch.  It dispatches to scipy ``method='trust-ncg'`` with:

* ``jac=_grad_for_newton(x)`` -- routes through the existing
  ``final_jac`` (analytic where available) or
  ``_fd_grad_pure(merit_fn, ..., scheme='central')``.
* ``hess=_hess_for_newton(x)`` -- FD-Jacobian-of-FD-gradient;
  symmetrised after construction.  ``O(N^2)`` merit calls per
  Hessian; ``eps_outer = 1e-4``.

### Large-N user warning

When ``n_params > 30``, a ``UserWarning`` is issued recommending
``method='L-BFGS-B'`` for larger problems.  The optimisation
still proceeds -- the warning is advisory, not fatal -- because
the user may have other reasons (e.g. wanting an explicit Hessian
for downstream sensitivity analysis) to choose Newton on a
larger problem.

### Tests (2)

* ``test_newton_converges_on_small_problem`` -- 5-var quadratic;
  asserts final merit < 1e-4 and ``norm(x) < 1e-2``.  Newton
  with a quadratic merit should converge in a single step (the
  Hessian is exactly 2*I, gradient at x is 2*x, so the Newton
  step is ``-x``).
* ``test_newton_falls_back_on_large_problem`` -- 50-var
  quadratic with ``max_iter=2``; asserts the
  L-BFGS-B-recommendation UserWarning is emitted AND the run
  completes with a finite final merit.

### Edge cases discovered during constrained-opt method-compatibility check

* **``method='lm'`` (Levenberg-Marquardt)** silently ignores
  ``constraints=`` because it dispatches to ``scipy.optimize.
  least_squares``, not ``scipy.optimize.minimize``.  v4.16
  explicitly rejects this combination at the up-front method-
  compat check (it's not in
  ``_METHODS_SUPPORTING_CONSTRAINTS``).  Pre-v4.16 there was no
  ``constraints=`` kwarg, so the silent-ignore was never a
  user-visible bug; the new explicit rejection catches users
  porting from the soft-penalty pattern.
* **``method='differential_evolution'`` / ``'basin_hopping'`` /
  ``'dual_annealing'``** all silently ignore ``constraints=``
  for the same reason (they take their own ``bounds=`` parameter
  and route to dedicated solvers, not ``minimize(constraints=
  [...])``).  v4.16 rejects all three with the same clear
  ValueError.
* **scipy's ``constraints=`` keyword** is supported on SLSQP +
  trust-constr only.  v4.16's ``_METHODS_SUPPORTING_CONSTRAINTS``
  enumerates exactly these two; the validator message points at
  both with usage hints ("SLSQP for small-to-medium problems
  with smooth merits, trust-constr for larger / non-smooth
  ones").

## Backward compatibility

All five new ``design_optimize`` kwargs default to ``None`` or
sensible no-op values:

* ``constraints=None`` -- no constraints applied (legacy path).
* ``state_file=None`` -- no state file written, no resume
  attempted (legacy path).
* ``state_save_every=1`` -- only consulted when ``state_file`` is
  non-None.
* ``hess=None`` -- scipy uses its default Hessian strategy for
  the chosen method (legacy path).
* ``method='newton'`` -- new dispatch branch; existing
  ``method='L-BFGS-B'`` / ``'SLSQP'`` / ``'lm'`` etc. callers
  unaffected.

Pre-v4.16 ``design_optimize`` callers see byte-for-byte identical
behaviour.
