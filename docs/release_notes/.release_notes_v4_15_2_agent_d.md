## v4.15.2 -- Agent D scope: close `rays_from_field` docstring-vs-code drift and missing test coverage

Closes the audit findings flagged in `docs/audits/AUDIT_V4_15_1_2026_05_18.md` Part 3 against `lumenairy.raytrace.from_field.rays_from_field` (introduced in v4.15.1 / Cluster B Item 6).  The v4.15.1 release shipped the wave-to-ray bridge function with correct underlying physics, but two algorithmic gaps (P1-NEW-D, P1-NEW-H), one docstring drift (P2), and five untested code paths (`'uniform'` placement; `'unwrap_gradient'` angle method; vortex per-pixel direction recovery; anamorphic direction cosines; `'cdf'` reproducibility) needed closure.  All eight items addressed below.

### D.1 -- P1-NEW-D: `_place_cdf` applies `intensity_threshold` pixel-wise

`_place_cdf` (`lumenairy/raytrace/from_field.py:328` pre-fix) applied `intensity_threshold` to the MARGINAL sums:

```python
Ix = I.sum(axis=0)
Ix = np.where(Ix > threshold * Ix.max(), Ix, 0.0)
```

`'rejection'` and `'uniform'` both threshold per-pixel.  The marginal-threshold form lets sub-threshold background noise accumulate across rows / columns and survive the threshold (a thin bright streak surrounded by sub-threshold noise then spreads the placement over the full y-extent because the noise sum dominates the y-marginal).

**Fix.**  Apply the threshold pixel-wise BEFORE forming the marginal sums:

```python
I_norm = I / I.max()
I_thresh = np.where(I_norm > threshold, I, 0.0)  # pixel-wise
Ix = I_thresh.sum(axis=0)  # marginal of thresholded
Iy = I_thresh.sum(axis=1)
```

This makes `'cdf'` consistent with the other two placement modes and matches the docstring's claim of a pixel-wise threshold.  The `placement` parameter docstring in `rays_from_field` (the public docstring) is updated to spell out the pixel-wise behaviour and note the v4.15.2 fix.

Pinned by `test_cdf_placement_pixel_threshold_excludes_thin_streak` in `tests/unit/test_v4_15_2_agent_d.py`: a short y-streak of bright pixels in a sub-threshold-noise field must confine the rays to the streak's y-rows, not scatter across the full y-extent.

### D.2 -- P1-NEW-H: `rays_from_field` warns on `n_actual < n_rays`

`_place_rejection` caps at `50 * n_rays` candidate tries and may exit short; `_place_uniform` returns only surviving sub-grid pixels.  Either helper can return fewer than `n_rays` without warning; previously a `ValueError` only triggered at `n_actual == 0`.  Downstream consumers assuming `bundle.x.shape[0] == n_rays` silently saw under-counts.

**Fix.**  After the placement step in `rays_from_field`, when `n_actual < n_rays` emit a `RuntimeWarning` (not an error -- the partial bundle is still useful) identifying the placement mode and the actual / requested counts:

```python
if n_actual < n_rays:
    warnings.warn(
        f"rays_from_field: placement '{placement}' returned "
        f"{n_actual} rays vs requested {n_rays}. ...",
        RuntimeWarning,
        stacklevel=2,
    )
```

`stacklevel=2` ensures the warning attributes the call site of `rays_from_field`, not the internal `warnings.warn` line.  The `n_rays` docstring is updated to document the short-return contract.

Pinned by `test_short_return_emits_warning` in `tests/unit/test_v4_15_2_agent_d.py`.

### D.3 -- P2: top-of-file docstring updated from Madelung to phase-ratio

The module-level docstring at the top of `lumenairy/raytrace/from_field.py` said the direction estimator was `k_perp = grad(phi)` via the paraxial mapping.  This was technically correct for the *continuous-limit* claim, but the inline docstring on `_angle_complex_gradient` (which v4.15.1 already had right) makes clear that the actual implementation uses the *phase-ratio* central difference `arg(E[i,j+1] * conj(E[i,j-1])) / (2 dx)`.

**Fix.**  The Math reference section at the top of the file now explicitly describes the phase-ratio formulation, references the inline docstring for the full derivation, and notes that the form is the discrete analogue of the continuous Madelung formula `Im(grad E / E)` (CLUSTER_B_SPEC.md §4.4) with the discretisation rationale spelled out (exact for plane waves with `|k_x dx| < pi`; singularity-safe because `np.angle` is bounded).  No code change.  Also adds a v4.15.2 history-note paragraph at the bottom of the docstring listing the four agent-D edits.

### D.4 -- P2: `'uniform'` placement test coverage

### D.5 -- P2: `'unwrap_gradient'` angle method test coverage

Previously zero coverage.  Added two pins:

* `test_unwrap_gradient_on_smooth_phase` -- on a smooth tilted plane wave at theta=5deg the recovered `L` matches `sin(theta)` to 1e-6 and agrees with `'complex_gradient'` to 1e-6 pixel-by-pixel.  Confirms the unwrap-along-axis-independently estimator works on smooth phase profiles.
* `test_unwrap_gradient_finite_on_vortex` -- on the LG-like vortex `E = (r/w)*exp(i*theta)*exp(-r^2/w^2)`, `'unwrap_gradient'` produces a finite (non-NaN, non-Inf) result everywhere.

#### Measured behaviour of `'unwrap_gradient'` on vortex fields

Empirically: `'unwrap_gradient'` on the LG-like vortex agrees with `'complex_gradient'` to ~1e-15 pixel-by-pixel.  Both methods produce finite values that closely match the analytical phase gradient `(k_x, k_y) = (-y, x) / (r^2)` away from the singularity core.  Neither method NaNs, warns, or recovers a meaningfully different direction.

Why?  `np.unwrap` along the x axis and along the y axis independently does NOT cross the branch cut at the origin in a way that produces an inconsistent unwrap.  Each axis's 1-D unwrap stays within `(-pi, pi]` locally, and `np.gradient` then estimates the same slope as the phase-ratio form along each axis separately.  The two methods only diverge in pathological cases (e.g. a vortex with the singularity at a pixel boundary, where the unwrap along one row hits a `pi` jump and adds `2 pi`).

The test pins the empirically-observed finite-result contract; it does NOT pin a warning because v4.15.2 does not introduce a vortex-singularity warning (those would require detecting the `2 pi` integral around closed loops, out of scope for a docstring-vs-code patch).  The `'unwrap_gradient'` docstring already calls the method "fragile near phase singularities; use only for smooth phase profiles" -- the test confirms this prose is conservative: in practice the method does NOT explode on a typical LG vortex.

### D.6 -- P2: vortex direction-recovery pin (per-pixel)

The pre-fix vortex test (`test_complex_gradient_handles_vortex_without_nan`) only checked `np.isfinite`.  The per-pixel direction recovery was uncovered.

Added: `test_complex_gradient_vortex_direction_recovery_per_pixel`.  Build the LG-like vortex, place rays via rejection sampling, and assert that for rays at `r > 2 * dx` (safely outside the singularity core) the recovered direction `(L, M)` is parallel or anti-parallel to the analytical tangent `(-y, x) / r` (i.e. `|cos(angle)| > 1 - 5e-2`).  Tolerance accounts for the finite-difference error near the core and the radial phase contribution from the Gaussian envelope.

### D.7 -- P2: anamorphic `dx != dy` direction-cosines pin

The pre-fix `test_anamorphic_dy_passes_through` only tested ray positions.  Direction cosines were uncovered.

Added: `test_anamorphic_direction_cosines_use_correct_pitches`.  An anamorphic tilted plane wave `E = exp(i * (kx*X + ky*Y))` on an `dx != dy` grid (1 um x 3 um) with `theta_x = 4 deg`, `theta_y = 2 deg`.  Assert `L = sin(theta_x)` and `M = sin(theta_y)` independently, confirming the angle helper uses the correct per-axis pitch.  A Gaussian envelope concentrates placement inside the grid so boundary one-sided differences (where `ix_plus = clip(ix+1, 0, Nx-1)` halves the recovered `kx`) don't contaminate the test.

Same field, two calls with `random_state=42`; assert bit-identical positions, direction cosines, OPD, alive, and (implicitly) error_code via `assert_array_equal` (eight bundle arrays per call pair).

### D.9 -- P3: `'uniform'` edge cases (`n_rays=0` and `n_rays > N^2`)

Pre-fix:

* `n_rays=0` raised `ValueError: n_rays must be a positive integer`.  No documented contract for "an empty bundle".  Downstream code wanting to request zero rays as a no-op had to special-case at the call site.
* `n_rays = 2 * N**2` on an N x N grid returned `2 * N**2` rays with the sub-grid landing on duplicate pixels (the `np.linspace(0, N-1, ny_grid)` `np.round` collisions).  Logically there can only be N^2 unique grid pixels.

**Fixes.**

* Loosened validation to `n_rays >= 0` (was `>= 1`).  `n_rays == 0` now returns an empty `RayBundle` with all per-ray arrays of shape `(0,)` cleanly, before any placement step runs.  The error message for invalid `n_rays` is updated to say "non-negative integer".
* `_place_uniform` now deduplicates the sub-grid landings stably by composite-index `np.unique` -- the helper never returns more rays than there are unique grid pixels.  Combined with D.2, `n_rays = 2 * N**2` on an N x N grid returns at most N^2 rays AND triggers the short-return `RuntimeWarning`.

Pinned by `test_uniform_placement_n_rays_zero`, `test_uniform_placement_n_rays_zero_works_for_cdf_and_rejection`, and `test_uniform_placement_n_rays_exceeds_grid_size`.

### Measured behaviour notes

* **`'unwrap_gradient'` on a vortex**: agrees with `'complex_gradient'` to ~1e-15 pixel-by-pixel.  Both methods produce finite values that closely match the analytical phase gradient away from the singularity core.  Neither NaNs, neither warns, neither recovers a meaningfully different direction on the LG-like vortex tested.  See `test_unwrap_gradient_finite_on_vortex` for the pin.
* **Pixel-wise threshold delta**: the v4.15.2 `_place_cdf` rework is a strict refinement -- a strictly-narrower set of pixels survives the threshold under the new behaviour than under the old, so the CDF concentrates more tightly on bright regions.  For separable-Gaussian inputs (the most common visualisation use case) the behaviour change is below test tolerance because the marginal sum and pixel-thresholded marginal are nearly identical when the support is connected and well above noise.  Only for sub-threshold-noise + thin-bright-region scenarios does the change become test-visible (the new `test_cdf_placement_pixel_threshold_excludes_thin_streak` pin).
* **Short-return frequency**: in normal use (`'cdf'` with default `intensity_threshold=1e-4` and a typical beam profile), no short-return warning fires.  `'rejection'` with the default 50x candidate budget delivers `n_rays` in practice for any reasonable acceptance rate (the budget runs out only for very high-rejection fields).  `'uniform'` returns the requested count whenever `n_rays <= N**2` and the supporting region is well-sampled.  The warning is a defensive guard; routine workflows won't see it.
