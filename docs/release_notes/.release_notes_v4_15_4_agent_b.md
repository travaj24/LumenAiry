# v4.15.4 -- `_validation.py` hoist, `_PerturbedABCDFallbackSentinel` deletion, `-W error::DeprecationWarning` test hygiene (Agent B)

Patch release closing the **P2-NEW-F1-D** (`_validation.py` lazy-import hoist), **P2-NEW-F1-B option (a)** (dead-sentinel deletion), and **P3-NEW-F2-4** (`-W error::DeprecationWarning` test hygiene) findings from `docs/audits/AUDIT_V4_15_3_2026_05_18.md`.

## Three hygiene closures, one release

The v4.15.3 audit identified three closely-related hygiene items: a lazy import that papered over a circular dep that did not exist, a dead sentinel class whose v4.15.3 "deprecated-but-kept" marker was data-only, and 57 `v4.15.x` test failures under `pytest -W error::DeprecationWarning` because tests legitimately invoked the documented Schell-family `return_kind` default-path warning without shielding.  All three are surface hygiene rather than physics; all three are addressed in one release for a clean changelog.

## B.1 -- `_validation.py` lazy-import hoist (P2-NEW-F1-D)

### What changed

`lumenairy/_validation.py` v4.15.3 imported `PartialCoherenceMCF` inside the body of `_check_2d_scalar_field`:

```python
def _check_2d_scalar_field(E, fn_name):
    # Lazy import avoids a circular dependency from
    # ``sources.core`` (which imports from ``_deprecation``).
    from lumenairy.sources.core import PartialCoherenceMCF as _MCF
    ...
```

The audit grep-verified that `sources.core` does **not** import from `_validation` -- it only imports from `_deprecation`.  No circular dependency exists.  The lazy import was paying a per-call `_bootstrap._find_and_load` / `_handle_fromlist` cost (~1 us) for nothing.  In optimisation loops where the helper fires per propagator call (1-10 ms per merit eval), the wasted cost was small but real.

v4.15.4 hoists the import to module scope:

```python
# Module-level import -- v4.15.3 used a lazy import inside the function
# body, citing a (hypothetical) circular dependency with
# ``sources.core``.  ``sources.core`` does NOT actually import from
# ``_validation`` (it only imports from ``_deprecation``), so the
# circular-dep claim was inaccurate and the lazy import wasted ~1 us
# per propagator call (1-10 ms per merit eval in optimisation loops).
# v4.15.4 hoists the import to module scope.
#
# If a future refactor introduces a ``sources.core`` -> ``_validation``
# import path, switch to a ``TYPE_CHECKING`` import + duck-typed
# predicate (e.g. ``hasattr(E, 'mcf_matrix')`` or
# ``type(E).__name__ == 'PartialCoherenceMCF'``) instead of restoring
# the lazy import -- the duck-typed predicate is free of import-order
# constraints AND keeps the helper hot-loop cheap.
from lumenairy.sources.core import PartialCoherenceMCF as _MCF
```

### Hoist verification

`python -c "import lumenairy"` runs clean.  No `ImportError`.  No circular-import message in stderr.  The hypothetical circular dep is, as expected, hypothetical.

The new comment block contains defensive language: if a future refactor *does* introduce a `sources.core -> _validation` import path, the maintainer is instructed to switch to a `TYPE_CHECKING` import + duck-typed predicate (e.g. `hasattr(E, 'mcf_matrix')` or `type(E).__name__ == 'PartialCoherenceMCF'`) rather than re-introduce the lazy import.  The duck-typed predicate is free of import-order constraints AND keeps the helper hot-loop cheap.

## B.2 -- `_PerturbedABCDFallbackSentinel` deletion (P2-NEW-F1-B option a)

### What changed

`lumenairy/optimize/core.py` v4.15.2 defined three new `_Sentinel` subclasses (`_InvalidFocalLengthSentinel`, `_FailedScanStrehlSentinel`, `_PerturbedABCDFallbackSentinel`) at lines `:2044-2144`.  v4.15.3 (Agent C) wired the two scalar sentinels at their intended callsites; the third (`_PerturbedABCDFallbackSentinel`) was left unwired because the underlying fallback at `ToleranceAwareMerit.evaluate` is a 2-tuple `(efl_p, bfl_p) = (ctx.efl, ctx.bfl)`, not a single scalar -- wrapping the tuple in a single sentinel singleton would break downstream `sub_ctx.efl = efl_p` / `sub_ctx.bfl = bfl_p` usage.

v4.15.3 marked the class as dead code via a class-level `_v4_15_3_dead_code: bool = True` attribute and an explicit deprecation docstring.  The audit flagged that the marker is **data-only**: no static analyser honours arbitrary class attributes, the class still ships as a public name in the module namespace, and a future contributor reading the v4.15.2 sentinel block has no in-band signal that the class is dead.

v4.15.4 takes option (a) from the audit: **delete the class and its singleton outright**.

### Deletion scope

| What | Pre-v4.15.4 lines | Post-v4.15.4 |
|---|---|---|
| `class _PerturbedABCDFallbackSentinel(_Sentinel)` definition | `optimize/core.py:2130-2183` (~54 lines incl. docstring) | deleted |
| `_PERTURBED_ABCD_FALLBACK_SENTINEL_OBJ = _PerturbedABCDFallbackSentinel()` | `optimize/core.py:2185` | deleted |
| `_SENTINEL_REGISTRY` entry | populated lazily on `__init__` of the class | never populated (class deleted) |
| Replacement | `# v4.15.4 (audit AUDIT_V4_15_3 P2-NEW-F1-B option a): ...` comment block citing the audit closure | n/a |

The `ToleranceAwareMerit.evaluate` perturbed-ABCD failure branch (`optimize/core.py:2895-2907`) is unchanged: it still writes the tuple-shaped fallback `efl_p, bfl_p = ctx.efl, ctx.bfl`.  Only the unwired sentinel definition is removed.  Net deletion: ~58 lines (54 class body + singleton instantiation + spacing).

### Test pin updates

The v4.15.2 test pin in `test_v4_15_2_agent_e.py::TestOptimizeCoreSentinelMigration` previously asserted the class existed.  v4.15.4 updates it to:

1. Remove the dead class from `EXPECTED_SUBCLASSES` (now 3 entries, was 4).
2. Remove the singleton from the repr / pickle round-trip loops.
3. Add a new `test_perturbed_abcd_fallback_sentinel_deleted_v4_15_4` pin that asserts both names are gone via `hasattr(oc, name) is False`.

The v4.15.3 `test_v4_15_3_agent_c.py::TestPerturbedABCDSentinelDeadCode` class (which asserted the v4.15.3 class-attribute marker and AST-unwiredness) is converted into a 2-test `TestPerturbedABCDSentinelDeletedV4_15_4` class asserting the deletion stuck.  The `test_perturbed_abcd_sentinel_pickle_round_trip_still_works` cross-check is removed (no singleton to round-trip).

The v4.15.3 `test_v4_15_3_agent_d.py::test_changelog_v4_15_2_sentinel_line_citations_refreshed` line-count assertion is loosened from `len(actual_lines) == 3` to `== 2` to reflect the deletion.

The v4.15.0 `test_v4_15_agent_f.py::TestF5ChangelogLineCitations::test_changelog_cites_actual_current_lines` test reads `CHANGELOG.md` and verifies the `_ZERO_APERTURE_MASK` branch citation matches the actual `if _cache['mask'] is _ZERO_APERTURE_MASK` line.  The deletion shifted that line from `:2980` to `:2938`; the CHANGELOG citations at lines `:154` and `:608` are updated to `:2938`.

### Why option (a) over option (b) ("keep + document as deprecated")

The v4.15.3 closure took option (b) -- keep the class, mark it deprecated.  The v4.15.4 audit finding is that **data-only deprecation markers don't survive the next refactor**: a future maintainer doing a sweep of `_Sentinel` subclasses (e.g. to add a new method to the base class) will either inadvertently introduce a use of the dead class or strip out the marker without realising it was load-bearing.  Deletion is the surgical move.  The audit closure (option (a)) is to bite the bullet and absorb the test-pin churn in the same release.

## B.3 -- `-W error::DeprecationWarning` test hygiene (P3-NEW-F2-4)

### What changed

`pytest -W error::DeprecationWarning` on `tests/unit/` against v4.15.3 yielded **63 failures on this dev box** (the audit cited 57; minor environment variance).  Every failure traced to the same root cause: a v4.15.x test legitimately invoked one of the Schell-family factories (`create_gaussian_schell_source`, `create_schell_model_source`, `create_annular_incoherent_source`, `Source.gaussian_schell`, `Source.schell_model`) -- or the LED-source factory in one v4.15.0 test -- using the legacy positional default, which fires the documented v4.15.1 `return_kind` `DeprecationWarning`.

The tests *want* the warning to fire (some pin its content; most just need the factory's 4-tuple return shape).  Under `-W error::DeprecationWarning` the warning gets promoted to an exception and the test fails before reaching its assertion.

### Approach: per-module `pytestmark` filterwarnings

Two viable options:

1. **Per-test-site `pytest.warns(DeprecationWarning, match=...)` shielding** -- explicit but verbose; touches 57 distinct test sites.
2. **Per-module `pytestmark = pytest.mark.filterwarnings('default::DeprecationWarning')`** -- one edit per file; pins DeprecationWarning back to its default "report once" handling for the whole module, leaving every other module's strict promotion intact.

v4.15.4 takes option 2.  Eight test modules each receive one `pytestmark` definition at the top (post-import, pre-test-class):

```python
# v4.15.4 (AUDIT_V4_15_3 P3-NEW-F2-4): the Schell-family tests below
# legitimately invoke the factories with the legacy positional default
# (the v4.15.1 ``return_kind`` default-path triggers a
# DeprecationWarning).  Pin DeprecationWarning back to ``default`` for
# this module so the suite stays clean under strict
# ``-W error::DeprecationWarning``.
pytestmark = pytest.mark.filterwarnings(
    'default::DeprecationWarning',
)
```

### Files touched

| File | Failures shielded | Trigger |
|---|---|---|
| `tests/unit/test_v4_15_1_agent_b.py` | 14 | `create_*_schell_source` ensemble-shape pins |
| `tests/unit/test_v4_15_2_agent_c.py` | 12 | `_make_ensemble` / `_make_mcf` helpers |
| `tests/unit/test_v4_15_2_agent_e.py` | 2 | `Source.gaussian_schell` / `Source.schell_model` ensemble-tuple pin |
| `tests/unit/test_v4_15_3_agent_a.py` | 20 | `_make_ensemble` helper (9 sibling guards * 2 + 2 sanity) |
| `tests/unit/test_v4_15_agent_b.py` | 8 | `TestB3SchellSources`, `TestB4AnnularIncoherent`, `TestP2FacFactoryValidationMetaPin` |
| `tests/unit/test_v4_15_agent_f.py` | 1 | `TestF1LedSourceErrorMessage` (LED, not Schell, same pattern) |

Six files * one one-line addition = 6 module-level marker lines.  The shielded warnings still fire; they just don't promote to exceptions.
