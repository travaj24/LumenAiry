# LumenAiry v4.16.1 / Agent C release notes

**Scope:** Audit items 9-15 from AUDIT_V4_16_0_DEEP_2026_05_19 Part 8.

## Summary

Closes 7 audit items targeting:

* Constraint API consistency (vector-return crashes + lambda pickle-fail
  pattern at workers>1).
* Two sibling-gap meta-pins carried over from prior audits
  (GLASS_VALIDITY <-> GLASS_REGISTRY; @lru_cache <-> _cache_registry).
* `_clear_local_asm_caches` registration inconsistency (early-binding
  vs the canonical late-binding lambda pattern used by the other 8
  cache enrollments).
* `warnings.warn` hygiene gaps at `prescriptions.py:1019, 1470`.
* 4 stale v4.15 ROADMAP-content tests pinning release-specific
  wording that drifts each cycle (re-written to be release-agnostic).

## Audit closures

### C.1 -- Constraint scalar-only validation

`Constraint.fun` was documented as accepting `f(x) -> scalar | ndarray`
but the pymoo wrapper at `multi_objective.py:269,273` coerces each
constraint result via `float(_f(xv))`, which raises `TypeError: only
length-1 arrays can be converted to Python scalars` on a `(K,)`-shaped
ndarray.

**Fix (option a from the audit):** narrow the docstring to
scalar-only and add `__post_init__` validation that probes
`fun(np.zeros(1))` and rejects ndarrays of shape != `()` with a clear
`TypeError` citing the constraint's label.  Probe is best-effort
(wrapped in try/except so a `fun` that legitimately rejects the
synthetic probe -- e.g. requires a specific parameter-vector shape --
does not break dataclass construction).

* `lumenairy/optimize/core.py:3074-3220` (Constraint docstring +
  `__post_init__` validation).
* Regression tests: `tests/unit/test_v4_16_1_agent_c.py::test_constraint_*`
  (5 tests).

### C.2 -- Constraint lambda pickle-fail UserWarning

`Constraint(fun=lambda x: ...)` is the recommended idiom in the
example block but lambdas aren't picklable -- a parallel-workers
optimizer (`differential_evolution(workers>1)` / joblib FD-gradient)
fails with `PicklingError`.

**Fix:** add a `UserWarning` at `__post_init__` when `fun.__name__ ==
'<lambda>'`, recommending a module-level function for
parallel-workers compatibility.  Single-process SLSQP / trust-constr
works with lambdas without issue, so the warning is a soft heads-up
rather than a hard rejection.

* `lumenairy/optimize/core.py:3120-3147` (lambda detection + warn).
* Regression tests: `tests/unit/test_v4_16_1_agent_c.py::test_constraint_lambda_*`
  (3 tests).

### C.3 -- `_check_glass_registry_consistency()` extends to GLASS_VALIDITY

The v4.14.2 consistency check walked `GLASS_REGISTRY <-> SELLMEIER_COEFFICIENTS`
in both directions but did not cover the v4.16.0 addition of
`GLASS_VALIDITY`.

**Fix:** extend the check at module-load time:

1.  Every key in `GLASS_VALIDITY` MUST appear in `GLASS_REGISTRY`
    (a validity entry without a registry counterpart is unreachable
    -- the warn helper looks up by registry name).
2.  The reverse direction (registry -> validity) is intentionally NOT
    enforced as a hard requirement; user-registered callable glasses
    typically don't declare a wavelength range, and a missing
    validity entry safely defaults to the no-warning sentinel
    `(0.0, inf)`.
3.  Each `GLASS_VALIDITY` entry must be a 2-tuple
    `(lambda_min, lambda_max)` with `lambda_min < lambda_max`, both
    finite, non-negative.

* `lumenairy/glass.py:625-735` (`_check_glass_registry_consistency`
  + new `_GLASS_VALIDITY_REGISTRY_EXEMPTIONS` set).
* Regression tests: `tests/unit/test_v4_16_1_agent_c.py::test_glass_validity_*`
  (6 tests).

### C.4 -- 10th dispatcher meta-pin: cache-registry enrollment walker

New AST-walker that closes the
`@lru_cache` / module-level `_CACHE = OrderedDict(...)` <-> `_cache_registry`
sibling-gap.  The walker:

1.  Walks every public `lumenairy/*.py` module (excluding
    `_cache_registry.py` and `__init__.py` files).
2.  Discovers every `@functools.lru_cache(...)` decorator on a
    top-level function AND every module-level cache declaration of
    the form `_FOO_CACHE: 'OrderedDict[...]' = OrderedDict()`.
3.  For each discovered cache, verifies the owning module contains
    at least one `register_cache_clearer(...)` call (or
    `_register_cache_clearer(...)` aliased import).
4.  Reports caches without enrollment, OR listed in
    `_CACHE_REGISTRY_EXEMPTIONS` with a cited rationale.

**Walker discovery counts at v4.16.1:**

* **15 caches discovered** (target was 12-15):
  * 8 enrolled (the canonical v4.16.0 set).
  * 7 documented exempt (transitively drained by sibling clearers,
    or singleton build-once-per-process objects).
  * 0 MISSING.

**Were any orphan caches found?**  No.  The 7 exemptions are all
legitimate: 5 caches under `propagation.py` are drained transitively
by `_clear_local_asm_caches` (the `asm_local` enrollment), 1
(`_HG_MODE_STACK_CACHE`) is drained transitively by
`clear_lg_mode_stack_cache`, 1 (`_JAX_IFT_SOLVER_CACHE`) is a
singleton build-once-per-process JAX-decorated solver that doesn't
grow, and 2 phase-retrieval kernels are drained as a group by
`clear_phase_retrieval_caches`.

Counter-pin: `test_counter_pin_fake_unregistered_cache_fails`
injects a synthetic cache record into a file that has NO
`register_cache_clearer` call and asserts the main pin fires.

Positive-signal counter-pin:
`test_counter_pin_fake_registered_cache_does_not_trip` injects a
synthetic cache record into a file that DOES have a registration
call and asserts the main pin does not flag it.

* `tests/unit/test_v4_16_1_dispatcher_pin_cache_registry_enrollment.py`
  (6 tests; uses the canonical `lru_cache(maxsize=None)` on
  `_file_to_ast` for ~30x speedup per the v4.15.5 P3-NEW-F1-2
  pattern).

### C.5 -- Late-binding lambda for `_clear_local_asm_caches`

`propagators/propagation.py:803` registered `_clear_local_asm_caches`
via a bare function-reference (early-binding); the other 8
cache-owning modules use a late-binding lambda
(`lambda: getattr(_this_mod, '<clear_fn>')()`).  The discrepancy
means `mock.patch.object(propagation, '_clear_local_asm_caches', ...)`
is silently bypassed by `clear_asm_caches` -- a tester-visible
inconsistency vs the other 8 caches.

**Fix:** convert to the canonical late-binding pattern.  The cost is
one extra attribute lookup per cache per drain (negligible vs the
actual cache-clear work).  External contract preserved: every cache
drained pre-v4.16.1 is still drained.

* `lumenairy/propagators/propagation.py:796-823` (late-binding
  lambda).
* Regression tests:
  * `tests/unit/test_v4_16_1_agent_c.py::test_clear_local_asm_caches_*`
    (3 tests; one uses `mock.patch.object` to verify the late-binding
    closure observes the monkey-patch).
  * `tests/unit/test_v4_16_1_dispatcher_pin_cache_registry_enrollment.py::test_propagation_asm_local_uses_late_binding_lambda`
    (AST-based structural pin).

### C.6 -- Stale v4.15 ROADMAP-content tests rewritten release-agnostic

The audit (P1-NEW-2WAY-1) flagged 4 tests pinning specific ROADMAP
wording that drifts each release.  At v4.16.0 HEAD the tests fail
because the ROADMAP has been updated for v4.16.0 and the literal
strings no longer match.

**Rewrites:**

1.  `tests/unit/test_v4_15_2_agent_e.py::TestRoadmapBaseline::test_roadmap_references_v4_15_1_baseline`
    -- now asserts the structural invariant that the header
    annotation parses to `(major, minor, patch) >= (4, 15, 1)` and
    that the `## Current state` section exists; no specific newer
    version is pinned.  The original AUDIT_V4_15_1 P1-NEW-I closure
    (no `v4.15.0, ~1400 tests` claim) remains pinned as a
    name-anchored absence check.

2.  `tests/unit/test_v4_15_4_agent_c.py::test_roadmap_test_count_matches_actual_collected`
    -- now accepts either the v4.15.4 `unit tests collected` wording
    OR the v4.16.0 `unit tests passing` wording.  The upper-bound
    check (claimed <= live `pytest --collect-only` count) is removed
    because it drifts each release and creates a brittle pin; the
    lower bound (claimed >= 1824) is preserved as the audit closure
    floor.

3.  `tests/unit/test_v4_15_4_agent_c.py::test_roadmap_closed_audits_includes_audit_v4_15_2_and_3`
    -- now scans BOTH the explicit-name wording (`AUDIT_V4_15_2`,
    `AUDIT_V4_15_3` as literal substrings) AND the range wording
    (`AUDIT_V4_X through AUDIT_V4_Y all closed`).  A range that
    encompasses the requested audit version passes.

4.  `tests/unit/test_v4_15_4_agent_c.py::test_roadmap_4_of_5_meta_pins_claim`
    -- now accepts either the original `N of M` wording (with N >= 4)
    OR an itemised list of >= 4 meta-pin items (`V1:`, `V2:`, ...,
    `V9:`) under a `Meta-pin coverage` heading.  The v4.16.0 ROADMAP
    uses the itemised form.

All 4 tests pass at v4.16.0/v4.16.1 HEAD and will continue passing
through future release cycles without per-release maintenance.

### C.7 -- `warnings.warn` hygiene at `prescriptions.py:1019, 1470`

Both audit-cited `warnings.warn(...)` calls (the `Glasses not in
GLASS_REGISTRY` warnings emitted by `apply_real_lens` callers) had
NO explicit `UserWarning` category and NO `stacklevel`.  Default
category is `UserWarning` (correct), but missing stacklevel means
the warning points at this line rather than the user's caller.

**Fix:** add explicit `UserWarning` category + `stacklevel=2` to both
sites.

* `lumenairy/io/prescriptions.py:1019-1023` and `1470-1476`.
* Regression tests:
  * `tests/unit/test_v4_16_1_agent_c.py::test_prescriptions_warn_calls_have_explicit_category_and_stacklevel`
    (AST-walks all warn calls in prescriptions.py).
  * `tests/unit/test_v4_16_1_agent_c.py::test_prescriptions_specific_warn_lines_pinned`
    (name-anchored pin for the two `Glasses not in GLASS_REGISTRY`
    siblings).
