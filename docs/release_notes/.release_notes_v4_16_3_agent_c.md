## v4.16.3 -- Agent C: optimize-subsystem polish closures

Closes the 2 P2 polish items from
`docs/audits/AUDIT_V4_16_2_2026_05_20.md` concentrated in
`lumenairy/optimize/core.py`:

* **P2-NEW-F1-1** -- `Constraint.__post_init__` auto-probe removal
  was a silent behaviour change in v4.16.2.  v4.16.1 shipped a
  `fun(np.zeros(1))` auto-probe to shape-check the constraint return
  at construction time; v4.16.2 removed it (probe was expensive for
  BFL-style callables that internally ran a full ray-trace) and
  moved the contract to opt-in `Constraint.validate()`.  Compare to
  the v4.16.1 `MultiWavelengthMerit` SUM->AVG transition which DID
  get a one-cycle `FutureWarning` in v4.16.2 -- same
  silent-behaviour-shift treated inconsistently.  v4.16.3 emits a
  one-cycle `DeprecationWarning` (latched at module level so
  optimisation loops that build N `Constraint(...)` objects don't
  flood the warning channel) describing the v4.16.1 -> v4.16.2
  transition, advising callers to call `.validate()` explicitly,
  citing v4.16.2 as the change-version and v5.0 as the removal
  target for the transitional warning.
* **P2-NEW-F1-2** -- the `pickle.dumps` probe catch list at
  `optimize/core.py:3229-3232` was
  `(pickle.PicklingError, AttributeError, TypeError)` -- too narrow.
  It missed `RecursionError` (deep object graph), `RuntimeError`
  (raised by a custom `__reduce__`), `MemoryError` (huge object),
  and arbitrary exceptions from `__reduce__` / `__getstate__`.  A
  `fun` whose `__reduce__` raised `RuntimeError` propagated out of
  `Constraint(...)` construction, defeating the warning's
  "friendlier than rejecting" intent.  v4.16.3 widens to
  `except Exception` -- pickling is a best-effort heuristic; any
  failure is a "not safely picklable" signal.  `BaseException`
  (`KeyboardInterrupt` / `SystemExit`) is intentionally left to
  propagate so interpreter-control signals are not swallowed.

Both changes preserve every existing v4.16.2 contract: same warning
text + category for picklable callables (none), same UserWarning
for unpicklable callables (text unchanged), same opt-in
`.validate()` contract.  No merit-value drift, no physics-semantics
change.

### P2-NEW-F1-2 -- `pickle.dumps` catch widened to `Exception`

`lumenairy/optimize/core.py`.

**Before (v4.16.2)**:

```python
import pickle
try:
    pickle.dumps(self.fun)
except (pickle.PicklingError, AttributeError, TypeError) as e:
    warnings.warn(...UserWarning...)
```

**After (v4.16.3)**:

```python
import pickle
try:
    pickle.dumps(self.fun)
except Exception as e:  # noqa: BLE001 -- best-effort probe
    warnings.warn(...UserWarning...)
```

**Coverage table** (regression tests pin all 3 new paths):

| `__reduce__` raises | v4.16.2 narrow catch | v4.16.3 widened catch |
|---|---|---|
| `pickle.PicklingError` (lambda)     | warn          | warn          |
| `AttributeError` (closure)          | warn          | warn          |
| `TypeError` (C-extension callable)  | warn          | warn          |
| `RuntimeError` (custom `__reduce__`) | **propagates (crashes!)** | warn |
| `RecursionError` (deep object graph) | **propagates** | warn |
| `MemoryError` (huge object)         | **propagates** | warn |
| `KeyboardInterrupt` (Ctrl-C)        | propagates    | propagates (correct: BaseException) |

The first three rows (v4.16.2 baseline behaviour) are unchanged.
The next three are the new coverage: any failure in `pickle.dumps`
is now treated as "not safely picklable" rather than letting the
exception escape from `Constraint(...)` construction.

The last row is the safety contract: we widened to `Exception`,
NOT `BaseException`, so `KeyboardInterrupt` and `SystemExit` still
propagate.  Pinned by
`test_p2_pickle_probe_does_not_swallow_keyboard_interrupt`.

**Realistic motivation**: a `fun` that wraps a JAX-traced computation
or a library object that explicitly refuses pickling via a runtime
error (rather than the canonical `pickle.PicklingError`) would have
crashed `Constraint(...)` construction pre-v4.16.3.  The
v4.16.2 closure intent was "warn, don't reject" -- v4.16.3
delivers that for the full exception surface.

## Sibling-gap discipline

Per the audit's "sibling-gap sweep" instruction, swept the file
for the same patterns at adjacent sites:

| Pattern                                                                    | Sites checked                                                                                                       | Status |
|----------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|--------|
| Silent auto-removed feature without `DeprecationWarning`                   | v4.16.1 -> v4.16.2 transitions inside `optimize/core.py`: `MultiWavelengthMerit` SUM->AVG (already has FutureWarning in v4.16.2); `Constraint.__post_init__` auto-probe (this closure) | Constraint auto-probe is the only sibling-gap; MultiWavelengthMerit already has its FutureWarning latch. |
| Narrow `except (...)` catch list around best-effort heuristics             | Full-file grep across 24 `except (...)` sites in `optimize/core.py`                                                  | The pickle-probe catch list is the only best-effort heuristic with a narrow tuple.  The other 23 sites are all merit/fun evaluation handlers where the narrow tuple is intentional (they want to propagate non-evaluation errors).  No other sibling-gap candidates. |

Detailed `except (...)` site survey (the audit asked for findings,
so documenting):

* Sites at 745, 1077, 1308, 1359, 1510, 1547, 1970, 2409, 2718,
  2742, 2968, 3041, 3903, 3921, 3992, 4109, 4151 -- all are
  evaluation-loop wrappers around `merit.evaluate(ctx)` /
  `fun(x)` calls inside a try-except returning `inf` or
  `nan` on failure.  They intentionally catch a narrow set
  (`ValueError, RuntimeError, ZeroDivisionError, ...`) so that
  truly-exceptional errors (`KeyboardInterrupt`,
  `BaseException`, `MemoryError`, programming-error
  `AttributeError`s) propagate to halt the optimisation rather
  than silently corrupt the merit landscape with `nan`s.
  Widening these to `Exception` would actively hurt
  debuggability.
* Sites at 1493, 1892, 3783, 3791 -- file-I/O / JSON-parsing
  handlers; narrow tuple is correct (only the documented
  I/O-failure modes silently return `None`).
* Site at 2501 -- a checkpoint-resume parser; narrow tuple is
  correct for the same reason.

The pickle-probe is uniquely a "this is a best-effort heuristic"
site: there's no recovery path beyond "emit a warning advising
the user to use a module-level function".  The widening is
appropriate here and only here.

## Migration notes for users

* **`Constraint(...)` construction** -- first construction per
  process now emits a one-shot `DeprecationWarning` describing the
  v4.16.1 -> v4.16.2 auto-probe removal.  This is purely
  informational; the behavioural change happened in v4.16.2.  If
  you came to rely on the v4.16.1 vector-return rejection at
  construction time, call `c.validate()` explicitly after
  construction for the same best-effort scalar-shape check.
  Silence the transitional notice via
  `warnings.filterwarnings('ignore', category=DeprecationWarning,
  module='lumenairy.optimize.core')`.  The warning is scheduled
  for removal in v5.0.
* **`Constraint(fun=<unpicklable>)`** -- previously the
  `pickle.dumps` probe could itself crash if the `fun`'s
  `__reduce__` raised a non-`(PicklingError, AttributeError,
  TypeError)` exception (e.g. `RuntimeError` from a custom
  `__reduce__`).  v4.16.3 widens the catch so any failure during
  the pickle probe is treated as "not picklable" and emits the
  existing `UserWarning` rather than propagating the underlying
  exception out of construction.  `KeyboardInterrupt` and
  `SystemExit` still propagate as before.
