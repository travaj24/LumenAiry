## E.1 -- UI subpackage (7 findings)

### P1-UI-1: stale Thorlabs sort-table glass list (`main_window.py:1551`)

`_build_thorlabs_menu._efl_of` uses a Lensmaker estimate to sort the
Thorlabs sub-menus by EFL.  The high-index conditional list
(`('S-LAH64', 'N-SF11')` -> `n=1.785`) silently fell back to the
N-BK7 n_d=1.5168 estimate for any catalog entry whose `glass` was
N-LASF9 or S-NPH1 -- so menu sort placed those high-density-flint
singlets alongside crown singlets despite having ~10-15% shorter
focal lengths at the same radii.

Fix: extended the table to add `'N-LASF9' -> n=1.85` and
`'S-NPH1' -> n=1.81`.  The sort heuristic is the only consumer; the
actual physics still flows through `get_glass_index`.

### P1-UI-2: nudge keystroke bypasses coord-mode (`main_window.py:1639`)

Shift+Up / Shift+Down (and the Ctrl+Shift bigger-nudge variants)
mutated `Element.distance_mm` directly.  In `'absolute'` display
mode the Distance column shows the front-vertex Z (not the relative
gap), so the keystroke contract drifted from the visible value to
the underlying object.

Fix: read the current display value via `get_display_distance`, add
`delta_mm`, and write back through `set_display_distance` -- the
canonical coord-mode-aware setter that already handles `_checkpoint`,
the absolute-mode back-vertex derivation, and the `system_changed`
signal emission.  Pin tests cover both relative and absolute modes
under a live `SystemModel`.

### P1-UI-3: undo/redo drops three model fields (`model.py:1295-1303`)

`SystemModel._capture_state` snapshot covered elements, wavelengths,
EPD, field angles, coordinate mode, and optimizer variables -- but
*not* `wavelength_weights`, `field_weights`, or `lens_options`.
Editing any of the three and then Ctrl+Z left them at their
post-edit values while the rest of the model rolled back: an orphan
state with weights pointing to a different elements list.

Fix: added all three to `_capture_state` and `_restore_state` with
list/dict copies (no need for `deepcopy` because the contents are
flat containers of immutables).  Restore uses `state.get(...)` so
older snapshots that lack the keys (e.g. ones serialised by a
pre-v4.15 Snapshots-dock save) are tolerated -- the live values are
left alone in that legacy case.  Pin tests cover all three fields
independently.

### P1-UI-4: inconsistent prev-element back-vertex calc (`model.py:717-718` vs `:752`)

Two methods computed "where is the previous element's back vertex in
world space?" with different formulae:

| Call site | Formula |
|---|---|
| `set_element_absolute_field` (was `:717-718`) | `sum(s.thickness for s in prev.surfaces)` -- ALL surfaces |
| `set_display_distance` (`:752`) | `prev_elem.internal_thickness_mm` -- `sum(surfaces[:-1])` only |

Same value for freshly-inserted Thorlabs singlets (where the
back-surface thickness is 0 by convention), but the two diverge for
elements whose back-surface thickness was explicitly written to
non-zero (e.g. by an ungroup-then-edit workflow, or after the trace
builder mutates `surfaces[-1].thickness = next_elem.distance_mm * 1e-3`
and the model never resets it).  The absolute-position editor and the
absolute-distance setter then disagreed about where the same prev
back vertex sat.

Fix: extracted a single `SystemModel._prev_element_back_vertex_world`
staticmethod that uses the slicing form (`internal_thickness_mm`).
Both call sites now route through it.  Pin tests cover the helper's
return value on a synthetic non-zero-back-thickness element and assert
the source of `set_element_absolute_field` references the helper.

### P1-UI-5: re-parent segfault risk (`waveoptics_dock.py:2134-2150`)

`_open_mft_options_dialog` re-parents the `grp_mft` form widget into
the dialog for the duration of `dlg.exec()`, then on exit
unconditionally calls `self.grp_mft.setParent(original_parent)`.
If the original parent has been destroyed C++-side during the modal
loop (closing the parent dock, switching workspace tabs that delete
the dock, end-of-life cleanup), the Python proxy is still live but
the C++ widget is dead -- `setParent(dead_C++)` dereferences freed
memory and segfaults.

Fix: imported `shiboken6` and gated the re-parent on
`shiboken6.isValid(original_parent)`.  On dead-parent, `grp_mft` is
re-parented to `None` (top level, kept alive) and a diagnostic is
posted via `diagnostics.diag.report` so the issue surfaces during
QA without crashing the app.  Structural pin asserts both
`shiboken6` and `isValid` appear in the method source.

### P1-UI-6: last-write-wins ray-trace OPD (`psf_mtf_dock.py:222-225`)

`_load_from_raytrace` built the geometric pupil by writing
`opd_grid[iy, ix] = opl` -- a fancy-indexed assignment.  When
multiple rays mapped to the same pixel (typical for N=256 grids with
dense ray fans), numpy's right-to-left iteration order silently kept
the last ray's OPD.  The retained OPD per pixel was a function of
the ray-loop order, not the optics.

Fix: switched to a mean-OPL-per-pixel accumulator using
`np.add.at(sum_grid, (iy, ix), opl)` + a parallel int counter; final
`opd_grid[valid] = sum_grid[valid] / cnt_grid[valid]`.  This matches
the `analysis/core.py` azimuthal-average pattern at
`np.bincount(..., weights=...)` (lines 986-988).  Median was the
audit's other option; mean was selected because it matches the
existing analysis-module idiom and is identical to last-write-wins
for the 1-ray-per-pixel case (preserving any existing geometry
where rays already mapped uniquely).

### P1-UI-7: out-of-aperture rays snap to pupil edge (`psf_mtf_dock.py:223-224`)

`np.clip(((x/dx) + N/2).astype(int), 0, N-1)` silently snapped any
ray landing outside the pupil grid onto the {0, N-1} index boundary,
polluting the pupil edge with OPDs whose corresponding rays were
geometrically nowhere near the rim.

Fix: built the raw indices without clipping, computed a boolean
`in_bounds = (ix_raw >= 0) & (ix_raw < N) & (iy_raw >= 0) & (iy_raw < N)`
mask, and indexed `opl_in = opl[in_bounds]` BEFORE the accumulator
pass.  The summary text now reports the number of out-of-bounds rays
that were dropped, so a poorly-sized aperture is visible immediately
rather than hidden in a smeared rim.

## E.2 -- Codegen version pin (P1-CG)

`io/codegen.py` (both `_generate_unrolled` and the system-style
`_generate_system_style` builder) now stamps the generator's
`lumenairy_version` into the auto-header comment AND emits a runtime
gate:

```python
import lumenairy
if tuple(map(int, lumenairy.__version__.split(".")[:3])) < (X, Y, Z):
    raise RuntimeError(
        f"This script was generated by lumenairy X.Y.Z; "
        f"current version is {lumenairy.__version__}. Upgrade lumenairy.")
```

where `(X, Y, Z)` is the major.minor.patch tuple of the version that
was active when codegen was invoked.  Reads the version dynamically
from the `lumenairy` package's `__version__`, so the same codegen
code emits whatever pin tuple matches the install at run time -- no
hand-maintained constant.

Tests pin both the gate's structural elements (the `lumenairy.__version__`
read, the `raise RuntimeError`, the matching pin tuple) and the
header-comment `lumenairy_version: X.Y.Z` stamp.

## E.3 -- Ghost-analysis seed kwarg (P1-GH-1)

`analysis/ghost.non_sequential_stray_light` hard-coded
`np.random.default_rng(0)` for the BSDF Monte-Carlo TIS integration
(2000-sample cos-weighted hemisphere).  Every call returned the same
TIS number, so the user could not estimate the Monte-Carlo
variance -- the integration error was hidden behind perfect call-
to-call repeatability.

Fix: added `seed: int | None = None` kwarg.  `seed=None` (the new
default) defers to `np.random.default_rng()` (system entropy) so
repeated calls give a sample-to-sample spread that is usable as a
stand-in for the integration error.  `seed=<int>` reproduces the
pre-4.15 behaviour for any caller that needs determinism (CI tests,
regression baselines, sensitivity analyses where the noise floor
must be pinned).

Backwards-compat: callers that relied on the deterministic
`seed=0` behaviour can opt back in with `non_sequential_stray_light(
..., seed=0)`.  The new public default deliberately changes the
numerical output (drawing from entropy now), which the audit
explicitly accepts in exchange for a usable uncertainty estimate.

## E.4 -- Bundled Sellmeier fallback for tuple-registered glasses (P1-GL-1)

Five `GLASS_REGISTRY` entries (`SiO2`, `F_SILICA`, `FUSED_SILICA`,
`S-LAH64`, `S-LAH79`) were tuple-registered (pointing to
`('main', 'SiO2', 'Malitson')` or `('specs', 'OHARA-optical', ...)`
shelves) with no row in `SELLMEIER_COEFFICIENTS`.  In a minimal
install (no `refractiveindex` package) every lookup raised
`ImportError`.

Fix: bundled Sellmeier coefficients for all five glasses.

| Glass | Source | n_d (Sellmeier) | n_d (refractiveindex.info) | residual |
|---|---|---|---|---|
| `SiO2` / `F_SILICA` / `FUSED_SILICA` | Malitson 1965 (J. Opt. Soc. Am. 55, 1205-1209) | 1.458464 | 1.458460 | ~4e-6 |
| `S-LAH64` | OHARA Zemax 2017-11-30 (formula 2, from refractiveindex.info-database YAML) | 1.788001 | 1.788001 | ~1e-10 |
| `S-LAH79` | OHARA Zemax 2017-11-30 (formula 2, from refractiveindex.info-database YAML) | 2.003300 | 2.003300 | ~4e-7 |

All five round-trip below the audit's 5e-5 tolerance at n_d AND
across 488 / 532 / 633 / 1064 / 1310 / 1550 nm.

Judgment call (audit-requested):

* **SiO2 / F_SILICA / FUSED_SILICA**: bundled with the well-known
  Malitson 1965 coefficients verbatim from the spec (audit-supplied),
  with C_i expressed as `(0.0684043**2, 0.1162414**2, 9.896161**2)`
  so the format stays consistent with the rest of
  `SELLMEIER_COEFFICIENTS` (B / C^2 in um^2).
* **S-LAH64 / S-LAH79**: sourced from the `refractiveindex.info-
  database` YAML for the Ohara Zemax 2017-11-30 catalog (entries
  `specs/ohara/optical/S-LAH64.yml` and `S-LAH79.yml`, both formula
  2).  These are the same coefficients the `refractiveindex` package
  consumes -- so the fallback gives bit-equal results to the
  refractiveindex-installed path (within the verified residuals
  above).  Verified against the audit-supplied n_d targets (1.78800
  and 2.00329) at d-line and confirmed within tolerance across the
  full catalogued ranges.

The dispatcher fallback path
(`glass.py:512-517`, "`if not _REFRACTIVEINDEX_AVAILABLE: if glass_name
in SELLMEIER_COEFFICIENTS: return _sellmeier_index(...)`") already
existed -- adding the rows is sufficient to enable the fallback.

Tests monkey-patch `_REFRACTIVEINDEX_AVAILABLE = False` and
`_glass_cache = {}` to simulate the minimal install, then assert
each of the five glasses returns its catalog n_d within 5e-5.

## E.5 -- Glass registry reverse-direction consistency (P2)

`_check_glass_registry_consistency` (new in v4.14.2 per P0-NEW-1's
"convert silent drift into a fail-fast at module load") only walked
the forward direction: every `'__sellmeier__'`-flagged registry
entry must have a coefficient row.  The reverse direction was
unguarded: a coefficient row added without a corresponding registry
entry was silent dead code (the dispatcher returns `ValueError` on
the missing registry entry BEFORE it consults `SELLMEIER_COEFFICIENTS`).

Fix: added a second pass that asserts every key in
`SELLMEIER_COEFFICIENTS` appears in `GLASS_REGISTRY`.  Both pure-
Sellmeier (`'__sellmeier__'`) and tuple-style registry entries are
accepted -- tuple entries fall back to `SELLMEIER_COEFFICIENTS`
when `_REFRACTIVEINDEX_AVAILABLE` is False, so the coefficient row
is reachable in that path too.

Tests inject a synthetic orphan row (`'__ORPHAN_TEST_GLASS__'`)
into `SELLMEIER_COEFFICIENTS` and assert
`_check_glass_registry_consistency` raises `RuntimeError` with the
orphan name and an `"unreachable"` rationale.  Baseline assertion
confirms the shipped registry passes both walks.
