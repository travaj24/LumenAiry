## v4.16.3 -- Agent B: default-config knob honesty pass

Closes 1 P1 + 2 P2 findings from
`docs/audits/AUDIT_V4_16_2_2026_05_20.md` concentrated on the
v4.16.2 pre-v5.0 default-config knobs (2 of 3 had zero downstream
consumers; the 1 wired knob's consumer was unreachable dead code):

* **P1-NEW-F1-1** -- Migration-Guide.md §4.16.2 documented a
  one-shot `set_default_wave_propagator('fresnel')` recipe that
  silently no-ops at v4.16.2 ship (apply_real_lens hardcodes
  'asm').  Replaced with an honest recipe that uses
  `set_default_complex_dtype` / `set_default_real_dtype` (the
  knobs with real consumers) and an inline "v4.16.2/v4.16.3
  limitation note" calling out the API-only status of the wave-
  propagator + dy knobs.
* **P2-NEW-F1-3** -- `propagate_ensemble`'s `get_default_real_dtype`
  fallback was structurally unreachable.  The earlier
  `hasattr(ensemble, 'dtype')` gate + `np.asarray` coercion at
  `ensemble.py:~287-302` guaranteed `getattr(ensemble, 'dtype',
  None)` always returned a valid numpy dtype, so the
  `except (TypeError, ValueError)` branch was structurally dead
  code and the knob had no reachable consumer library-wide.
  Refactored so `get_default_real_dtype()` is the canonical
  `in_dtype is None` fallback (a reachable code path for any
  future input that doesn't expose a `.dtype` attribute), with the
  `try/except` retained as a belt-and-suspenders guard for the
  exotic-dtype case.
* **P2-NEW-F1-4** -- `set_default_wave_propagator` and
  `set_default_dy` setters now emit a one-shot `UserWarning` that
  the knob is API-only at v4.16.2/v4.16.3 (zero downstream readers
  across the lumenairy package); consumer wiring at
  `apply_real_lens` / `apply_real_lens_traced` / `propagate` is
  staged for v5.0 alongside the file-split work.  Latched at
  module scope via `_DEFAULT_WAVE_PROPAGATOR_NO_CONSUMER_WARNED`
  and `_DEFAULT_DY_NO_CONSUMER_WARNED` so optimisation loops
  calling the setter repeatedly don't flood the warning channel.
  Parallel to the v4.16.2 `_MULTIWL_AVG_WARNED` pattern.

Picked audit option (b) -- honesty-first -- for both P1-NEW-F1-1
and P2-NEW-F1-4, per the prompt's "Pick option (b) for v4.16.3
unless you have a strong reason to go invasive."  Shipping the
resolver wiring in `apply_real_lens` / `apply_real_lens_traced`
(option a) would have crossed into territory v5.0 owns; the
honest documentation + setter warning approach matches the audit's
recommended scope.

Picked the refactor option (not the dead-code-removal option) for
P2-NEW-F1-3 because the refactor turns the knob from "API-only"
to "narrowly consumed" -- the `in_dtype is None` path is reachable
for any future ensemble-like input that lacks a `.dtype` attribute
(e.g. a list-of-arrays going through the v4.16.2 `np.asarray`
coercion that could theoretically fail in a future numpy release).
This preserves the v4.16.2 CHANGELOG claim that
`set_default_real_dtype` has at least one wired consumer.

No physics semantics change.  No new top-level API surface.  No
existing setter signatures changed.

### P1-NEW-F1-1 -- Migration-Guide.md §4.16.2 honest recipe

`Migration-Guide.md`.

**Before** (pre-v4.16.3):

```python
# Old (per-call kwarg every entry point):
field = la.apply_real_lens(field, prescription=pres, wavelength=wl,
                            dx=dx, wave_propagator='fresnel')

# New (one-shot at app initialization):
la.set_default_wave_propagator('fresnel')
field = la.apply_real_lens(field, prescription=pres, wavelength=wl, dx=dx)
```

Silently no-ops -- `apply_real_lens(_lens_real.py:209)` hardcodes
`wave_propagator: str = 'asm'` and does NOT consult
`get_default_wave_propagator()`.  User copy-pasting this recipe
silently got ASM-propagated output instead of Fresnel.

**After** (v4.16.3):

The recipe now leads with the precision knobs (which DO have real
consumers) and retains the per-call `wave_propagator=` kwarg on
the `apply_real_lens` example, paired with a clear inline
limitation note above the code block:

```markdown
> **v4.16.2/v4.16.3 limitation note.**  Two of the three new knobs
> (`set_default_wave_propagator`, `set_default_dy`) store the
> default but have **zero downstream consumers** in `lumenairy/`
> at v4.16.2 ship.  Entry points like `apply_real_lens` continue
> to hardcode `wave_propagator='asm'` and accept
> `wave_propagator=...` / `dy=...` as per-call keyword arguments.
> The library-wide resolver rollout that makes these setters
> actually steer the default at every entry point is staged for
> v5.0 alongside the file-split work.
```

And the new code recipe:

```python
import numpy as np
import lumenairy as la

# Old (per-call dtype every entry point):
field = la.apply_real_lens(field, prescription=pres, wavelength=wl,
                            dx=dx, wave_propagator='fresnel')

# New (one-shot at app initialization).  set_default_complex_dtype
# is honored library-wide; set_default_real_dtype is honored at
# the propagate_ensemble no-input-dtype real fallback site (v4.16.3+):
la.set_default_complex_dtype(np.complex64)
la.set_default_real_dtype(np.float32)

# Per-call wave_propagator= still required until v5.0:
field = la.apply_real_lens(field, prescription=pres, wavelength=wl,
                            dx=dx, wave_propagator='fresnel')
field = la.apply_real_lens_traced(field, ..., wave_propagator='fresnel')
```

### P2-NEW-F1-3 -- `propagate_ensemble` real-dtype fallback shape

`lumenairy/propagators/ensemble.py:~342-368`.

**Before** (v4.16.2):

```python
in_dtype = getattr(ensemble, 'dtype', None)
try:
    real_dtype = np.dtype(in_dtype).type(0).real.dtype
except (TypeError, ValueError):
    # v4.16.2 (pre-v5.0 prep): honour set_default_real_dtype for
    # the no-input-dtype fallback path.
    from .propagation import get_default_real_dtype
    real_dtype = get_default_real_dtype()
```

The `try` clause never raises in practice: by the time control
reaches this site, `ensemble.dtype` exists (the earlier
`hasattr(ensemble, 'dtype')` gate + `np.asarray` coercion at
`:287-302` guaranteed it), and `np.dtype(some_numpy_dtype)
.type(0).real.dtype` succeeds for every numeric / bool / object
numpy dtype.  The single CHANGELOG-cited consumer wiring for
`set_default_real_dtype` was structurally dead code.

**After** (v4.16.3):

```python
# v4.16.3 (audit P2-NEW-F1-3): re-shape the fallback so
# get_default_real_dtype() is the canonical in_dtype is None path
# rather than an unreachable except branch.
from .propagation import get_default_real_dtype
in_dtype = getattr(ensemble, 'dtype', None)
if in_dtype is None:
    real_dtype = get_default_real_dtype()
else:
    try:
        real_dtype = np.dtype(in_dtype).type(0).real.dtype
    except (TypeError, ValueError):
        real_dtype = get_default_real_dtype()
```

The `in_dtype is None` branch is reachable for any future
ensemble-like input that lacks a `.dtype` attribute (the duck-
typing gate at `:287-296` does include a coercion fallback to
`np.asarray`, but a future numpy release that fails on exotic
inputs could leave `ensemble` without a usable dtype attribute).
The retained `try/except` guards the exotic-dtype case (e.g. a
future numpy dtype that doesn't expose `.real`).

Pinned by `TestEnsembleRealDtypeFallbackShape` (2 tests):
* `test_get_default_real_dtype_is_reachable_via_none_branch` --
  source-level structural pin (`inspect.getsource`) requires an
  `if in_dtype is None:` guard with a `get_default_real_dtype()`
  call within ~500 chars.
* `test_propagate_ensemble_honours_real_dtype_via_default` --
  end-to-end happy-path smoke: complex64 ensemble through a
  trivial propagator yields a float32 accumulator (the
  matching-real-counterpart contract still works post-refactor).

### P2-NEW-F1-4 -- one-shot UserWarning on no-consumer setters

`lumenairy/propagators/propagation.py:~270-360`.

**Module-level latches** (added just below the three globals):

```python
# v4.16.3 (audit P2-NEW-F1-4): module-level latches so the
# "API-only in v4.16.2/v4.16.3; consumer wiring follows in v5.0"
# notice fires only once per process (parallel to
# _MULTIWL_AVG_WARNED in optimize.core).
_DEFAULT_WAVE_PROPAGATOR_NO_CONSUMER_WARNED = False
_DEFAULT_DY_NO_CONSUMER_WARNED = False
```

**Emission inside `set_default_wave_propagator`** (after the
existing validation + `DEFAULT_WAVE_PROPAGATOR = name` assignment):

```python
if not _DEFAULT_WAVE_PROPAGATOR_NO_CONSUMER_WARNED:
    _DEFAULT_WAVE_PROPAGATOR_NO_CONSUMER_WARNED = True
    import warnings as _warnings
    _warnings.warn(
        "set_default_wave_propagator: stores the default but no "
        "library consumer reads it yet in v4.16.2/v4.16.3 (zero "
        "downstream readers across the lumenairy package).  "
        "Consumer wiring at apply_real_lens / "
        "apply_real_lens_traced / propagate is staged for v5.0 "
        "alongside the file-split work.  In the interim, pass "
        "``wave_propagator=`` per-call.  Silence this notice via "
        "``warnings.filterwarnings('ignore', category=UserWarning, "
        "module='lumenairy.propagators.propagation')``.",
        UserWarning, stacklevel=2,
    )
```

Parallel emission inside `set_default_dy` (with `set_default_dy`
substitutions and a `dy=` per-call kwarg pointer).

**Critical detail -- ValueError-before-warn ordering:** the
validation block (`if not isinstance(name, str):` etc.) runs
BEFORE the warn-emit / latch-flip code, so a user typo
(`set_default_wave_propagator('GBD')`) raises `ValueError`
without flipping the latch -- the legitimate notice still fires
on the next valid call.  Pinned by
`test_validation_failure_no_warning` (one per setter).

`set_default_dy(None)` -- the `value is None` early-return branch
was lifted up so the warn-emit code runs in both branches.  Both
`set_default_dy(None)` and `set_default_dy(<float>)` legitimately
set the default, so both should surface the no-consumer notice.

`set_default_real_dtype` does NOT emit the no-consumer warning --
it IS consumed (post-P2-NEW-F1-3 refactor) at the
`propagate_ensemble` `in_dtype is None` fallback.  Pinned by
`TestSetDefaultRealDtypeDoesNotEmitNoConsumerWarning`.

**Documentation update -- the 3-knob comment block at
`propagation.py:~227-265`** now states the v4.16.3 honest status
per knob: `DEFAULT_REAL_DTYPE` "consumed at one site
(propagate_ensemble's no-input-dtype real-accumulator fallback)";
`DEFAULT_WAVE_PROPAGATOR` and `DEFAULT_DY` "API ONLY in
v4.16.2/v4.16.3.  No library code reads it yet.  Setter emits a
one-shot UserWarning."

## Migration notes for users

* **`set_default_wave_propagator(name)`** -- first call per process
  now emits a one-shot `UserWarning` that the knob is API-only at
  v4.16.2/v4.16.3 (no library code reads it yet).  The setter
  stores the value; `get_default_wave_propagator()` returns the
  stored value; but `apply_real_lens` / `apply_real_lens_traced`
  / `propagate` continue to hardcode `'asm'`.  Pass
  `wave_propagator=` per-call until v5.0 lands the resolver.
  Silence the notice via
  `warnings.filterwarnings('ignore', category=UserWarning,
  module='lumenairy.propagators.propagation')`.
* **`set_default_dy(value)`** -- same status as
  `set_default_wave_propagator`.  Pass `dy=` per-call until v5.0.
* **`set_default_real_dtype(dtype)`** -- the v4.16.2 CHANGELOG
  claim that this knob has at least one wired consumer is now
  honest at v4.16.3: `propagate_ensemble`'s `in_dtype is None`
  real-accumulator fallback reads
  `get_default_real_dtype()` rather than hardcoding `np.float64`.
  No user-visible behaviour change for typical ndarray inputs
  (which DO expose `.dtype` and so use the matching-real-counterpart
  fast path); the knob is consulted only for input shapes that
  lack a `.dtype` attribute.
* **Migration-Guide.md §4.16.2** -- the recipe at
  `Migration-Guide.md:163-175` was rewritten.  The pre-v4.16.3
  copy-paste recipe that combined
  `set_default_wave_propagator('fresnel')` with
  `apply_real_lens(field, ..., dx=dx)` (no per-call
  `wave_propagator=`) silently produced ASM-propagated output
  instead of Fresnel.  Users who copied that recipe should
  re-add the per-call `wave_propagator='fresnel'` kwarg until
  v5.0.
