## Bug 1 -- `MultiWavelengthMerit.evaluate` SUM -> AVG

**Site:** `lumenairy/optimize/core.py`, the `return` line at the
tail of `MultiWavelengthMerit.evaluate`.  Pre-fix line was line 2509
in v4.16.0; post-fix the explicit `return self.weight * total /
max(len(self.wavelengths), 1)` is at line 2520 (with comment block
above).

**Before:**
```python
            total = total + self.sub_merit.evaluate(sub_ctx)
        ...
        return self.weight * total
```

**After:**
```python
            total = total + self.sub_merit.evaluate(sub_ctx)
        ...
        # v4.16.1 (AUDIT_V4_16_0_DEEP P1-DEEP-1-1): SUM -> AVG.
        return self.weight * total / max(len(self.wavelengths), 1)
```

**Physics doublecheck.** The docstring documents this class as
averaging the sub-merit across wavelengths, and both sibling classes
(`MultiFieldMerit`, `ToleranceAwareMerit`) already divide by
`len(...)` at their `return`.  The fix restores the documented and
sibling-class-consistent semantics.

**Regression-test design.** A trivial `_ConstantMerit` returns a
fixed value per sub-context call.  Build a 1-wavelength wrapper and
a 3-wavelength wrapper around the same sub-merit; under AVG
semantics both return the constant.  Under the pre-v4.16.1 SUM
semantics the 3-wavelength wrapper returned `3 * constant`.  The
sibling-parity test (`test_bug1_multiwavelength_merit_sibling_parity`)
exercises all three wrapper classes against the same constant
sub-merit and pins the AVG shape across them.

**Are there sibling sites with the same bug?**  Both sibling
classes (`MultiFieldMerit.evaluate` at line 2693, `ToleranceAware
Merit.evaluate` at line 3007 post-drift) already use the
`total / max(len(...), 1)` form -- the bug was localised to
`MultiWavelengthMerit`.  No additional sites need patching.

## Bug 2 -- `shack_hartmann` wavefront pitch quantisation

**Site:** `lumenairy/analysis/detector.py`, the
`np.cumsum(...) * lenslet_pitch` pair at line 576-577 in v4.16.0.
Post-fix the cumsum uses `pitch_actual = sa_pixels * dx`.

**Before:**
```python
    wf_x = np.cumsum(sx_safe, axis=1) * lenslet_pitch
    wf_y = np.cumsum(sy_safe, axis=0) * lenslet_pitch
```

**After:**
```python
    # v4.16.1 (AUDIT_V4_16_0_DEEP P1-DEEP-2-1): use the ACTUAL on-grid
    # quantized pitch for the slope-to-wavefront integration.
    pitch_actual = sa_pixels * dx
    wf_x = np.cumsum(sx_safe, axis=1) * pitch_actual
    wf_y = np.cumsum(sy_safe, axis=0) * pitch_actual
```

**Physics doublecheck.** The Shack-Hartmann measures focal-spot
centroids per sub-aperture, converts to local wavefront slopes
(`slope = centroid_shift / lenslet_focal`), and reconstructs the
wavefront by cumulative-trapezoidal integration of the slope grid:
`delta_phi = slope * pitch`.  The slopes are measured between
sub-aperture centres spaced by `sa_pixels * dx` (the integer-pixel
quantisation of the lenslet pitch).  The integration step `delta_phi
= slope * pitch` MUST use the same pitch as the measurement
geometry -- otherwise the reconstructed amplitude is biased by
`(sa_pixels * dx) / lenslet_pitch`.

**Empirical demonstration of the bug pre-fix.** At `dx = 5 um` and
`lenslet_pitch = 8.5 um` (ratio 1.7), `sa_pixels = round(1.7) = 2`,
so `pitch_actual = 10 um` while the requested `lenslet_pitch = 8.5
um`.  Pre-v4.16.1 the integration step multiplied by `8.5 um`
(requested); post-v4.16.1 it multiplies by `10 um` (actual).  The
reconstructed wavefront amplitude pre-fix was `8.5 / 10 = 0.85` of
the post-fix amplitude -- a `15%` low bias relative to the
physically correct on-grid value (or, equivalently, the post-fix
amplitude is `1.176x` the pre-fix amplitude, i.e. `17.6%` higher).

**Regression-test design.** The
`test_bug2_shack_hartmann_non_integer_pitch_amplitude` test takes a
known constant-slope (pure-x-tilt) input, runs the SH, and
empirically inverts the cumsum step to recover the multiplicative
pitch `P` used by the reconstruction.  Post-fix `P == sa_pixels *
dx` to within 1%; pre-fix `P == lenslet_pitch` (a 15-18% offset).
The
`test_bug2_shack_hartmann_amplitude_ratio_physics_pin` test runs
two configurations with the SAME `sa_pixels` but different
requested `lenslet_pitch / dx` ratios (1.6 vs 2.4) -- post-fix both
recover the same on-grid `P`; pre-fix they tracked the two
different requested pitches (1.5x apart).  The integer-ratio sanity
test pins that the fix is a no-op when `sa_pixels * dx ==
lenslet_pitch`.

**Are there sibling sites with the same bug?**  Searched the file
for other `cumsum * lenslet_pitch` patterns -- this was the only
site in the SH reconstruction.  The 3 other `lenslet_pitch` uses
(lines 386, 400, 403) are at the pre-quantisation step (sub-
aperture coordinate setup + guard) where the requested value IS
correct.  Fix is complete; no additional sites.

## Bug 3 -- `_detect_backend` directory misclassification

**Site:** `lumenairy/io/storage.py`, lines 1315-1319 in v4.16.0.
Post-fix the function expands to ~25 lines (includes docstring +
the marker-file check).

**Before:**
```python
def _detect_backend(path):
    """Auto-detect backend from file extension or path structure."""
    if path.endswith('.zarr') or os.path.isdir(path):
        return 'zarr'
    return 'hdf5'
```

**After:**
```python
def _detect_backend(path):
    """Auto-detect backend from file extension or path structure.
    ...
    """
    s = str(path)
    if s.endswith('.zarr'):
        return 'zarr'
    if os.path.isdir(s):
        # Restrict directory-routing to a real Zarr store via the
        # canonical store-marker files.
        if (os.path.exists(os.path.join(s, 'zarr.json'))
                or os.path.exists(os.path.join(s, '.zarray'))):
            return 'zarr'
    return 'hdf5'
```

**Physics-domain doublecheck.** Per the Zarr v3 spec
(https://zarr-specs.readthedocs.io/en/latest/v3/core/v3.0.html),
`zarr.json` at the group root is the canonical Zarr v3 store
marker.  Per the Zarr v2 spec (https://zarr.readthedocs.io/en/
stable/spec/v2.html), `.zarray` at the array root is the v2
marker.  A directory without either marker is, by definition, not
a Zarr store.  The new directory-routing check is therefore
spec-compliant -- it rejects a generic directory as Zarr and falls
through to HDF5.

**Regression-test design.** Three tests pin the fix:
1. `test_bug3_detect_backend_h5_with_sibling_directory` creates a
   bare directory matching a typical HDF5 path; pre-v4.16.1 this
   would silently route to Zarr.  Post-fix it routes to HDF5.
2. `test_bug3_detect_backend_zarr_marker_routes_to_zarr` exercises
   both Zarr v3 (`zarr.json`) and v2 (`.zarray`) markers and a
   bare directory; pins all three dispatch outcomes.
3. `test_bug3_detect_backend_accepts_pathlib_path` passes
   `pathlib.Path` objects with `.zarr` and `.h5` extensions; pre-
   v4.16.1 this would raise `AttributeError` because `Path` has no
   `.endswith` method.  Post-fix the `str(path)` cast normalises
   the input.

**Are there sibling sites with the same bug?**  Searched
`io/storage.py` for other `path.endswith(...)` patterns: lines
1357 and 1451 already use `str(filepath).endswith(...)` (the
correct pattern).  Other dispatcher functions (`append_plane`,
`load_planes`, `list_planes`, `write_sim_metadata`, etc.) all
route through `_detect_backend`, so the fix propagates to every
backend-dispatch surface.  No additional sites need patching.

## Bug 4 -- LM bounds parsing accepts `None` endpoints

**Site:** `lumenairy/optimize/core.py`, the two-line bound parsing
inside the `method == 'lm'` branch of `design_optimize`, lines
4057-4058 in v4.16.0.  Post-fix the parser is a 5-line helper
function `_resolve_bound` plus the two list comprehensions.

**Before:**
```python
            lb = np.array([b[0] if b else -np.inf for b in (bounds or [None] * n_params)])
            ub = np.array([b[1] if b else +np.inf for b in (bounds or [None] * n_params)])
```

**After:**
```python
            # v4.16.1 (AUDIT_V4_16_0_DEEP P1-DEEP-1-2): explicit
            # None-aware unpacking.  ...
            def _resolve_bound(b, i, default):
                if b is None:
                    return default
                v = b[i]
                if v is None:
                    return default
                return float(v)
            _bounds_iter = bounds if bounds is not None else [None] * n_params
            lb = np.array([_resolve_bound(b, 0, -np.inf) for b in _bounds_iter],
                          dtype=np.float64)
            ub = np.array([_resolve_bound(b, 1, +np.inf) for b in _bounds_iter],
                          dtype=np.float64)
```

**Physics doublecheck.** scipy's `least_squares` documents
`bounds=(lb, ub)` as 1-D array-likes of finite floats OR `+/-np.inf`
(see https://docs.scipy.org/doc/scipy/reference/generated/
scipy.optimize.least_squares.html).  `None` is NOT in the spec.
The fix routes any user-supplied `None` to `+/-np.inf` (the
"no bound on this side" idiom in the optimisation literature) and
produces a clean float64 array that scipy accepts without complaint.

**Empirical demonstration of the bug pre-fix.**  Calling
`design_optimize(..., method='lm', bounds=[(None, 1.0), (0.0, None),
(-2.0, 2.0)])` pre-v4.16.1: `b = (None, 1.0)` is truthy (non-empty
tuple), so `b[0] if b else -np.inf` returns `None`, which leaks
into `np.array([None, 0.0, -2.0])` -> object-dtype array -> scipy
raises an opaque error inside `least_squares`.  Post-v4.16.1 the
explicit `None`-check returns `-np.inf` for the missing endpoints
and the call proceeds cleanly.

**Regression-test design.** `test_bug4_lm_bounds_with_none_lower`
exercises a 3-parameter LM problem with mixed `(None, finite)`,
`(finite, None)`, and `(finite, finite)` bounds; pre-v4.16.1 this
raises; post-fix it completes cleanly.  `test_bug4_lm_bounds_
finite_respected` is a sanity test that the explicit-finite-bound
path is unchanged (a `[0, 1]` upper-bound is honoured on a problem
whose unconstrained optimum lies outside that interval).

**Are there sibling sites with the same bug?**  Searched the file
for other `if b else` / `b[0] if b else` patterns in bounds-
handling code.  The other bounds-consuming methods
(`differential_evolution`, `dual_annealing`, `L-BFGS-B`,
`trust-constr`, etc.) pass `bounds` through to scipy unchanged
(scipy's `_minimize` family accepts the `(lb, ub)` tuple list
directly without the LM-specific `np.array` conversion).  Of those
scipy entry points, `scipy.optimize.minimize` with `'L-BFGS-B'`
DOES accept `None` endpoints per the API spec.  `differential_
evolution` and `dual_annealing` REQUIRE finite bounds and raise
on `None`.  The LM-specific bug was the result of an extra
`np.array(...)` conversion not present on the other paths.

**Are there sibling sites where None bounds would also break?**
We checked `multi_objective.py`'s pymoo wrapper and the
`basin_hopping` minimizer_kwargs -- they pass `bounds` directly to
scipy without converting.  No other sites need patching.
