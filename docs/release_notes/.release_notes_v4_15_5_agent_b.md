## v4.15.5 -- Agent B scope: OPD plotting + validation helper closures

Closes 2 P1 + 4 P2 + 2 P3 findings from
`docs/audits/AUDIT_V4_15_4_2026_05_19.md` localised to
`lumenairy/analysis/plotting.py`, `lumenairy/_validation.py`, the
two vector-diffraction call sites in
`lumenairy/propagators/vector_diffraction.py`, and the singlet OPD
example.  All changes are additive and backwards-compatible at the
public-API surface (`fan_units` defaults to `'m'` which is the
v4.15.4 input convention; `_check_2d_scalar_field` `input_kind`
defaults to `'field'` which is the v4.15.4 error-message wording;
`radial_rms_n_bins` defaults to `'auto'` which clamps below the
historic fixed 32 only on tiny grids).

### B.1 -- P1-NEW-V2-1: `plot_opd_fan` ``fan_units`` kwarg

`lumenairy.raytrace.opd_fan_data` returns OPD in WAVES
(`raytrace/core.py:3772, 3780` divides by `wavelength` internally);
`plot_opd_fan` was documented as expecting METRES.  The canonical
pipeline `plot_opd_fan(*opd_fan_data(...), units='waves',
wavelength=wl)` therefore divided by `wavelength` a SECOND time,
silently shrinking values by ~6e5 at 633 nm.

Fix: add a `fan_units: str = 'm'` kwarg to `plot_opd_fan`.

* `fan_units='m'` (default; back-compat with v4.15.4) interprets
  the input arrays as metres, exactly as v4.15.4 did.
* `fan_units='waves'` interprets the input as waves of the trace
  wavelength.  Internally the arrays are multiplied by `wavelength`
  on entry, so the existing metres-based scaling path stays the
  single source of truth for the `units='waves' | 'nm' | 'um' | 'm'`
  display conversion.
* Invalid values raise `ValueError` with a useful message.
* `fan_units='waves'` requires a positive `wavelength` regardless
  of the display `units` (we need it to go waves -> metres first);
  validated up front with a clear error.

Docstring updated prominently: a new "common pitfall" paragraph on
the `fan_units` kwarg explains the `opd_fan_data` mismatch and
shows the canonical pipeline.

**Decision: defaulted to `'m'`**.  This preserves v4.15.4 callers
exactly (including the 10 existing unit tests and any user code
that was already manually converting waves -> metres).  The audit
explicitly recommended this back-compat default; the alternative
(default `'waves'`) would have broken the 10 v4.15.4 tests as
well as the documented v4.15.4 docstring wording.  Users on the
`opd_fan_data` pipeline now opt in to `fan_units='waves'` via a
single explicit kwarg.

### B.2 -- P1-NEW-V2-2: `_radial_rms_profile` centered RMS

`_radial_rms_profile` (`plotting.py:1416`) used the raw
`sqrt(mean(opd**2))` per bin -- variance about zero, dominated by
piston.  The 1-D fan RMS (`_opd_pv_rms_1d`, `plotting.py:1173`) and
the 2-D heatmap RMS (`plot_wavefront`, `plotting.py:1107-1108`)
both used the mean-subtracted variance form, so the 4-panel summary
displayed two RMS numbers for the same OPD that did not reconcile
(the singlet example printed RMS = 1.3347 waves uncentered, while
the heatmap annotation reported ~0.89 waves centered).

Fix: switch the per-bin reduction to the centered form
`sqrt(mean((opd - in_aperture_mean)**2))`.  The baseline mean is
the SINGLE in-aperture mean of the entire OPD (computed once),
NOT a per-bin local mean -- a per-bin local mean would by
construction zero out every annulus, returning a flat line at
machine epsilon for any axisymmetric OPD.

Docstring updated explicitly: a new paragraph notes the centered
convention, cites the matching `plot_wavefront` and `_opd_pv_rms_1d`
sites, and explains why the global mean is the right choice over a
local mean.

### B.3 -- P2-NEW-V2-3: `plot_opd_summary` docstring units fix

v4.15.4 docstring at `plotting.py:1459-1461` said `opd_2d` "Inputs
are interpreted in the `units` system" -- the code in fact treated
the input as metres and multiplied by `1/wavelength` for
`units='waves'` (line 1593-1594).  The fan args explicitly said
"in METRES" so the 2-D arg's docstring was inconsistent.

Fix: rewrote the `opd_2d` parameter description to say
"2-D OPD map in METRES" + a `.. note::` block clarifying that
`units` controls only the DISPLAY conversion.  Also updated the
`units` description to note "the 2-D OPD is always interpreted in
metres internally."

### B.4 -- P2-NEW-V2-4: example centered-RMS print

`examples/plot_opd_summary_singlet.py:83` printed
`np.sqrt(np.mean(finite**2))` = 1.3347 waves; the heatmap
annotation rendered centered RMS = 0.89 waves.  ~50% disagreement
on the same OPD.

Fix: switched the example to the centered form
`np.sqrt(np.mean((finite - finite.mean())**2))` and updated the
print label to `centered RMS = ...`.

**New centered-RMS value (replacing v4.15.4's 1.3347 waves):**

```
Singlet N-BK7 R1=+50/R2=-50 mm, d=4 mm, A=10 mm, lambda = 633 nm
  2-D OPD: PV = 2.9318 waves, centered RMS = 0.8901 waves
```

This matches the heatmap annotation on the same figure to the
displayed precision and is consistent with the radial-RMS profile
in the (0, 1) panel (now also centered).

PV is unchanged (2.9318 waves) -- only the RMS interpretation
moved.  **Agent C should update CHANGELOG/ROADMAP/README** if any
of those reference the v4.15.4 1.33-waves uncentered value.  The
v4.15.4 release notes / audit cite that number; the value is now
0.8901 waves.

### B.5 -- P2-NEW-F1-3: `_check_2d_scalar_field` ``input_kind``

The helper's error message hardcoded "expected 2-D complex field"
but `richards_wolf_focus` and `debye_wolf_psf` take a pupil per
their docstrings.  Users passing wrong-shape inputs to these two
saw "expected 2-D complex field" -- semantically misleading.

Fix: parameterise the helper with
`input_kind: str = 'field'`; threaded through both vector-
diffraction call sites with `input_kind='pupil'`.  Backwards-
compatible default preserves the v4.15.4 wording for every other
call site.

If Agent A's V6 walker surfaces `compute_psf` / `compute_otf` /
`compute_mtf` as new guarded sites, those analyzers may benefit
from `input_kind='pupil'` or `input_kind='psf'` per the function
semantics; left as an integration-time choice for Agent A so we
don't both edit the same call sites.

### B.6 -- P2-NEW-V2-5: even-N central-row / column fallback

`plot_opd_summary` at `plotting.py:1545-1551` (v4.15.4 line
numbers) used `col_centre = Nx // 2` and `row_centre = Ny // 2`
for the fallback fan extraction, but `_radial_rms_profile` used
`(Nx - 1) / 2.0` / `(Ny - 1) / 2.0` as the geometric centre.  For
odd N these lined up; for even N=32 the index sat one half-pixel
right of the geometric centre -- a ~3% offset of semi-aperture
relative to the radial baseline.

Fix: changed both to `(N - 1) // 2`.  For odd N this is the unique
central sample (unchanged); for even N it picks the lower of the
two centre-adjacent samples (sub-pixel error <= 0.5 pixel either
way, but now consistent with the radial profile's geometric centre).
Added a `Notes` section in the docstring explaining the convention
and recommending explicit `(py, opd_y, px, opd_x)` from
`opd_fan_data` for sub-pixel-accurate chief-ray referencing.

### B.7 -- P3-NEW-F1-4: `plot_opd_fan` docstring specifies centered RMS

v4.15.4 docstring at `plotting.py:1265` just said "RMS" without
specifying the convention.

Fix: replaced the brief "PV / RMS overlay" line with an explicit:

> PV: max - min over finite (in-aperture) pixels.
> RMS: centered RMS about the in-aperture mean (matches
> :func:`plot_wavefront` convention so the 2-D heatmap and the
> 1-D fan RMS numbers reconcile).

### B.8 -- P3-NEW-F1-5: `radial_rms_n_bins` exposed kwarg

`_radial_rms_profile` used a fixed `n_bins=32`.  On a 16x16 OPD,
11 of 32 bins are empty -> visibly fragmented line.

Fix: added a `radial_rms_n_bins: int | 'auto' = 'auto'` kwarg to
`plot_opd_summary`.  The `'auto'` default calls a new
`_auto_n_bins(N_in_aperture, ceiling=32)` helper that clamps to
`min(32, int(sqrt(N_in_aperture)) // 2)` so the resolution scales
with the available pixel count.  Explicit integers bypass the
clamp.  Non-positive integers raise `ValueError`.  Internally
`_radial_rms_profile`'s signature is unchanged (still takes
`n_bins`) so the helper remains independently testable; only the
plumbing in `plot_opd_summary` is new.
